0.1立项的核心抽象

断言
风控正在经历一次性质上的范式转移：从「靠人扩张能力」到「靠系统扩张能力」。在快手这种头部公司，这不是效率话题，是对竞品的相对位置 + 对监管的解释能力 + 对黑产的对抗 ROI 三件事的同时位移。

本立项的 ask：¥1500 万 / 6-12 周 / 1 个内容安全子场景 shadow 实验。

立项决策三角 · 认知框架

Part 1-7 不是 7 个孤立判断，是一个"立项三角"的三个支撑角。每个角立得起来 → 三角稳定 → 立项；任一角塌 → 立项垮。

这是一个 mental model：把"要不要做"压成一个有形状的认知图——三角形稳定 / 不稳定一目了然。可套用任何战略级立项判断。

认知框架的可复用性：这个"立项三角"是看待立项的形状——必然性是顶角（为什么必须做），窗口性 + 可控性是底角（为什么现在 + 不出事兜底）。三角是"最少能立住的形状"——用三角而不是四边五边，是因为立项判断本质就这三件事，不能少也不必多。
套用任何战略级"要不要做 X"判断：站到三角形外面看，三个角都立得起来吗？

URG (Unified Risk Graph 统一风险图) 是啥

一句话：风控所有事实的统一数据底座。所有人 / Agent / 系统读同一份事实。

类比：现状像散在不同 Word 文档里的数据——档案中心一份、case 一份、判罚一份；Alice 调查 case 要切 5 个系统拼数据。URG 像把所有文档合并到一个 Notion workspace：所有人编辑同一份，互相能看到。

MVP 期只 4 个核心实体（CTO 警告"不要一上来全做"）：Case / Action / EvidenceRef / TraceRef。其他实体逐步并入。

关键约束：Agent 永远不直接写 URG，必须经 Action Adapter 过门。所有写入带元数据（谁 / 何时 / 依据 / trace_id）。事件溯源（append-only）。

完整解释见 附录 D 术语速查。

The Gate（控制平面 / 架构承重墙）是啥

一句话：所有"写到生产"的动作必须经过的唯一入口，是 AI Native 风控架构的承重墙。

包含 4 个组件：Action Adapter（唯一写动作入口）+ Policy-as-Code（红线代码化）+ Trace / Replay / Audit（全链路可追溯）+ Rollback（git-style 可回滚）。

类比：像机场安检——每个想登机（写生产数据）的人必须过同一道门 / 同一套检查。机场可以扩建航站楼（加 Agent），但安检不变。

v2-v3 期最大工程：把现有所有风控写动作入口（判罚 / 策略 / 运营后台 / 工单 / 应急通道）收编到 The Gate 或封禁。否则 The Gate 只是 Agent 的门，不是生产动作的唯一门。

Risk Agent Society（多 Agent 协作运行时）是啥

一句话：多个域内 Agent 协同跑的运行时层，跑在 The Gate + URG 之上。

终态包含：内容安全 Agent 群 / 反欺诈 Agent 群 / 商家电商 Agent 群 / 合规审查 Agent 群 / 跨域 Arbiter Agent（仲裁冲突）。

"Society" 这个词刻意选用——多 Agent 不是"线性流水线"，是"协作社会"：有冲突、有仲裁、有专长分工，但仍受控制平面 + 治理层约束。

建设优先级倒数第 2：必须先立 The Gate 才能建 Agent Society，否则做出一堆 Agent 没控制平面承接 = 愿景项目。

Action Adapter / Policy-as-Code / Trace / Rollback 是啥

Action Adapter：The Gate 的写入组件。Agent 想做任何动作（建 case / 改优先级 / 路由人审 / 提议判罚）必须调它。像银行柜台——核身份 / 查规定 / 查幂等 / 执行 / 记账。

Policy-as-Code：把"规则 / 红线 / 权限"写成代码由统一引擎运行时强制。不写在文档 / PPT / 某人脑子里。例如"实时机审禁调 LLM"这条红线写成 Rego 代码，每次请求自动检查。

Trace / Replay / Audit：每次 Agent 动作的完整"过程录像"——结构化、可关联、可原样回放。监管 inquiry 时可秒级溯源"为什么这个动作"。

Rollback：每次策略变更是 git-style commit，一键回到上一稳定版本。守门指标越界自动回滚。

3.1支柱 1 · 结构性失效

展开：加规则 / 加模型 / 加审核员 / 加平台 在头部公司语境下为什么都到顶

加规则到顶：

  • 策略数已 40000+，新规则跟旧规则冲突 / 覆盖度饱和
  • 维护成本（review / 灰度 / 监测）超过新增价值
  • 规则只能解决"已经见过"的对抗模式

加模型到顶：

  • 单点模型对抗鲁棒性边际收益递减（黑产专攻模型盲点）
  • 模型迭代周期（2-6 周）落后于对抗演化周期（< 2-3 个月）
  • 跨场景泛化弱（短视频模型用不到电商）

加审核员（含 BPO）到顶：

  • BPO 弹性招聘也有上限（培训周期 3-6 个月 + 人才市场容量）
  • 外包能力天花板（不能做跨域综合 / 对抗发现 / 合规解释）
  • 劳动力成本 8-12%/年上涨
  • 24/7 排班 + 倦怠管理边际成本增加

加策略平台到顶：

  • 再多平台还是 O(人头)，没解决"判断本身"是瓶颈
  • 跨业务线平台整合复杂度爆炸
  • 新业务上线要重做平台适配

3.2支柱 2 · 性质不同的解法

AI Agent 解决的是规则 / 模型物理上做不到的事——不是它们的延伸。

规则模型Agent
解决问题closed-form 高速过滤closed-form 分类 / 评分open-form 开放推理
新对抗上线3-7 天2-6 周当时即可（喂证据推理）
多步综合不能不能可以
跨域综合不能不能可以
对话解释不能不能可以

关键概念：工作单元级的接管。规则 / 模型替代"单步判断"，Agent 第一次能替代"调查 → 综合 → 提议 → 解释"整条工作链路。

展开：快手语境的 open-form 例子

电商商家 M5678 被多个用户举报售假。一个真实的 open-form 工作流：

  1. 查商家近 90 天交易（SKU 维度找异常）
  2. 查用户退款 + 评价（情绪 + 关键词）
  3. 查相似商家历史处罚（哪些被永久封禁，哪些是误判）
  4. 查商家关联账号（同设备 / 同 IP / 同收款）
  5. 查物流（虚假物流？）
  6. 综合 5 条线索：是真售假、是争议性产品、还是被恶意举报？
  7. 给处置建议（删品 / 限流 / 封店）+ 引用相似 case 处置先例

规则做不到——不是 if-then 能描述的。

模型做不到——不是分类任务。

人能做，但 10-15 分钟一个 case。在快手日均几十万这类 case 量下，人审产能根本不够。

Agent 5 分钟一个，并行 N 个。

压力头部公司特有
① 监管表率央网信办 / 公安部对头部公司"做表率"，AI 治理新规快手必受要求

8.5控制平面建设优先级（CTO 给的 7 项顺序，不可乱序）

  2. Trace / Replay / Audit —— 没有 trace 不能做后面的
  3. Risk Case Service —— case 作为统一资产
  4. URG MVP —— 只统一 Case / Action / EvidenceRef / TraceRef，不要一开始统一 User / Content / Device
  5. Agent Contract —— 定义 Agent 间交换的标准对象：proposal / evidence / risk_score / confidence / policy_conflict / required_escalation

8.6数据飞轮 + Agent 自进化（核心新内容）

飞轮成立的关键
不是"AI 自己改自己"，是系统按结构化方式沉淀 6 类资产 + 受控自动化 + 严格的不可自改红线。CTO 反复强调：自进化的边界比能力更重要。

8.6.1 数据飞轮的 6 个资产层（不是 5 个，CTO 加了第 6 个）

资产层每次 case 产生用途

② 采纳信号审核员"采纳 / 修改 / 驳回" + 时延（多久决策）分层 ground truth（见 8.6.3）
③ Memory 候选成功闭环的 case 经状态机升级下次相似 case 检索引用
④ Skill 模板重复模式归纳的调查 / 处置 template新版 Agent prompt / tool 选择优化
⑤ 对抗样本库红队主动找 + 漏报 / 误杀 case 自动入库eval set + 对抗鲁棒性训练

8.6.2 自进化的 4 个层次（边界严格，L4 是架构红线永远关）

层类型允许范围边界
L1 自动 每日用 gold set 跑 eval，监控漂移 仅产报告，人看
L2 半自动 + 严格 guardrail Prompt / Tool 变更先 A/B，达统计显著且无回归 → 自动 promote 必须 6 道 guardrail（见下方）
L3 半自动 Memory 候选经状态机自动升级 tier；失败的自动 deprecate 高 tier 必须人签
L4 架构红线永远关 Agent 不能改自己的 prompt / tool / policy / eval 集 / Memory 准入规则，不能合并自己的 PR 最多生成 proposal，由人或独立治理系统批准
L2 自动 promote 的 6 道 guardrail（缺一不可）
① 最小样本量 ≥ 阈值
② 分桶无回归（按业务线 / case 类型 / 时间段分桶都不能负向）
③ 核心红线指标（误杀率 / 漏放率）零回退
④ 冷启动观察期（promote 后 N 天监控）
⑤ 人工 veto 窗口（自动 promote 公告期内人可否决）
⑥ 自动回滚条件（出指标越界立即回滚）

没这 6 道，"统计显著"会变成"自动上线事故"。

8.6.3 采纳信号必须分层（不能直接当 ground truth）

审核员采纳不等于 Agent 对，驳回也不等于 Agent 错。人审本身有误判、赶时间、业务压力、口径漂移。哪些采纳信号能进训练，哪些必须等更长时间，必须明确：

信号类型等待时间能否进训练
审核员当时决策（采纳 / 驳回）实时仅 evaluation 信号，不进训练
+ 商家 / 用户申诉结果3-7 天弱 ground truth，进 holdout
+ 二审 / 复核结果1-2 周较强 ground truth
+ 判罚生效 + 业务 outcome（GMV / NPS 影响）30-60 天强 ground truth，可进训练集
+ 长期观察（复发 / 同类 case 验证）3-6 个月最强 ground truth，进 gold set

内容营销号的模式不能直接迁移到电商商家。反欺诈设备关联不能直接迁移到未成年保护。跨域迁移默认禁止，需明确契约：

8.6.6 Memory Curator 工程化分层（百万 case/day 不靠人撑）

百万 case/day 下，Curator 不可能人工审所有 memory。必须分层采样：

  1. 机器分层：按 4 维评估每个 memory 候选 —— 风险等级 / 影响面 / 置信度 / 争议度
  2. 低风险 + 高置信 + 低争议 → 自动进 DRAFT，进入低 tier，不需要人审
  3. 高风险 OR 低置信 OR 高争议 → 进 QUARANTINED，强制等 Curator 审
  4. 高 tier（B/A）升级 → 必须人签
  5. Curator 团队规模：5-10 人足够（不是几千人审核团队）。机器筛 + 人审高价值样本

8.6.7 Adversary Red Team Agent：物理隔离 + 独立 quarantine

红队 Agent 不能跟生产 Agent 串谋（否则就是"自我证明"）。三层隔离：

  • 不共享生产 Agent 的 prompt repo / Memory promote 权限 / 评估口径
  • 不同 LLM endpoint（甚至不同 provider）/ 不同 owner / 不同汇报线
  • 红队产出的攻击样本进独立 quarantine，经人或独立 eval pipeline 验证后才能影响主系统

📺 展开：现状 vs 终态的同一个 case 完整流转对比

场景：一个用户发布疑似营销号的短视频。

现状（今天的流转）

  1. 视频上传 → 机审实时引擎评分（5ms）：规则命中"高营销词" + 模型给营销号概率 0.78
  2. 转人审 → 进入审核队列（积压数小时到次日）
  3. 审核员 Alice 打开 case：
    • ① 看视频本身（30s）
    • ② 切到档案中心查商家近 30 天发布（2 min）
    • ③ 切到关联系统查同设备 / 同 IP 账号（1-2 min）
    • ④ 切到判罚历史查相似商家被处罚记录（1-2 min）
    • ⑤ 翻群历史 / 问 leader 不确定的（5+ min，部分 case）
    • ⑥ 综合判断（1-2 min）
    • ⑦ 写处罚理由 + 操作（1-2 min）
  4. 判罚策略验证 → 执行
  5. 跨域影响没人主动检查
  6. 经验留在 Alice 脑子里。下次类似 case 来如果是 Bob 审，可能判得不一样

总耗时：单 case 8-10 分钟（85% 在拼数据）。

终态（v5 完全 AI Native）

  1. 视频上传 → 机审实时引擎评分（5ms，规则 + 模型不变）→ 转 Agent 调查队列
  2. Kafka emit → Risk Agent Society 自动接管
  3. 多 Agent 并发调查（10-30 秒）：
    • ① 内容安全 Agent：查商家档案 / 30 天发布 / 相似营销号 / 关联账号（并发）
    • ② 跨域协同 Agent：触达未成年用户吗？是否电商业务线？
    • ③ 合规审查 Agent：广告法合规？冷静期？
    • ④ 综合 Agent：输出 Recommendation（证据 + 反例 + 置信 + 引用 Memory）
    • ⑤ 全程进 Trace（经 The Gate）
    • ⑥ 多 Agent 冲突 → 跨域 Arbiter Agent 分析根因
  4. Alice 打开 case：看完整调研材料 1-2 分钟核完
  5. Alice 决策（仍是人最终决定）→ 经 The Gate Action Adapter → 判罚策略 → 执行
  6. 处置结果回填 Memory（采纳 / 改判 / 驳回）+ 失败时进 Failure Taxonomy
  7. 跨域影响自动检查（持续）：同类视频爆发？对抗升级？
  8. 治理层抽审：Trace Auditor 抽 5-10% trace 检查 Agent 偏差
  9. 飞轮转动：本 case 进入 Memory 候选 → QUARANTINED → 经 Curator 升级 → 下次相似 case 自动引用

关键差别：现状 Alice 自己跑全程 85% 时间拼数据。终态 Agent 并发跑全程，Alice 看 AI 整理好的做最终决策。Trace 自动留，Memory 自动沉淀（受状态机约束），跨域自动检查（受 applicability_contract 约束），治理自动抽审。

B反对意见 + 标准回应（决策弹药库）

"快手 R&D 预算百亿级，¥1500 万这点钱不用走那么严的审批吧？"

反驳：

  1. 不是钱的问题，是"项目分类正确性"的问题。¥1500 万走集团战略项目审批 = 浪费高管时间；走部门预算 = 越权
  2. "业务线实验"分类是为了给项目正确的失败容忍度。集团级失败有 PR 风险，业务线实验失败是正常学习
  3. 规模虽小，但牵动 HR / 法务 / 合规 / BPO 多方，仍需 cross-functional 立项 review
"为什么不直接做集团级 AI 风控？分阶段拖延不浪费时间吗？"

反驳：

  1. 集团级直接上 = 风险线性放大。一次失败可能让"AI 风控"在快手内部 3 年不能再提
  2. 业务线实验是"用快手量级真实数据验证可行性"的最快路径。6-12 周的 ROI 比 12-24 个月的大项目高 5-10 倍
  3. 实验通过后再启动 v1（¥几千万-亿级），上限会比直接立项更高
"政治内容不碰，那 AI 风控在快手价值还剩多少？快手最大风险就是政治内容啊。"

反驳：

  1. 政治内容不是快手风控总盘的主要 case 量。电商 + 反欺诈 + 商家风控 + 内容质量加起来占 case 总量的 70-85%
  2. v1 不碰政治 = 实验避开最高风险场景。政治内容审核出错 = 公司级公关 + 监管事故。AI 在这种场景不能轻易碰
  3. "AI 不碰政治内容"反而是项目的优势 framing——证明边界设计稳健，监管反而更容易批
  4. 未来如果业务线实验 + v1 + v2 全跑通后，最早可能也要 2-3 年后才考虑触碰政治内容，且必然是"辅助资深审核员"而非"替代"
"不讲降本怎么给资本市场讲 AI 故事？"

反驳：

  1. 资本市场对 AI 故事的关注点不止"省了多少钱"。"控风险能力提升 + 监管解释 + 海外对抗 TikTok" 这些战略叙事一样有效
  2. v1 阶段就讲降本 = 内部 HR / 工会舆论压力扩大，最终落地难度反而高
  3. v2 阶段（业务扩张吸收完效能后）可以讲"AI 让风控成本曲线变缓"，这跟"裁员降本"完全不同
  4. Steve Jobs / Tim Cook 的 AI 叙事核心也不是降本，是能力跃迁
"AI 出错谁负责？审核员还是研发？还是要 COO 担？"

清晰责任划分：

  1. v1 阶段 Agent 只给建议，人是最终决策 → 决策错责任在人
  2. Agent 给的建议本身不合理 → 责任在 Agent owner（研发 + 算法 + 治理）
  3. 所有动作有 trace，事后能精确追溯
  4. 项目级 sponsor 负责实验整体——但实验是"shadow + 不进生产决策"，出"AI 误判"事故的可能性结构上不存在

核心：v1 阶段 Agent 永远在"辅助 + 闸门"角色，不在"决策者"角色。责任不能转移给 AI。

"大模型幻觉怎么办？AI 给错建议把审核员误导怎么办？"

多层防护：

  1. Prompt 严格要求："所有结论必须有 evidence 列表里的对应项支撑"
  2. 结构化输出 schema 校验：缺 evidence 字段 → 拒收
  3. 强制反例搜索 step：Agent 自己找反例
  4. UI 显示反例点：审核员看到不确定性
  5. 定期 eval：用历史 case 跑回归，监控质量
  6. 事故快速降级：一键关闭 Agent，回归人审

关键基线：今天人审误杀率 ~1-2%，shadow 模式必须证明 AI 辅助后 ≤ baseline 才扩。

"用 Claude 数据出境合规吗？"

必须前置签完合规审批（8 条硬条件第 5 条）。可选路径：

  1. POC 阶段：脱敏后调 Claude（user_id 哈希、PII scrub、敏感字段不出），具体由法务 + 数据安全审批
  2. 稳定后：迁移到公司自部署模型（Qwen / DeepSeek 自部署），数据完全不出域
  3. 监管严格业务线（金融 / 未成年人）：直接用自部署模型，不走外部 API
"实验失败怎么对外解释？快手会被嘲笑吗？"

反驳：

  1. "业务线实验"分类的好处就是失败有 PR 弹性。没承诺过"集团级 AI 战略"
  2. 实验失败仍有 3 个价值产出（见 §7.2）：硬数据报告 + 团队能力 + 合规边界
  3. 事先约定的 Kill Criteria 让"停止"成为成熟决策的体现，不是失败
  4. 对外口径："我们做了一次业务线实验，验证 AI 在我们业务的实际效果，决定基于数据下一步路径"

说明

Round 1 · CTO 7 个反问（终态架构）
Q1. "3-5 年终态"凭什么？真正慢的不是技术，是组织 / 监管 / BPO 合同。
A：接受调整为 5-8 年。技术 2-3 年成熟，瓶颈在组织。修订时间表：v1 6-12 周 → v2 1 年 → v3 2-3 年 → v4 4-5 年 → v5 5-8 年。
Q2. "事件总线 + Agent 群" vs "机审-人审-判罚" 到底是结构性差别还是包装词？
A：4 个可测量的结构性差别：① 决策从串行变并发（单 case 8min → 2-3min）② 反馈从事后报表变实时治理（新对抗 10 天 → 2-3 天）③ 跨域综合从靠人记得变系统支持（跨域事故 月均 3-5 次 → 1-2 次）④ 人的角色从执行者变设计者+终审。
Q3. 一线审核员 1-3 万 → 1-3 千是组织地震，怎么过？
A：实事求是承认。v1 不变 / v2 不变（业务扩张吸收）/ v3 每年 -5-10% 自然流失 / v4-v5 累积到 5-8 千（保守）。BPO 合同从"按 case 数"到"按复杂度"。HR / 工会 day 0 介入。承认终态可能只到 5-8 千，不是 1-3 千。
Q4. Risk Agent Society 多 Agent 冲突谁说了算？
A：三层仲裁。① 优先级矩阵硬规则（合规 > 用户安全 > 反欺诈 > 业务增长）② 跨域 Arbiter Agent 不给结论给"分歧根因"③ 治理终审。URG 是基础：冲突是结论冲突不是数据冲突。
Q5. 规则模型在终态退到哪？AI Agent 边界在哪？
A：按决策速度分层。≤ 100ms：规则 + 模型主导，Agent 不进。1s-60s：模型 + Agent 协作。≥ 60s：Agent 主导。规则模型保留实时层永远，Agent 只在 case 调查 / 跨域 / 治理。
Q6. 治理层 3-5 年后跟得上 AI 决策速度吗？谁治理治理层？
A：人工治理一定跟不上百万级动作。三层治理：① 机器红线层（Policy-as-Code 自动）② 治理 Agent 层（受限 AI 抽审 5-10%）③ 人类治理委员会（T0/T1 + 红线）。谁治理治理层：① 治理 Agent 不能改自身 Policy ② 强制写 trace ③ 季度第三方外审。
Q7. v1 → 终态台阶 v2 / v3 / v4 怎么分？
A：见 Part 8.4 v1-v5 五阶段表格，每阶段含明确触发 / 范围 / 退出标准 / 可回滚 / 组织变革对应。

Round 2 · CTO 8 个反问（数据飞轮 + 自进化）
Q1. 5 个资产层覆盖全了吗？少了什么？
A（CTO 直接指出）：缺最关键的失败原因标签（Failure Taxonomy）。没有它飞轮只堆数据不进化。失败要拆成可训练的根因：证据缺失 / 工具错 / prompt 错 / 模型错 / Memory 污染 / 人审错 / 策略口径变了。升级为 6 个资产层。
Q2. 采纳信号能直接当 ground truth 吗？
A：不能。审核员采纳 ≠ Agent 对，驳回 ≠ Agent 错。人审有误判、赶时间、业务压力、口径漂移。必须分层：实时采纳（仅 eval）→ 申诉结果 3-7 天（弱 GT）→ 二审 1-2 周 → 判罚生效 + outcome 30-60 天（强 GT）→ 长期观察 3-6 月（gold set 最强）。
Q3. Memory 自动升级 tier 的准入门槛太虚。
A：CTO 要求代码级状态机。DRAFT → QUARANTINED → VERIFIED → PROMOTED → DEPRECATED → REVOKED。每状态明确：谁能写 / 谁能读 / 哪些 Agent 可引用 / 过期时间 / 撤回后如何影响历史 trace。
Q4. L2 自动 promote 不能默认开放。
A：必须 6 道 guardrail：① 最小样本量 ② 分桶无回归 ③ 核心红线指标零回退 ④ 冷启动观察期 ⑤ 人工 veto 窗口 ⑥ 自动回滚条件。"统计显著"≠"安全 promote"。
Q5. L4 不应该叫 "v5 后讨论"，应该写成架构红线。
A：CTO 强制：L4 永远关。Agent 永远不能改自身 prompt / tool / policy / eval 集 / Memory 准入规则 / 合并自己的 PR。最多生成 proposal，由人或独立治理系统批准。如果不写死，3 年后一定被"提效"理由突破。
Q6. 跨域知识迁移必须默认禁止，不是默认共享。
A：必须有 domain_scope 和 applicability_contract：适用业务线 / 主体类型 / 证据前提 / 禁用场景 / 迁移审批记录 / holdout 测试。没契约的 memory 跨域不能引用，否则 URG 变跨域污染源。
Q7. Memory Curator 在百万 case/day 下不可能靠人撑。
A：必须分层采样。机器按 4 维评估（风险 / 影响面 / 置信度 / 争议度）→ 低风险 + 高置信 + 低争议自动进 DRAFT；高风险 / 低置信 / 高争议进 QUARANTINED 强制人审；高 tier 必须人签。5-10 人 Curator 团队足够，不是几千人审核团。
Q8. Adversary Red Team Agent 怎么不跟生产 Agent 串谋？
A：三层物理隔离。① 不共享生产 prompt repo / Memory promote 权限 / 评估口径 ② 不同 LLM endpoint / 不同 owner / 不同汇报线 ③ 产出攻击样本进独立 quarantine，经人或独立 eval pipeline 验证后才能影响主系统。否则两个 Agent 互相适配，表面指标好但真实对抗能力不一定提升。

  • 数据飞轮 6 资产层 + 自进化严格 4 层（L4 永远关）
  • 每个失控点（自改 / Memory 污染 / 跨域乱迁移 / Red Team 串谋 / 假阳性 promote）都有工程化防御

终态的可信度不取决于"Agent 写得多聪明"，取决于"The Gate / URG / 治理 / Failure Taxonomy / Memory 状态机 / Red Team 隔离这些控制平面工程化得多扎实"。

说明
文档全篇出现的专业名词集中预解释。任何卡壳的术语都能在这里查到。点开看。
O(...) 表示法 是什么 —— 大 O，描述"成本怎么随规模长"

来自计算机科学，描述规模变大时，成本（或工作量）以什么速度增长。不是精确数学，是数量级的语言。

写法含义风控例子
O(1)不管规模多大成本固定查一个 user_id 几亿用户也是几毫秒
O(n) / O(headcount)规模翻倍成本翻倍（线性）加 10% case 量就要加 10% 审核员
O(场景 × 对抗)两个因素相乘增长新增 1 个业务线要面对所有对抗，新增 1 种对抗所有业务线要应对
O(power-law)幂律分布：少数事件主导且非线性放大1% 最猛攻击造成 80% 损失；一个新 AI 工具流出 → 攻击规模 10 倍化

文档里这么用：

  • "业务扩张 O(场景×对抗)" = 业务越多，对抗越多，两者相乘
  • "风控人力 O(headcount)" = 加 case 必须加人，线性
  • "对抗演化 O(power-law)" = 不是平稳增长，会突然跳起来

三条曲线脱钩的本质：人力线性追不上"相乘 + 突跳"的双重压力。

closed-form vs open-form 推理 是啥

closed-form（封闭式）：问题有清晰边界、有限选项、能写成 if-then 规则或分类标签。

例子：判断一笔订单是不是 ＞ 200 元、用户是不是新注册、设备指纹是不是黑名单——规则和模型擅长。

open-form（开放式）：问题需要跨多个数据源综合、需要推理"如果……那么……"、答案不是预定标签。

例子："这商家是真的售假、还是争议产品、还是被恶意举报？" —— 要看交易、退款、评价、关联账号、物流、相似 case 历史处罚，综合给结论 + 解释为什么。

关键：规则 / 模型物理上做不到 open-form——它们只能做"已知模式过滤"。Agent 第一次让 open-form 推理可批量化（5 分钟一个 case，并行 N 个）。

shadow 模式 / shadow-only 是啥

shadow mode（影子模式）：让新系统跟真实生产并行跑，但**新系统的输出不进入真实决策**，只用来对比 / 评估。

风控里：Agent 对 case 给出"建议处置"，但实际处置仍由人审决定。Agent 的建议只展示给审核员（或仅离线对比），不自动执行。

价值：用真实数据验证 Agent 质量，没有生产风险——即使 Agent 错得离谱也不会真的误杀用户。

v1 实验阶段全程 shadow-only 是 codex（COO 角色）8 条硬条件之一。

automation bias（自动化偏差）是啥

人面对一个"看起来很有道理的自动化建议"时，倾向于少做独立思考、直接采纳——即使建议本身有错。

风控场景：审核员看到 AI 给的"建议封禁 7 天 · 置信度 0.85"，可能不再认真核证据，直接点采纳。结果：AI 错了人也跟着错。

已被研究 5+ 年的真问题（医学影像 AI 是重灾区）。防御机制成熟：

  • UI 不显示数字置信度
  • 强制显示反例点
  • 延迟揭示 AI 建议（审核员先独立判，再看 AI）
  • 双盲 A/B 监控（看 AI 组 vs 不看 AI 组错误率）
  • 审核员 KPI 从"处理量"转"申诉胜诉率"

立项 8 条硬条件第 ④ 条包含 automation bias 验收指标。

BPO 是啥

Business Process Outsourcing，业务流程外包。中文俗称"外包"。

风控语境：第三方外包公司（如某些大型 BPO 厂商）提供大量内容审核员，按 case 数或人天计费。快手一线内容审核员里很大比例是 BPO 而非自有员工。

典型成本结构：BPO 单价 ≈ 自有员工 50-70%，但管理 / 培训 / 质量稳定性比自有差。

baseline 是啥

"基线"——做对比的起点。

风控里：当前人审的误杀率、漏放率、平均处理时间，就是"baseline"。Agent 上线后要证明新指标"≥ baseline"（不能比现在差）。

关键：v1 不要求 AI 比人强多少，只要求"不比人差"。这是 shadow 模式 + Kill Criteria 的底线。

Kill Criteria（实验终止标准）

实验开始前定好"什么数字不达到就立即停"。开始后不许讨价还价、不许"再给我点时间"。

本立项 5 条 Kill Criteria：

  • 判准率 < 70% → 停
  • 单 case 调查时间压缩 < 40% → 停
  • 新异常命中有效率 < 30% → 停
  • 看 AI 组错误率 > 不看 AI 组（automation bias 失控）→ 停
  • 事故率 > baseline → 停

任意 2 条不达标 = 终止实验。¥1500 万止损。

Policy-as-Code 是啥

把"规则 / 权限 / 红线"写成代码或 DSL（领域专用语言），由统一引擎运行时强制。不写在文档、不写在 PPT、不写在某人脑子里。

风控里：例如"实时机审链路禁止调用 LLM"这条红线，不是口头约定，是写成 Rego 或类似 DSL 代码，每次请求自动检查。AI 不能改写，只有治理多签可以发版。

对比传统：业务代码里散落的 if-else 写在每个服务里、容易被绕过。Policy-as-Code 集中、可审计、可版本化。

CoI / ROI 是啥

ROI = Return on Investment，投资回报率。"花了 X 钱，得了 Y 收益"。

CoI = Cost of Inaction，不做的代价。"如果不投这个项目，损失的钱"。

关键区别：ROI 算"做了能赚多少"；CoI 算"不做会亏多少"。立项时 CoI 经常比 ROI 更有说服力——"不做 = 损失 ¥30 亿" 比 "做了 = 赚 ¥10 亿" 更难反驳。

本文档 Part 4 就是 CoI 论证。

A/B 测试 / 双盲 是啥

A/B 测试：把用户（或 case）分两组，一组用新方案（A），一组用旧方案（B），对比效果。

双盲：A 组和 B 组的人不知道自己在哪组，避免心理预期影响行为。

风控里：50% 审核员看 AI 建议（A 组）+ 50% 不看（B 组），对比两组的判罚错误率。如果 A 组错误率 ≥ B 组 = automation bias 失控，停止 AI 展示。

DAU / MAU / GMV / NPS 业务指标

DAU (Daily Active Users) = 日活跃用户数。快手 DAU 4 亿+。

MAU (Monthly Active Users) = 月活跃用户数。快手 MAU 7 亿+。

GMV (Gross Merchandise Value) = 商品交易总额，电商业务核心指标。快手电商 GMV 千亿级。

NPS (Net Promoter Score) = 净推荐值，用户满意度指标。误杀 / 误判会让 NPS 下降，反过来影响 DAU 留存。

Transparency Report（透明度报告）

头部互联网公司定期发布的"我们删了多少内容、为什么删、用 AI 占多少比例"的公开报告。

TikTok、YouTube、Meta、Twitter 都发。TikTok 的 Transparency Report 明确披露：内容审核大量使用 AI 辅助。

本文档引用 TikTok Transparency Report 作为"行业 AI 化已发生"的证据。

RAG / embedding / 向量库 是啥（如果你要细看 Part 3 支柱 2）

RAG = Retrieval-Augmented Generation，先检索再生成。

意思：先从历史 case 库找相似的几个，再让大模型基于这些参考资料给建议。

向量 / embedding：把一段文字变成一串数字（768 维左右），语义相近的数字坐标也相近。这样能"找跟当前 case 行为像的"，而不只是"按 user_id 精确查"。

向量库（Milvus / ES kNN）：专门存这些数字坐标 + 快速找最相似的几个。

详细见配套文档 agent-architecture-design.html。

Part 8 终态架构里的内部术语

下面这些是文档 Part 8 终态架构里反复出现的内部术语，外行第一次见容易卡。

URG (Unified Risk Graph 统一风险图) 是啥

一句话：风控所有事实的统一数据底座。所有人 / Agent / 系统读同一份事实。

不是什么：不是图形界面 / 不是某种数据库技术（不是用 Neo4j 就叫 URG）/ 不是一次性建好的产品。

类比：

现状像散在不同 Word 文档里的数据——档案中心一份、case 一份、判罚一份、策略一份。Alice 调查 case 切 5 个系统拼数据；反欺诈把用户标"高风险"+ 内容安全标同一用户"优质创作者"。

URG 像把所有文档合并到一个 Notion workspace：所有人编辑同一份，互相能看到。

核心实体（MVP 期只 4 个，CTO 警告"不要一上来全做"）：

  • Case（风险事件单元）
  • Action（动作记录）
  • EvidenceRef（证据引用，不复制证据本身）
  • TraceRef（trace 引用，不复制 trace 本身）

User / Content / Device / Memory 由现有系统引用，逐步并入。

物理实现：Kafka 事件总线 + 关系库 + 向量库的组合。事件溯源（append-only）。

关键约束：Agent 永远不直接写 URG，必须经 Action Adapter 过门。所有写入带元数据（谁 / 何时 / 依据什么 / trace_id）。

The Gate（控制平面 / 统一执行护栏）是啥

一句话：所有"写到生产"的动作必须经过的唯一入口，是 AI Native 风控架构的承重墙。

包含 4 个组件：

  • Action Adapter（唯一写动作入口，见下条）
  • Policy-as-Code（红线代码化运行时强制）
  • Trace / Replay / Audit（全链路可追溯）
  • Rollback（git-style 可回滚）

类比：像机场安检——每个想登机（写生产数据）的人必须过同一道门 / 同一套检查。机场可以扩建航站楼（加 Agent），但安检不变。

为什么是承重墙：CTO 强调"架构主体不是 Agent，是 The Gate + URG"。Agent 可以替换 / 扩展 / 下线，The Gate 一旦立住不能动。

v2-v3 期的最大工程：把快手现有所有风控写动作入口（判罚 / 策略 / 运营后台 / 灰度工具 / 工单 / 应急通道）收编到 The Gate 或封禁，否则 The Gate 只是 Agent 的门，不是风控生产动作的唯一门。

Action Adapter（写动作的唯一入口）是啥

一句话：The Gate 里负责"接收写请求 → 查 Policy → 检查幂等 → 执行 → 写 trace"的具体组件。

类比：像银行柜台。任何想从账户取钱（写生产）的人都过同一个柜台。柜员（Adapter）做：

  • 核实身份（鉴权）
  • 查规定（Policy 检查）
  • 查是否重复操作（幂等）
  • 执行 / 拒绝
  • 记账（写 trace）

关键：Agent 不直接调底层服务，调 Action Adapter。Action Adapter 内部分发到 Dubbo / 现有 Java 服务。Agent 只知道"想做什么"，不知道"具体哪个服务实现"。

详细工程实现见配套文档 agent-architecture-design.html §4.2。

Agent Society（多 Agent 协作运行时）是啥

一句话：多个域内 Agent 协同跑的运行时层，跑在 The Gate + URG 之上。

包含哪些 Agent（终态）：

  • 内容安全 Agent 群（视频 / 直播 / 评论 / 用户）
  • 反欺诈 Agent 群
  • 商家 / 电商 Agent 群
  • 合规审查 Agent 群
  • 跨域 Arbiter Agent（仲裁冲突）

关键：Society 这个词刻意选用——多 Agent 不是"线性流水线"，是"协作社会"，有冲突、有仲裁、有专长分工。但仍受控制平面 + 治理层约束。

CTO 强警告：Agent Society 必须最后建（建设优先级第 6 位），不能先于 The Gate。否则做出一堆 Agent 没有控制平面承接 = 愿景项目。

Memory tier (A/B/C/D) Memory 质量分级

一句话：每条 Memory 按"可信度"分 4 级，决定哪些 Agent 能引用、哪些场景能用。

tier来源谁能引用
A 最高事故复盘 / Curator 显式标注 / 监管确认所有 Agent + 高风险决策可引
B 较高判罚生效 + outcome 回填后所有 Agent
C 中人审采纳 + 申诉 / 二审复核通过大多数 Agent
D 最低（DRAFT）Agent 自己写的 / 未验证不进检索，只在 Curator 工作台可见

关键：Agent 写的 memory 永远 tier=D。必须经升级路径（人审 / 判罚 outcome / Curator 签）才能进检索。这是防"Agent 错 → memory → 再被引用"的核心机制。

详细 6 状态机：DRAFT → QUARANTINED → VERIFIED → PROMOTED → DEPRECATED → REVOKED，见 Part 8.6.4。

CDIG (Cross-Domain Influence Graph 跨域影响图) 是啥

一句话：描述"A 域改动会影响 B 域哪些指标"的因果图谱。v4 阶段才用。

例子：

  • "内容安全收紧营销号策略" → "电商商家投放限流" → "GMV 下降"
  • "反欺诈封禁新设备聚集账号" → "新用户激活率下降"
  • "未成年保护扩大识别" → "审核工单激增"

每条边带：方向 / 强度 / 时延 / 是否需要联动。

怎么用：

  • 某个域要改策略时自动检查 CDIG：会影响哪些下游？
  • 跨域 Arbiter Agent 仲裁冲突时参考 CDIG 推因果
  • 事故复盘时反向追溯：这次连锁反应有没有 CDIG 没覆盖的边

v4 才用，原因：CDIG 需要积累足够跨域数据才能建。v1-v3 期没这个数据。

Failure Taxonomy（失败原因结构化标签）是啥

一句话：把 Agent 失败拆成可训练的结构化根因标签。是数据飞轮的关键资产层。

为什么重要：CTO 直接指出——没 Failure Taxonomy，飞轮只会堆数据，不会知道"该改 Agent / 改工具 / 改策略 / 改审核培训"。

失败类型枚举（每次失败强制打标签，进结构化数据库）：

  • EVIDENCE_MISSING 证据缺失（拉不到关键数据）
  • TOOL_ERROR 工具错（调用挂 / 超时 / 返回错）
  • PROMPT_ERROR Prompt 错（指令不明确 / 引导偏差）
  • MODEL_ERROR 模型错（幻觉 / 理解偏差）
  • MEMORY_POISONED Memory 污染（引用了错的）
  • HUMAN_OVERRIDE_WRONG 人审错（审核员判错被申诉推翻）
  • POLICY_DRIFTED 策略口径变了（旧 prompt 跟不上新规）

用途：每月按 Failure Taxonomy 聚合 → 知道下个迭代该改哪里。

applicability_contract（跨域迁移契约）是啥

一句话：每条 Memory 带的"我能在哪些域 / 哪些场景被引用"的显式契约。跨域迁移默认禁止，有契约才允许。

为什么：CTO 警告——"内容营销号模式不能直接迁移到电商商家。反欺诈设备关联不能直接迁移到未成年保护。"没有契约，URG 会变跨域污染源。

契约字段：

  • domain_scope：适用业务线（如 "content-safety:marketing-account"）
  • subject_type：主体类型（video / user / merchant）
  • evidence_prerequisites：依赖的证据前提
  • forbidden_scenarios：禁用场景（如 "minor-user" / "celebrity"）
  • migration_audit：跨域迁移审批记录（谁批 / 何时 / holdout 测试结果）

没契约的 Memory，跨域 Agent 不能引用。

gold set（评估金标集）是啥

一句话：人工精标的"标准答案集"，用来评估 Agent 质量。

构成：

  • 1000-5000 条人工标注的 (case, 正确判罚) 对
  • 每月新增 100-300 条（跟上对抗演化）
  • 按业务线 / 难度 / 对抗类型分桶

怎么用：

  • 每日跑 eval：Agent 在 gold set 上的判准率
  • Prompt / Tool 变更前先在 gold set 跑 A/B
  • 新版本上线门槛：≥ baseline + 无回归

关键约束：gold set 必须由 Curator + 资深审核员维护，Agent 不能写 gold set（否则就是自我证明）。

立项的不是 "AI Native 风控集团战略项目"，是 ¥1500 万 / 6-12 周 / 1 个安全业务线的 shadow 实验。要证明的不是 AI 是趋势，是在快手量级的真实风控线上，AI Agent 能不能变成"可审计、可隔离、可控风险"的能力。跑出来，再谈集团级基础设施。
