1风控场景迁移落地 · 不迁移框架，迁移机制

这一章想干什么
把第 1~3 层的 12 个组件，按"能不能、要不要进快手风控线上链路"重新做一次取舍。结论先说：风控的主战场不是"选哪个 Agent 框架"，而是把状态、记忆、权限、审计、评估 这些机制嵌进 Java 主导的生产链路。框架可以不上，机制必须有。

1.1不迁移框架，迁移机制

姊妹文《Agent 3 层理念架构》把 12 个组件按层位讲透了，但"理解" 不等于"采纳"。风控线有 3 条硬约束让"整框架照搬"几乎不成立：

  • Java 主导：核心交易/审核/判罚链路是 JVM，Python 框架不能进进程内；走 RPC 多 5~20 ms 在毫秒级 SLA 里是灾难。
  • 强审计、强合规：每条决策要可追溯到模型版本 + prompt 版本 + 规则版本 + 人审签名，开源框架的 trace 默认 schema 不够。
  • 反对抗 + 多租户：策略要按业务线/团队级隔离，需要权限/记忆/动作三套 ACL，开源框架默认是单租户思维。

所以这一章的核心姿势是：风控不迁移框架，迁移机制——把 trace/eval、状态图、guardrail、checkpoint、memory event、permission gate、file policy 这 7 个机制吃透，在 Java 这边自己起接口。

1.2二分原则

A vs B 的判定线
A 类（直接套用）：语言无关 + 可内网自部署 + 协议化 的观测/评估 类基础设施。
B 类（仅借鉴机制）：凡是带运行时（Python / Node）+ 强生态绑定的代码框架；以及场景错配（终端 Coding Agent ≠ 线上风控服务）的产品。
原则一句话：凡进入毫秒级判罚链路的，只借鉴机制不引入运行时；凡属于观测评估且可内网自部署的，才允许直接套用。

1.4A 类 · Langfuse 精读（唯一可直接套用）

为什么能用：Langfuse 开源（MIT）+ Docker 自部署 + 兼容 OpenTelemetry + 有 Java SDK，是协议层而非框架层。trace / span / score / dataset / annotation 这套数据模型正好是风控 Agent 最缺的"决策可追溯 + 闭环改进" 底座。能直接用不是因为它懂风控，而是因为它选择不绑死任何业务。

对应风控收益：① 每条判罚动作落 trace + 模型版本 + prompt 版本 + 规则版本，监管举证查询毫秒级。② 差 case 标 annotation + 进 dataset，喂回 prompt 迭代 / 微调数据。③ LLM-as-judge 自动评 + 人工复核 = 数据飞轮的源头。

风险：① Postgres + ClickHouse 后端要扛快手级 QPS，需分片 + 采样策略（典型方案：高风险动作 100% 采样，低风险 1% 采样，仅 trace head 入库）；采样会导致审计缺口，监管样本需要 100% 留存。② 评分体系偏 LLM 质量，风控自定义维度（命中规则 / 模型分 / 人审签名）需扩展 score schema。③ PII / 敏感字段脱敏——trace 直接落 prompt / tool 输入会泄露用户信息，必须 SDK 侧过滤。④ 租户隔离——多业务线共用一套 Langfuse 需 project + ACL 双层隔离。⑤ trace 写入背压不能反压主链路——必须异步 + 本地缓存 + 丢弃熔断。⑥ 自部署运维成本：Postgres + ClickHouse + Redis + Worker 一套要专人维护。

未来限制：① 核心观测能力（trace / score / dataset）可自部署 MIT；企业治理能力（SCIM / audit logging / data retention 等 /ee 模块）可能需商业授权。② OTel 协议演进可能要求 SDK 升级。

外部依据：langfuse.com/docs · langfuse/langfuse

1.5B 类机制可抄清单（8 条）

这 8 个机制是 B 类组件里必须照搬到 Java 风控 的设计，每个都对应一个具体出处：

  1. 文件型 policy 分层（来自 Claude Code CLAUDE.md / Codex CLI AGENTS.md / Anthropic Agent Skills）：风控规则 SOP 用 RISK_AGENT.md 家族管理——平台级 / 业务线级 / 团队级三档，全部进 git、PR review、人是 owner。比塞向量库优越：可读、可评审、可审计、可回滚。
  2. execpolicy / action gate（来自 Codex CLI execpolicy + Starlark DSL）：风控动作（封 / 限 / 解 / 公示）用 OPA Rego 或 Cedar 写策略 DSL——规则即数据，让策略团队不写 Java 也能改。
  3. StateGraph + Checkpointer（来自 LangGraph Pregel 内核）：复杂 case 调查走显式状态图（Java 用 LangGraph4j 或自研最小状态机 ~150 行），每个节点 checkpoint，挂了能从断点恢复。
  4. interrupt / HITL（来自 LangGraph interrupt() + Claude Code permission 4 档）：高风险动作（封禁 / 资金 / 公开声明）必须有 WAITING_HUMAN 状态，不允许 Agent 自动 commit。permission 持久化"这次允许 / 总是允许" 是 The Gate 的标准接口。
  5. memory ADD/UPDATE/DELETE 事件（来自 mem0 + Letta read_only block）：用户画像 / 历史 / 黑名单走事件流而非快照，每个事件可追溯。Letta 的 read_only ACL 直接映射 Memory tier A（Policy 红线不可改）。
  6. ContextVar / ThreadLocal 写入来源隔离（来自 Hermes ContextVar + skill_provenance）：每次写记忆前 set 来源（user / agent / background），auto-promote 只动 agent 自创，永不越权改用户内容。Java 侧用 ThreadLocal<WriteOrigin>。
  7. assertion + eval 数据飞轮（来自 DSPy Assert/Suggest + Langfuse score）：评分 / 分类 / 判罚信号这些 prompt 敏感场景跑 assertion 自动重试 + metric-driven 优化。这是把人工调 prompt 的工作交给优化器 的范式，Agent 主体仍走 State Graph + Spring AI。
  8. budget / timeout / cost ceiling / circuit breaker（来自 Codex CLI 预算配置 + Agents SDK max_turns + 通用 SRE 实践）：每个 Agent 任务必须显式声明 token 上限 / 步数上限 / 时长上限 / 单 case 成本天花板，触顶熔断 → 降级到规则 / 人审。毫秒 SLA 和成本失控 的硬护栏，比 assertion + eval 更靠生产运行层。

1.6不要误用

五条红线
· 不要把 LangGraph 当实时判罚引擎——它是 Python，跨语言 RPC 是毫秒级 SLA 的死刑；它的设计可以抄，库不要进生产链路。
· 不要把 LangChain 当生产治理层——它的本体 是接口胶水（langchain-core + LCEL），不是治理基础设施，frequent breaking change 不适合风控线上依赖。
· 不要把 mem0 / Letta 当权限系统——它们是记忆模型，不是 ACL；高风险数据隔离 / 多租户权限要 The Gate 那一层做。
· 不要把 supervisor / swarm 当多 Agent 组织架构——它们是 LangGraph 之上的多 Agent 模板包，适合 demo 和低风险编排，风控生产 的多 Agent 协作要走自研的 The Gate + URG，不能让模板包替治理边界做决定。
· 不要把 Langfuse 当实时 policy gate / enforcement engine——它的角色是观测 + 评估 + 复盘，不在主判罚链路上。把"这条 trace 得分低" 当作"下条相似请求要拦截" 是错的；enforcement 必须由 OPA / Cedar / 自研规则引擎独立完成。

2LangChain 生态演进 · 从 Chain 胶水到 LangGraph Runtime

这一章想回答的核心问题
LangChain 为什么从最初的"链式调用" 演进到 LangGraph 的"图状态机"？链式不能做循环吗？——能做，但代价是把状态、恢复、人审、trace 责任散落在业务代码里。这一章用 LangChain 官方原话 + 源码 file:line + Pregel 血统 给出硬证据。

2.1仓库地图 + 时间线

LangChain 已经从"一个大包包天下" 演进成多仓库分层组合。当前（2025-Q4 后）的真实结构：

2.2langchain-core / Runnable / LCEL

定位：LCEL（LangChain Expression Language）的价值不是让 Agent 更聪明，而是把 prompt → retriever → model → parser 这类线性胶水 变成可组合 Runnable。

核心抽象：Runnable（基类）/ RunnableSequence（管道）/ RunnableParallel（并行）/ RunnableLambda（包装函数）。| 操作符是纯 Python __or__ dunder，无魔法——langchain-core/runnables/base.py:619-638 直接返回 RunnableSequence(self, coerce_to_runnable(other))。统一拿到 stream / batch / async / fallbacks / retry 这些原生能力。

# LCEL 典型范例
chain = prompt | model | StrOutputParser()
chain.invoke({"question": "..."})
chain.stream({"question": "..."})
chain.batch([{"question": q} for q in qs])

解决的痛点：老 Chain 类（SequentialChain / LLMChain）不是真正可组合——每个 Chain 自带一套 streaming/async/callback 实现，跨 Chain 拼装是噩梦。LCEL 把这件事统一成一个接口 + 五种适配器。

"these chains weren't really composable. Sure - we had SequentialChain, but that wasn't amazingly usable." —— LangChain LCEL 官方博客

2.3LangChain v1：create_agent 跑在 LangGraph 上，classic 被隔离

v1 信号：langchain 1.3+ 主包已被瘦身到只剩 6 个模块，旧的所有重东西（Chain / AgentExecutor / memory / vectorstores）全部隔离到 langchain_classic。新的 create_agent() 底层完全跑在 LangGraph 上——langchain/agents/factory.py 直接 import langgraph 的 StateGraph / ToolNode / Command / Send。

这意味着：Agent 门面留在 LangChain，真正 runtime 下沉到 LangGraph，旧链式资产进 classic。读者再听到"LangChain Agent" 不要联想老 AgentExecutor——它已经只是 LangGraph 的一个 facade。

AgentExecutor 退役原因（官方原话）："We've added a lot of parameters and functionality to AgentExecutor, but it's still just one way of running a loop."（v0.1.0 博客）

2.4LangGraph 内核 · Pregel + StateGraph + Channel + Checkpointer + interrupt

定位：LangGraph 的核心不是画图，而是用 Pregel 式状态传播 把循环、分支、恢复、人审变成可持久化执行。

Pregel 血统（官方亲口承认）："LangGraph is inspired by Pregel and Apache Beam. The public interface draws inspiration from NetworkX."。libs/langgraph/langgraph/pregel/main.py:448 docstring 明确说是 "Pregel Algorithm / Bulk Synchronous Parallel model"，每步分 Plan / Execution / Update 三阶段。

核心抽象：

  • StateGraph：用户描述节点 + 条件边 + 状态 schema
  • Channel：节点间通信通道，常用类型包括 LastValue / Topic / BinaryOperatorAggregate / EphemeralValue / AnyValue（reducer 决定如何合并多入边的写入；另有 DeltaChannel 等 beta 类型）
  • Checkpointer：每次 superstep 后把 state 持久化（SQLite / Postgres / Redis），挂了能从断点恢复
  • interrupt()：在任意节点调用 → 写盘 + 退出 → 外部喂回人审决策 → 继续。在主流 OSS Agent runtime 里少见地同时提供 durable + interruptable + state-editable
  • AgentMiddleware（v1 引入）：官方切面机制，可拦截每次 model call / tool call
# LangGraph 典型范例
graph = StateGraph(State)
graph.add_node("plan", plan_fn)
graph.add_node("act", act_fn)
graph.add_node("review", lambda s: interrupt({"need": "human approval"}))
graph.add_conditional_edges("plan", route_fn, {"safe": "act", "risky": "review"})
graph.add_edge("review", "act")
app = graph.compile(checkpointer=SqliteSaver(...))
app.invoke({"goal": "..."}, config={"thread_id": "case-123"})

2.5LangSmith trace / eval（核心 SDK MIT；server / Platform 闭源）

定位：LangSmith 是 LangChain 生态的商业观测面。SDK（langsmith-sdk）MIT 开源可嵌入任何 Python / TS 应用（甚至非 LangChain）。但 server 端、Platform、Self-hosted 全部闭源付费。

能力：trace（run tree）+ dataset（黄金集）+ evaluation（LLM-as-judge + 人工标注）+ prompt versioning + experiment comparison。

使用边界：可以用 SDK 自己往任意后端（Langfuse / 自建 ClickHouse）转发；但不能假设 LangSmith server 是开源基础设施。风控选 Langfuse，不是 LangSmith——同样的能力 + MIT 全栈 + 内网自部署。

2.6LangServe + supervisor / swarm 的真实状态

LangServe：明确 deprecated（2024-11-18 起，仓库 README 已挂"This repository is no longer actively maintained" 标记）。原作用：把 Runnable 包成 FastAPI 服务并发 OpenAPI。LangChain 官方建议改用 LangGraph Platform（闭源付费）或自己起 FastAPI。

supervisor / swarm：辅助模板包——LangGraph reference 仍把它们列在多 Agent 章节，适合 demo 和低风险编排。两者本质是多 Agent 编排模板包，适合 demo 和低风险场景，风控生产 不应把它当治理边界——治理要走 The Gate + URG，不能让模板包替治理决定。

2.7演进路线硬证据 · 5 段官方原话

这是用户长期困扰的问题："链式调用不能解决循环吗？为什么演进？"——下面 5 段 LangChain 自己的话，给出完整证据链。

① 承认老 Chain 抽象太差（LCEL 博客）
"these chains weren't really composable. Sure - we had SequentialChain, but that wasn't amazingly usable."

—— LangChain LCEL 官方博客。承认第一代 Chain 抽象失败：组合性差、隐藏 prompt、每个 Chain 自带一套 streaming/async。

外部依据：LangChain Expression Language 官方博客

② LCEL 是 DAG 的官方承认（LangGraph 发布博客）
"Effectively, these chains are directed acyclic graphs (DAGs)... we've lacked a method for easily introducing cycles."

—— LangGraph 发布博客（2024-01-17）。这是关键钉子：LCEL 本质是 DAG，设计上就画不出循环。Agent 的本质就是"think → act → observe → think" 的循环，DAG 表达不出来。

外部依据：LangGraph 发布博客

③ AgentExecutor 死结（v0.1.0 博客）
"We've added a lot of parameters and functionality to AgentExecutor, but it's still just one way of running a loop."

—— LangChain v0.1.0 博客（2024-01-08）。AgentExecutor 是把循环写死在框架内，加再多参数都只是一种循环，定制不动，所以 v1 弃用、改成 create_agent 跑在 LangGraph 上。

④ Pregel 血统亲口承认（LangGraph docs）
"LangGraph is inspired by Pregel and Apache Beam. The public interface draws inspiration from NetworkX."

—— LangGraph 官方 runtime docs（"runtime named after Google's Pregel algorithm"）。Pregel 是 Google 2010 年发的图计算论文（同名系统跑全网爬虫图、社交图）；BSP（Bulk Synchronous Parallel） 模型把"循环" 切成多个 superstep，每步可以持久化、可以中断、可以恢复。这正是 Agent 循环需要的——所以 LangGraph 直接把 Pregel 的 superstep 思路拿来做 Agent runtime。

外部依据：LangGraph 官方文档

⑤ Harrison Chase 三周年反省（2025-10-20）
"we traded power for ease of use" ... "the same high-level interfaces ... were now getting in the way when people tried to customize them to go to production."

—— Harrison Chase 三周年总结。这是最重的一段：老 LangChain"用易用性换了表达力"，到了生产场景反而挡路。所以 v1 大幅收缩主包、把 runtime 让给 LangGraph、把旧 Chain 全部归档到 classic。

核心结论（可直接背）
链式不是不能做循环，而是循环一旦进入分支、人审和恢复，就应该升级为状态图。
更具体：老 Chain 解决"串起来"，但抽象太死；LCEL 解决"串得优雅"（统一 Runnable + 原生 stream/batch/async），但设计上就是 DAG，画不出 Agent 循环；AgentExecutor 把循环写死在框架内，"只是一种循环" 定制不动；LangGraph 借鉴 Google Pregel 的 superstep + message-passing，把 Agent 显式建模为带 State 一等公民 + Checkpointer + 条件边 + interrupt 的图状态机，是把"控制流从框架内隐藏" 升级为"用户显式描述"。

2.8Java / Spring AI 替代位 + 风控"用 vs 不用"

LangChain 生态全是 Python（少量 TS），风控线 Java 主导不能进进程内。所以"用 vs 不用" 的判断要按链路 来：

能力LangChain 生态怎么做Java / 风控怎么承接
Runnable / 管道LCEL | 操作符 + RunnableSequenceSpring AI 1.x ChatClient 的 fluent API + 自研 Builder DSL（不要直接引 langchain-core）
Agent runtimeLangGraph StateGraph + Checkpointer + interruptLangGraph4j（JVM 端口，提供 Spring AI integration，可与 Spring AI 并用）或自研最小状态机 ~150 行（v1 case 不复杂时优先）
Retriever / RAGDocument / Retriever / 向量库适配Spring AI VectorStore + DocumentRetriever，背后接公司已有的向量库（Milvus / Tair Vector）
Tool 注册LangChain Tool + LangGraph ToolNodeSpring AI @Tool 注解 或自研 ToolRegistry；动作粒度按 The Gate 的 plugin-package-contract 声明
trace / evalLangSmith（闭源付费）Langfuse（MIT 自部署 + Java SDK）← 这是 A 类直接套
HITLLangGraph interrupt()自研 WAITING_HUMAN 状态 + 工单系统对接（审核员侧入口在 The Gate UI）

一句话原则：用 LangChain 的概念，不用 LangChain 的 Python runtime。把 Runnable / StateGraph / Checkpointer / interrupt / Channel / Reducer 这些词汇 在 Java 这边各起一个类——是最省脑的起点，也是未来与社区对话的最低成本。
