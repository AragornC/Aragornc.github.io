AI Native Risk Control · Engineering Design v3 · 快手语境

Agent 架构设计（快手语境 · 全 Java）

在快手 1500 万 QPS 机审实时引擎旁边建一个独立 Java 服务，业务线实验阶段不触碰实时链路。一种语言、最小新增、严格红线。

面向：风控中台研发 + 业务线 owner · v1 范围 = 1 个业务线 shadow 实验 · 立项论证见 ai-native-risk-case.html

0项目定位

TL;DR
新建 1 个 Java Spring Boot 服务（Agent Service），跑在机审实时引擎的外面，通过 Kafka 异步消费"转人审" case 做调查。v1 业务线实验阶段：1 个业务线 shadow，¥1500 万投入。不动机审 / 不进生产决策 / 不碰政治内容。

0.1快手风控的真实尺寸

0.2核心设计原则（不可妥协）

  1. 实时链路物理隔离。1500 万 QPS 实时引擎跟 Agent 服务永远不调用，三层红线保证（见 §2）
  2. v1 业务线实验范围硬收敛。1 个业务线（电商反欺诈 或 商家风控），shadow 模式
  3. 不碰政治内容 / 价值观定性。边界靠 Policy-as-Code 物理隔离
  4. Agent 作为可问责工作单元，每次动作可回放、可解释、可撤销
  5. 过门即权威。任何写入经 Action Adapter + Policy 检查
  6. Java 主导稳态，Java 跑推理。不引入跨语言负担

2实时链路三层红线

TL;DR
1500 万 QPS 机审实时引擎跟 Agent 服务的隔离，不能靠"口头承诺"。三层红线 = 架构 + 治理 + 责任，靠代码 + Policy + 组织共同保证。
红线 1

架构红线

机审实时引擎跟 Agent 服务物理隔离：不同 K8s namespace、不同网络段。机审代码层 Maven 依赖白名单：禁止引入 Anthropic SDK / 任何 LLM 依赖。CI 自动拒。

红线 2

治理红线

Policy-as-Code 写明"实时链路不允许 LLM 调用"。任何想突破必须治理委员会 + 安全 + 法务多签。默认拒绝 / 白名单审批。

红线 3

责任红线

实时引擎 owner ≠ Agent service owner。KPI 互斥：实时 owner 不为 AI 推动负责。任何"大促能不能 AI 实时拦"请求要走结构化审批，足够慢挡住临时压力。

3.1这次项目要新建什么

就一个：Agent Service（Java Spring Boot）。所有 v1 Agent 跑在同一个服务里，靠不同 Bean / 不同 Kafka consumer / 不同 HTTP endpoint 区分。

v1 不拆微服务的理由：

  • 实验阶段流量小（5-20 万 case/day），单服务集群完全扛住
  • 共享同样的 Agent Loop / Tool Registry / 配置
  • 拆微服务后部署 / 运维成本翻倍，没带来对应价值
  • 未来某个 Agent 量爆了再拆出来不晚

3.2不新增任何基础设施

项目零新增基础设施。Kafka / Redis / MySQL / ES / Dubbo / Apollo / K8s 全部复用你们已有。

唯一可能"新增"的是 Milvus（v2 阶段做 RAG 时考虑），但 v1 用 ES 的 kNN 凑合。

实验 · 必做

4.1 Case 调查 Agent（v1 主力）

机审转人审时自动跑，给审核员产出"已调研" case。

v1 实验范围限定

  • 业务线：电商反欺诈 或 商家风控（二选一，立项时定）
  • case 量：业务线日均 5-20 万
  • 模式：shadow，结果展示给审核员但不影响生产决策
  • 时长：6-12 周

触发方式

机审决策 = "转人审" 时，机审在自己的判罚流程外多发一份 Kafka 消息到 risk.case.investigation.request.{业务线} topic。Agent 服务消费这个 topic，每条消息触发一次调查。不是用户点的。

容量与成本（实验阶段）

日 case 量（业务线实验）5-20 万
每 case 平均耗时15-30 秒
每 case LLM call 数~6-10
每 case 平均 token in / out15k / 2k
每 case 成本（Claude Sonnet 4.5）~$0.06-0.10
日成本（10 万 case 中位估算）~$8000 ≈ ¥6 万
实验期总成本（10 周）~¥400-600 万 LLM API
并发 worker 数~30-80（视业务线 case 速率）
需要的 pod 数~10-20 个

审核员看到什么

审核员打开 case 详情页时，看到一个"AI 调查"模块：

  • 风险方向标签（如"疑似薅羊毛 · 新型租号联动"）
  • 主要证据 5-10 条（来源 + 时间 + 强弱标记，可点开看原始记录）
  • 相似历史 case 3-5 个（含历史处罚结果）
  • 反例点 1-3 条（Agent 自己找的反对证据）
  • 推荐处置（明确标"AI 建议"含置信度，UI 不显示数字置信度防 automation bias）
  • 完整 trace 入口（点开看 Agent 思考过程）

失败行为

Agent 永远不阻塞人审。三种状态：

状态UI 表现
已完成（绝大多数）直接展示
仍在跑"AI 调查中..."占位 + 普通证据，审核员正常审；完成时 SSE 推送更新
失败 / 超时"AI 调查失败"提示，审核员正常审，不阻塞

Java 代码骨架

@Component
public class CaseInvestigationConsumer {

    @Autowired AgentLoop agentLoop;
    @Autowired IdempotencyStore idempotency;
    @Autowired CaseInvestigationRepository repo;
    @Autowired KafkaTemplate<String, ?> kafka;

    @KafkaListener(topics = "risk.case.investigation.request.ecommerce-fraud",
                    concurrency = "30")
    public void consume(CaseInvestigationRequest req) {
        // 1. 幂等 + 业务线 ACL（双重保险）
        if (idempotency.exists(req.getTraceId())) return;
        if (!BUSINESS_LINE_WHITELIST.contains(req.getBusinessLine())) {
            log.error("业务线超出实验范围: {}", req.getBusinessLine());
            return;
        }

        // 2. 跑 Agent loop
        Budget budget = Budget.forCaseInvestigation();
        AgentResult result;
        try {
            result = agentLoop.run(
                AgentConfig.CASE_INVESTIGATOR_V1,
                new AgentInput(req),
                budget
            );
        } catch (Exception e) {
            repo.saveDegraded(req.getTraceId(), e.getMessage());
            return;
        }

        // 3. 持久化 + 广播
        repo.save(toEntity(result));
        kafka.send("risk.case.investigation.result", result.toMessage());
        idempotency.put(req.getTraceId());
    }
}
实验后半段

4.2 人审辅助 Agent

审核员在工作台跟 Agent 聊天，问证据 / 找相似 case / 生成处罚理由。

v1 实验范围

  • 仅同业务线（跟 4.1 同一个业务线）
  • 实验阶段后半段（第 4-6 周）启用
  • 仅核心审核员使用（约 100-500 人），不开放全部审核员

UI 形态

case 详情页右侧 Drawer，可关可开。流式（SSE）。能问：查关联账号、找相似 case、解释命中策略、整理处罚理由。不能：改判罚 / 跨业务线查 / 改 case 结论。

会话状态在哪存

MySQL 两张表：conversation（元数据）+ conversation_message（消息历史）。Agent Service 直接 JDBC 读写。每次用户发消息时 Java 把历史一起传给 LLM。

上下文压缩

Java 里做。当 messages 累积超过 100k token 时，用便宜模型（Claude Haiku）生成 summary 替换早期消息。

v2 演进，本立项不做

4.3 判罚 Review Agent

高影响判罚执行前同步复核。质检员 + 闸门混合，失败默认 escalate 给人。

为什么 v1 不做

  • 需要进入判罚链路（影响生产决策）
  • fail-close 语义需要充分验证后才能上
  • 错误成本远高于 Case 调查 Agent

v2 触发条件

v1 实验成功 + 完整生产 6 个月 + 事故率 ≤ baseline + 治理委员会批准后才考虑引入。

v2 阶段的具体设计（高影响判罚定义、错误码细分、fail-close 实现）不在本文档详述，待 v2 立项时另写。

v2 演进，本立项不做

4.4 策略治理 Agent

运营手动聊天 + 定时巡检。永远不自动改策略。

为什么 v1 不做

  • 策略治理需要广义风控生态（算法 / 策略 / 治理 / 法务）共同认可
  • 40000+ 策略的扫描成本不低，需要先验证基础能力
  • 跟 v1 实验的"控风险 + 监管表率"目标偏离

v2 阶段引入。具体设计待 v2 立项。

530 行 Agent 本质

TL;DR
不用 LangGraph / Spring AI agent 模块。Agent 就是 LLM 调用循环 + 工具执行，30 行 Java 写得完。Claude / Codex / ChatGPT 都不用 framework。
@Service
public class AgentLoop {

    @Autowired AnthropicClient anthropic;
    @Autowired ToolRegistry toolRegistry;
    @Autowired TraceRecorder trace;
    @Autowired PromptManager promptManager;

    public AgentResult run(AgentConfig config, AgentInput input, Budget budget) {
        List<Message> messages = new ArrayList<>();
        messages.add(new UserMessage(input.getUserMessage()));
        String traceId = trace.start(input);

        while (!budget.exhausted()) {
            // 1. 调大模型（带 prompt + tools schema）
            Response resp = anthropic.messages()
                .model(config.getModel())
                .systemPrompt(promptManager.load(config.getPromptName()))
                .messages(messages)
                .tools(toolRegistry.schemasFor(config.getAgentName()))
                .invoke();
            messages.add(resp.toMessage());
            budget.consumeLlm(resp.usage());
            trace.recordLlmCall(traceId, resp);

            // 2. 没工具调用 = 完成
            if (resp.toolCalls().isEmpty()) break;

            // 3. 执行工具（顺序或并发视 config）
            for (ToolCall tc : resp.toolCalls()) {
                trace.recordToolStart(traceId, tc);
                Object result = toolRegistry.invoke(tc.name(), tc.args(), input.getContext());
                trace.recordToolEnd(traceId, tc, result);
                messages.add(new ToolResultMessage(tc.id(), result));
                budget.consumeTool();
            }
        }

        trace.finish(traceId, messages);
        return new AgentResult(messages, traceId);
    }
}
就这。所有 4 类 Agent（v1 + v2）都基于这个核心循环
差别只在：① system prompt 不同 ② 允许的 tool 集合不同 ③ budget / timeout 不同 ④ 触发方式不同（异步 Kafka / 同步 HTTP）。本质代码是同一段。

5.1不用 LangGraph 等 framework 的原因

  • Anthropic 自己反对重 framework（《Building Effective Agents》论文公开）
  • Claude / Codex / ChatGPT 都不用 LangGraph
  • 30 行 Java 等价 LangGraph"高级特性"（条件边、checkpointer、streaming、interrupt）
  • Spring AI 1.0 才 GA，agent 抽象未稳定，直接用 SDK 更可控

6Tool 系统

TL;DR
Tool 用 Spring Bean + 注解定义，一处搞定执行逻辑 + LLM schema + UI 元数据。Spring 启动扫一遍自动注册。加新 tool = 写一个 Java class，走标准 CI/CD。

6.1Tool 定义：一个 Java class 搞定一切

@AgentTool(
    name = "query_user_archive",
    displayName = "查询用户档案",
    description = "查询用户的关联账号、设备、行为路径",
    tier = ToolTier.READ_ONLY,
    icon = "user-search",
    resultRenderer = "user_archive_card",
    allowedAgents = {
        AgentConfig.CASE_INVESTIGATOR_V1,
        AgentConfig.HUMAN_REVIEW_ASSIST_V1
    },
    // v1 业务线 ACL：只允许这些业务线调
    allowedBusinessLines = {"ecommerce-fraud"}
)
@Component
public class QueryUserArchiveTool {

    @Autowired ArchiveService archiveService;   // 你现有的 Dubbo service

    @ToolMethod
    public ArchiveResult invoke(
        @ToolParam(name="user_id", label="用户 ID") String userId,
        @ToolParam(name="scope", label="查询范围",
                    enums={"basic","relations","behavior"}) String scope
    ) {
        return archiveService.query(userId, scope);
    }
}

一个 Java class 同时承载：执行逻辑 + LLM schema + UI 元数据 + 权限分级 + 业务线 ACL + Dubbo 服务调用。

6.2Tool 三级权限

Tier范围调用方式
T1 只读查档案 / 查策略 / 查相似 case / 查判罚历史 / 命中详情v1 实验阶段主要用 T1
T2 受限可逆写建 case / 改 case 优先级 / 路由人审 / 写 memory draftv1 实验阶段不开 T2 写权限
T3 高影响执行判罚 / 改名单 / 改策略永远不让 Agent 调（v2/v3 也不开放）

6.3UI Catalog

前端启动时调 /api/tools/catalog 拿到完整 UI 元数据。Spring 扫所有 @AgentTool bean 自动暴露。函数调用 SSE 事件时按 tool name 查 catalog 渲染。

6.4加一个新 Tool 的流程

业务方提需求
研发确认现有 Java 服务有对应方法
写一个新 Java class 加 @AgentTool 注解
提 PR + review + 合并
Maven build + Docker 镜像 + K8s 灰度发布
Spring 扫到新 tool 自动注册，前端 catalog 自动看到

加新 tool 没有 Python / 没有跨服务发布。走你们现有 CI/CD。

7.2上下文压缩（Java 里做）

private List<Message> compressIfNeeded(List<Message> messages) {
    int tokens = TokenEstimator.estimate(messages);
    if (tokens < 100_000) return messages;

    List<Message> recent = lastN(messages, 10);
    List<Message> older = exceptLastN(messages, 10);

    // 用便宜模型压缩
    String summary = anthropic.messages()
        .model("claude-haiku-3-5")
        .systemPrompt("用 2000 字以内概括对话，保留所有 case_id / strategy_id / 数值结论")
        .userMessage(formatMessages(older))
        .invoke().text();

    List<Message> compressed = new ArrayList<>();
    compressed.add(new SystemMessage("[早期对话摘要]\n" + summary));
    compressed.addAll(recent);
    return compressed;
}

7.3Memory（跨对话知识）

Memory 类型存哪v1 实验阶段
对抗模式 / 历史 case 经验MySQL memory_item + ES 索引（v1 不上 Milvus）仅实验业务线相关
用户档案你现有档案中心（不动）只读引用
策略文档你现有策略库 / Git + ES只读引用

实验阶段 RAG 检索用 ES BM25 + 简单 vector（ES kNN）。如果实验成功且数据量增长到千万级，v2 阶段评估引入 Milvus。

7.4防 Memory 污染

三道防线
① Agent 写的 memory 永远 tier=D, status=DRAFT, human_verified=false
② Retrieval 默认 filter tier ≥ C AND human_verified=true（DRAFT 不进检索）
③ 升级路径：DRAFT → HUMAN_REVIEW (tier C) → PRODUCTION (tier B) → CANONICAL (tier A)

8技术栈逐个解释

TL;DR
项目 95% 是你们已有的技术栈。唯一可能新增的是 Milvus（v2 才考虑）。每一项都有解释 + 不用行不行。

8.1已有的（直接复用，零新增）

Spring Boot — Java 项目脚手架

HTTP server、依赖注入、配置管理、健康检查这些基础能力。Agent Service 用 Spring Boot 3 + Reactor。你们后端都是 Spring Boot，零学习成本。

Kafka — 排队和广播

分布式消息队列。机审产生"转人审" case → 扔 Kafka topic risk.case.investigation.request → Agent 服务从队列拉。关键：Kafka 是机审跟 Agent 之间唯一的通信通道，单向流动。机审从不读 Agent 输出。

Redis — 内存缓存 + 临时记忆

① 缓存（用户档案、相似 case 短时缓存）② 幂等键（防 Agent 重复处理）③ 限流计数 ④ 分布式锁（同一 case 同时只允许一个 worker 跑）

MySQL — 关系型业务数据

case_investigation / conversation / conversation_message / tool_registry / memory_item 等表。

Elasticsearch — 全文搜索 + Trace 热查询

Trace 热查询（30 天内）+ memory 文本检索 + ES kNN（v1 简单向量检索，替代 Milvus）。

Dubbo — Java 服务 RPC

Agent 调你们现有的策略库 / 档案中心 / 案例库 / 判罚历史走 Dubbo。复用 Spring + Dubbo 集成。

Apollo / Nacos — 配置中心

存 prompt 模板版本、Agent 配置、tool registry 配置。改完热 reload，无需重启。

8.2可能新增（按需）

Anthropic Java SDK — 调 Claude

v1 实验阶段必需（除非用国产模型，那就改用对应 SDK）。1 行 Maven 依赖。封装 HTTP 请求 / 签名 / 重试 / 流式响应 / function calling 协议。

Milvus — 向量数据库（v2 才考虑）

v1 不上。用 ES kNN 凑合。v2 阶段如果 memory 数据涨到千万级再评估引入。

Embedding 模型 — 把文字变成向量

v1 阶段：用 ES 内置 embedding 或 Claude/OpenAI 的 embedding API。v2 阶段考虑自部署 BGE-M3。

TL;DR

9.2变更类型与发布流程

变更怎么改发布
加新 tool写 Java classPR → CI/CD → 灰度
改 promptApollo 改配置热 reload，秒级

改 Policy（红线）Apollo / 代码多签后发布

9.3实验阶段灰度

三层灰度：

  1. 业务线灰度：仅 1 个业务线（电商反欺诈或商家风控）开启
  2. 审核员灰度：50% 审核员看 AI 建议 / 50% 不看（双盲 A/B）
  3. Case 比例：实验早期可只跑 10-20% case（观察成本和质量）

9.4监控告警

Prometheus + Grafana，跟你们现有体系一样。核心指标：

agent.latency.p50/p95/p99各 Agent 延迟
agent.llm.cost.usd（实时）关注成本，>阈值自动暂停 + 钉钉告警
agent.error.rate>5% / 5min → P2
agent.fail.reason{type}失败原因分布
kill_criteria.* 实时跟踪判准率 / 调查时间 / automation bias 指标

11明确不用 / v2+ 才考虑的

不用什么时候才考虑
LangGraph / LangChain4j当你有 50+ 不同 Agent 配置且需要复用状态机抽象。v1/v2 都不需要
Spring AI agent 模块Spring AI 1.5+ 稳定后可评估，预计 2026 年
Temporal 工作流当 Agent 跑变成"小时级长任务"或"多步骤跨天"时
独立 LLM Gateway当 Agent 数 ≥ 10 且需要跨 Agent 限流 / 计费时
独立 Action Adapter 服务当跨服务复用 tool 调用、需要统一审计 / 鉴权时
Python / 跨语言当 Java 生态无法解决的 LLM 工程问题时（目前没有）
Milvus 向量库case memory 数据量超 1000 万条时
判罚 Review Agentv1 实验成功 + 6 个月生产稳定 + 事故率 ≤ baseline 后
策略治理 Agentv2 阶段，独立立项
多业务线扩展v1 实验跑通 + 业务线 owner 同意 + 治理委员会批准
判罚链路接入v2，需要重新过 fail-close 设计 + 多签
政治内容审核永远不（除非 v3+ 极远期才可能讨论，且必须是辅助资深审核员，非替代）
实时链路接入永远不（架构红线）
v1 设计哲学
每一个"不用"都不是"永远不要"（除了政治内容 + 实时链路），而是"v1 实验不必要，等具体痛点 / 触发条件出现再加"。这样既保证 v1 能快速跑起来，也不堵死未来演进。
红线 · v1 实验阶段 Agent 只给建议、不做决策。判罚执行 / 改名单 / 改策略永远不让 Agent 自动做。实时链路物理隔离不可移除。所有动作可追溯、可解释、可降级回归人审。
