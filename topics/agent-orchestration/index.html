AI Agent Orchestration：结构化时间线

这份文档追问一个问题：为什么今天会出现 agent、workflow、orchestration、 harness、MCP、A2A、Agents SDK 这些东西？它们不是同一层概念，也不是一夜之间出现的。

贯穿场景

想象一个企业知识工作系统：它要读懂公司年报、公告、代码仓库、表格和内部文档， 能按用户指令生成可靠答案，必要时检索资料、调用工具、计算指标、核对引用、修复脚本， 并把结果交给另一个 agent 或业务系统继续处理。下面 8 个阶段不是在讲 8 个互不相干的产品， 而是在追问同一个场景逐层需要什么能力：先有语言建模底座，再有 prompt 任务接口、 助手对齐、推理与工具原语、workflow / agent loop、状态化编排、coding harness， 最后走向 MCP、A2A 和 Agent SDK 这样的协议与开发者原语。

Stage 01

Transformer 与预训练语言模型

2017-2019 · 语言建模底座时代

先解决语言建模底座，还没有 agent 能力。

起点瓶颈
论述

2017 年以前，处理文本序列的主流路线长期依赖 及其改进模型，例如 。 LSTM 缓解了早期 RNN 的 问题，但它仍然属于循环序列模型：信息需要沿时间步一格一格传递， 训练也难以像后来的 那样在序列维度充分并行。真正的起点瓶颈是： 这条路线在 和 上仍然受结构限制。

例子
任务 客户问：“Acme 2023 年研发投入暴涨 32%，钱花到哪个业务上去了？”
原文 “Acme Corporation, which after divesting its legacy printer division in 2022 has refocused around AI infrastructure, increased R&D spending 32% in 2023 because it accelerated GPU cluster procurement and chip design hiring.”
关系 模型必须知道 `it` 指的是句首的 Acme，而不是最近的 `AI infrastructure`；还要把 `GPU cluster procurement / chip design hiring` 和 `refocused around AI infrastructure` 连起来。
错法 如果模型抓不住远距离关系，可能写成“研发增长来自打印业务扩张”，但原文说打印业务已经在 2022 年剥离；也可能把 `it` 错绑到 `AI infrastructure`，导致因果主体混乱。
对应瓶颈 在 RNN/LSTM 中，`Acme` 的信息要沿很多 token 一步步传到 `it`，中间还夹着剥离打印业务、转向 AI 基础设施等干扰信息；文本越长，远处主语和因果关系越容易在传递中变弱。

突破与产出
论述

关键机制变化是：把 放到序列建模的中心。每个 不再只能沿着 RNN/LSTM 的时间步一格一格传递信息，而是可以在同一层里直接和其他位置计算相关性。 这就是 的核心取舍：牺牲一部分按时间递推的直觉，换来更短的信息路径和更好的序列维度并行。

之后的关键决策不是马上出现 agent，而是先把 Transformer 变成可复用的语言底座： 走 路线，强调双向语言理解； 走 路线，强调自回归生成。二者共同把 变成主流范式：先在大规模文本中学习通用语言能力，再通过 或提示适配具体任务。

例子
同一任务 客户问：“Acme 2023 年研发投入为什么上升？”模型仍然只拿到一段英文年报摘要，没有工具、没有检索、也不会自己打开财报。
这次变化 在 “Acme ... increased R&D because it accelerated GPU cluster procurement” 这类句子里，self-attention 允许 “it” 直接和 “Acme” 计算关系，也允许 “increased R&D” 直接关注后面的 “GPU cluster procurement”。
解锁能力 所以它更容易判断：研发投入上升不是因为已剥离的打印机业务，而是因为 AI 基础设施扩张；也更容易把这段英文翻译、分类、抽取成一句中文结论。
边界 但它还只是“读懂给到它的文本”。如果任务变成“去找 Acme 三年年报、抽表、核算趋势、写带引用的备忘录”，这还不是当前阶段的模型能力。
证据

产品落地 Google 2019 年把 BERT 用到 Search 的 ranking 和 featured snippets，官方称它会帮助 Search 更好理解美国英语里约 10% 的搜索。

仍未解决

这时还没有今天 LLM agent 的能力。模型主要是语言理解/生成底座，不会稳定遵循自然语言任务， 不会读外部文件，不会调用工具，也不会自己规划行动。

易错点

不要把架构说成 agent： Transformer 是模型架构，不是 agent 架构；BERT/GPT-2 也不是“会执行任务的助手”。

过渡：Transformer 证明“注意力架构 + 预训练”是一条可扩展路线，但应用一个新任务仍常常需要微调或专门设计。 下一步的关键决策是扩大规模，并让 prompt 本身成为任务接口。
Stage 02

规模化、Foundation Model 与 In-context Learning

2020-2022 上 · 规模化底座时代

prompt 从“文本开头”变成任务接口。

起点瓶颈
论述

阶段一让语言能力底座变得可扩展，但使用接口仍停留在“为每个任务单独适配”的阶段。当时常见路线是 加 ： 每加一个新任务，就要重走“收集 -> -> 评估 -> 部署”一遍。这条路线的结构性瓶颈不是模型不会处理文本，而是 太重：每多一个任务，就多一份数据、一条训练流水线、一个分叉的 副本和一个独立部署。问题因此被推到更抽象的位置：能不能让同一份训练好的权重，仅靠输入来切换任务，而不再训练？

例子
任务分析师面对同一份 Acme 年报，要同时完成三件事：把“风险因素”段落改写成客户能读的一句话摘要；把每条风险归到市场、监管、供应链、汇率等类别；根据财务表回答具体数字问题。
旧做法三个需求等于三套 fine-tuning：分别收集摘要样本、分类标签、问答对；分别训练、上线、评估。如果客户下周又加一种需求，这条链条还要重来。
关键问题同一个底座能否只换输入完成这些任务？这才是这一阶段的核心问题，不是“模型够不够大”。
证据
路线成本BERT 在 GLUE 上达到 80.5，是在 GLUE 9 个子任务上各自 fine-tuning 得到的结果。这个成功也暴露了旧路线的成本：同一个预训练底座之外，还要为下游任务保留各自的微调流程和权重副本。
问题起点GPT-3 论文开头把当时主流路径概括为：先做大规模无监督预训练，再在下游任务上 fine-tune；论文正是从“能否减少对任务数据和任务微调的依赖”这个问题出发。
要证明的瓶颈瓶颈不是“微调没用”，而是“每个任务都要独立适配”。对企业应用来说，这意味着数据、训练、评估和部署成本随任务数增长。
突破与产出
论述

关键变化不是出现 agent，而是 与 共同改变了模型使用方式：模型能力来自大规模预训练，任务适配则更多发生在推理时的 上下文里。这里的“学习”不是训练时学习，不会改权重；它更像是模型根据上下文里的说明、示例和格式约束，临时条件化自己的输出。

例子
这次变化prompt 里放三条样例：“原文片段 -> 客户能看懂的一句话风险摘要”，再放 Acme 新片段。模型不需要微调，就能尝试模仿这个映射。
解锁能力同一个模型可以用不同 prompt 临时切换任务：风险摘要、财务问答、标题生成、分类、翻译，都可以先用上下文试出来。
边界这仍然不是工具能力。Acme 的完整年报如果没有放进上下文，模型看不到；如果上下文太长放不下，它也不会自己去检索。
证据
上下文适配GPT-3 论文报告，在 上，GPT-3 175B 为 64.3%、 为 68.0%、 为 71.2%。同一模型随 prompt 示例增加而改善，说明 prompt 已经成为任务接口的一部分。
底座迁移2021 年 OpenAI Codex 把 GPT 路线迁移到代码生成；GitHub Copilot 官方发布时说明它由 OpenAI Codex 驱动。这里的 Codex 是代码模型，不是后来的 coding agent。
概念锚点Stanford 2021 报告提出 ：一次大规模训练出的模型，可以适配大量下游任务。这个概念把“一个底座，多种任务”的变化说清楚了。
产物
API/模型 API：把大模型能力作为服务接口交给开发者，prompt 成为主要使用方式。
代码模型：把自然语言和代码生成连接起来，是 Copilot 的底层模型路线之一。
产品GitHub Copilot：面向开发者的代码补全/建议产品，不是自治 agent，而是 IDE 内的模型能力入口。
仍未解决

模型仍更像“补全引擎”。它只能处理 prompt 里放得下的内容，不能访问最新年报或私有资料，也不保证按用户真实意图安全、有用地回答。

易错点

不要把上下文学习说成工具能力：in-context learning 是用输入引导模型，不等于模型有外部记忆、文件访问或行动能力。

过渡：规模化模型让 prompt 变强，但用户真正想要的是“听得懂要求、按要求完成任务”的助手，而不是只会续写文本的模型。下一步的关键决策是 instruction alignment。
Stage 03

Instruction Alignment 与产品化助手

2022 中-2023 上 · 助手对齐时代

模型开始更像“听指令的助手”。

起点瓶颈
论述

阶段二让 成为任务接口，但预训练语言模型的核心训练目标仍是 ：根据上下文做 。这个目标能训练出强大的语言续写能力，却不等于模型会稳定遵循 。当用户开始用自然语言提出任务时，真正暴露的瓶颈变成 ：模型生成“像答案的文本”，和输出 的助手回复，不是同一件事。

例子
任务用户把 Acme 年报片段贴给模型，并说：“请给客户写一段风险备忘录。只使用我给的材料；每个判断都附原文依据；如果证据不足，直接说证据不足；语气要给非技术客户也能读懂。”
问题纯续写型模型可能会写出一段很像咨询备忘录的文本，但它优化的是“下一段最像什么”，不是“是否严格遵守每条要求”。它可能补一个看似合理但材料里没有的风险，可能不给出处，也可能把“证据不足”写成确定结论。
瓶颈所以这里缺的不是更会写，而是让模型把“用户给出的约束”当成行为目标：要有用、诚实、按要求做，并在不能做时明确边界。
证据
目标错配 论文把问题明确表述为：语言模型目标和“遵循用户意图”并不一致；论文因此引入对齐方法，在突破侧详述。
真实偏差 用 817 个容易诱发错误信念的问题测试模型；论文报告，较大的 GPT-3 模型在真实性上反而低于较小模型，说明“规模更大”不会自动等于“更诚实地回答用户”。
人类基线差距TruthfulQA 论文报告，表现最好的 GPT-3-175B helpful prompt 在生成任务上 58% truthful、21% truthful and informative；人类基线为 94% truthful、87% truthful and informative。这个差距直接证明“像人类文本”仍远未等于“真实且有用地回答”。
突破与产出
论述

关键变化是 ：后训练阶段不再只让模型预测下一个 token，而是把“人类希望怎样回答”显式放进训练。 用人工写好的指令-答案样本教模型基本助手格式； 从人类偏好比较里学习“哪个回答更好”； 再用这个奖励信号优化模型输出。Anthropic 的 则把一组原则引入自我批判和改写过程，减少对逐条人工反馈的依赖。这里形成的是 ，还不是 agent loop。

例子
这次变化同样是 Acme 风险备忘录，对齐后的助手更可能先确认材料范围，再按“结论、依据、风险、缺口”组织输出；当材料里没有引用时，它更应该说“当前片段不足以支持这个判断”，而不是补一个漂亮但不存在的出处。
解锁能力用户不再需要把任务伪装成续写题，也不必写一堆 示例来暗示格式。自然语言指令本身开始成为可靠交互方式，模型行为更接近“按要求协作”。
边界它仍然只处理已经给到上下文里的材料。没有外部文件访问、检索、计算器或执行环境时，它不会自己打开年报、核对引用、重试失败步骤。
证据
偏好提升Ouyang et al. 2022 的人类偏好评估报告：在论文测试分布上，1.3B 输出被偏好于 175B GPT-3。这里证明的是“对齐训练改变人类偏好质量”，不是“模型一定更事实正确”。
训练路径 论文给出 SFT、reward model、RLHF 的三步后训练流程；这说明突破来自训练目标和反馈机制变化，而不是 ChatGPT 这个产品名字本身。
安全权衡Constitutional AI 论文展示了用原则驱动自我批判、改写和 AI feedback 的路径，目标是在 helpfulness 与 harmlessness 之间改善权衡。
产品门槛OpenAI 于 2022-11-30 发布 ；Anthropic 于 2023-03-14 发布 ；OpenAI 于 2023-03-14 发布 。这说明“助手式交互”从研究训练方法进入大众产品入口。
产物
训练方法SFT + RLHF：把人工示范、人类偏好和强化学习组合成 instruction-following 的后训练路线；代表产物是 和 ChatGPT 背后的对齐训练。
训练方法Constitutional AI：用原则驱动模型自我批判、修正和 AI feedback；代表 Anthropic 的对齐研究路线。
产品入口ChatGPT：产品化对话接口，不是底层架构名；它是模型、对齐、服务、UI、安全策略的组合。
产品入口Claude：Anthropic 的助手产品入口，强调有用、诚实、无害和可控的交互体验。
模型GPT-4：OpenAI 2023 年发布的多模态大模型，通过 ChatGPT Plus 和 API 提供；它是模型，不是 agent 编排框架。
仍未解决

它仍主要是在“回答”。没有天然读文件能力，没有外部工具权限，没有可靠长流程状态，也不能在执行失败后自动重试。

易错点

不要把 ChatGPT 当成架构：ChatGPT 是产品入口；它背后包含模型、对齐、服务、UI 和安全策略。

过渡：助手会听指令以后，用户开始提出更复杂的问题：先找证据、再计算、再写结论、再检查引用。下一步的关键决策是加入推理原语和行动原语。
Stage 04

推理原语与行动原语

2022 末-2023 上 · 推理行动原语时代

从“直接回答”走向“分步骤 + 请求工具”。

起点瓶颈
论述

阶段三让模型更像助手，但真实任务往往不是单问单答。它同时需要 和触达模型权重之外的 。如果系统只要求模型直接吐出最终答案，推理上的 不可检查，行动上的 也没有接口。瓶颈从“愿不愿意按要求回答”推进到“能不能把思考过程拆开，并把外部动作表达成可执行请求”。

例子
任务用户问：“请基于 Acme 年报，找出 2021-2023 年研发投入，计算 ，并解释研发投入变化是否带来经营风险。”这不是一句摘要题，而是查数、算数、解释、引用四件事连在一起。
问题如果模型只能直接回答，它可能写出“研发投入持续增长，风险可控”这种顺滑结论，却没有列出三年数字、没有展示公式、没有说明风险来自哪一段材料，也无法请求计算器核算。
瓶颈这里缺的不是更漂亮的表达，而是把任务拆成可检查步骤，并把“查表、计算、检索、读取文件”这类动作变成系统能执行的接口。
证据
推理被压扁 论文中的基线能证明瓶颈本身：PaLM 540B 在 上使用 standard prompting 只有 17.9%。这说明强模型直接给最终答案时，多步数学推理仍明显不足。
行动缺位Toolformer 论文把问题表述为：语言模型可以背很多知识，却仍会在精确计算、事实查询、翻译等场景受限；它研究的正是模型何时应该调用 API。OpenAI 后续发布 Function Calling，也说明工程上需要把外部动作变成结构化接口。
突破与产出
论述

这一阶段出现两类积木。 让模型把问题分成中间步骤，例如 和 ； 让模型用结构化格式请求外部函数、检索、计算器或 API，例如 、 和 。但这还不是 agent：它只提供“推理步骤”和“动作接口”，没有自动管理完整任务流程。

例子
这次变化模型不再直接写结论，而是先展开：“1. 找 2021-2023 R&D expense；2. 记录出处；3. 调用计算函数算 CAGR；4. 对照风险因素章节；5. 最后写客户备忘录。”
工具接口如果系统提供函数，模型可以输出 形式的请求，例如 `{"name":"calculate_cagr","arguments":{"values":[120,150,210]}}`。真正执行函数的是外层系统，不是模型文本本身。
边界模型能提出下一步和工具请求，但谁来管理多次调用、失败重试、权限、停止条件，还没有被这个阶段统一解决。
证据
推理原语在同一 PaLM 540B 和 GSM8K 任务上，standard prompting 是 17.9%，Chain-of-Thought prompting 提升到 56.9%；Self-Consistency 在 GSM8K 上进一步报告 74.4%。这说明“显式中间步骤”和“多路径投票”带来可测量增益。
行动原语OpenAI 2023-06-13 发布 Function Calling，让模型返回包含函数名和参数的结构化调用请求；Toolformer 论文则从研究侧探索语言模型学习调用 API 的机制。
产品化入口OpenAI 2023-03-23 发布 ChatGPT Plugins，把 ChatGPT 接入浏览器、代码解释器和第三方服务；这标志着“对话助手调用外部能力”进入产品形态。
产物
类型名称一句话说明具体应用来源
推理技巧Chain-of-Thought让模型显式写出中间推理步骤。数学题、常识推理、分步分析。
推理技巧Self-Consistency采样多条推理路径，再用投票得到答案。降低单条推理链偶然错误。
产品功能ChatGPT Plugins把对话助手接入外部服务。浏览网页、调用 Wolfram、连接 Expedia/Zapier 等服务。
APIOpenAI Function Calling让模型输出函数名和参数。开发者执行搜索、计算、数据库查询、业务 API。
研究方向Toolformer研究模型如何学习何时调用 API。计算器、检索、翻译等外部工具调用学习。
仍未解决

推理原语和工具调用只是积木。它们不能自动组织完整任务，也没有天然状态、重试、分支、权限、停止条件和错误恢复。

易错点

Function calling 不是 agent：它只是让模型能请求外部函数；是否形成 agent，取决于外层是否有观察、决策、执行和反馈循环。

过渡：一旦有了“会想步骤”和“能叫工具”的积木，工程问题就变成：谁来组织多次模型调用、多次工具调用、检索、状态和错误处理？这就是 LLM 语境下 orchestration 进入主舞台的原因。
Stage 05

第一代 Orchestration：静态 Workflow 与动态 Agent Loop

2022-2023 · 第一代编排(Orchestration)时代

代码控制流程，与模型动态决策开始分叉。

起点瓶颈
论述

阶段四让模型有了推理与行动积木，但单次调用仍无法承担一个完整任务。真实应用需要把多次模型调用、多次工具调用、外部检索、中间状态、错误处理组织起来。瓶颈从“积木有没有”变成“谁来组织积木”：、、、、 这些工程问题，在一个 prompt 里没有稳定位置。

例子
任务Acme 完整年报在 PDF 里，用户要求：“给出 2021-2023 年研发投入趋势，解释相关风险，并且每个数字和风险判断都附原文引用。”
单次调用问题即使模型会写步骤、会提出工具请求，一次调用也无法稳定完成整条链路：先要读取 PDF，再切分页面，再检索相关段落，再抽取表格数字，再计算趋势，再验证引用，最后生成备忘录。任何一步失败，后续结论都可能建立在错误上。
瓶颈缺的是流程层：它要记录已经找到哪些证据、调用过哪些工具、哪一步失败、是否需要换策略，以及什么时候可以停止。
证据
外部知识瓶颈RAG 论文把知识密集型任务的基线问题说得很直观：closed-book 生成模型只依赖参数记忆；论文列出的 T5-11B closed-book Natural Questions 结果为 34.5 EM，说明“只靠模型记忆回答外部知识”存在上限。
流程组织瓶颈、 和 都把复杂任务拆成多个 prompt 或子任务来研究；这说明问题已经从单次生成扩展到“多步 LLM 应用如何组合、检查和调试”。
突破与产出
论述

这里出现两条分叉。 是代码决定下一步，例如“切文档 -> 检索 -> 摘要 -> 校验引用”； 是模型读取 后决定下一步。 开始成为组织模型、prompt、工具、检索、状态和控制流的工程层。

这里几个常被混用的词其实在不同层： 是“接入外部知识”的模式； 是“把多次 LLM 调用串成预设步骤”的方法； 是“把模型、检索、工具、memory 组合起来”的工程框架； 是“模型根据 observation 动态决定下一步”的 agent loop 方法。

RAG 和 prompt chaining 通常落在静态 workflow 一侧，ReAct 是动态 agent loop 的代表，LangChain 则是承载这些模式的工程层。

例子
静态 workflow上传 PDF -> 切块并生成 -> 存入 -> 检索研发投入和风险因素 -> 抽取数字 -> 计算趋势 -> 生成备忘录 -> 检查引用。这里下一步由代码写死。
动态 agent loop如果 `R&D expense` 找不到，模型根据 observation 改搜 `research and development costs`、`technology investment` 或表格脚注；如果表格解析失败，它可以选择换 OCR、换页码或向用户追问。这里下一步由模型根据观察决定。
区别workflow 强在可控和可复现；agent loop 强在遇到未预设状态时能换策略。但早期 agent loop 往往成本高、脆弱、难评估。
证据
静态 workflowRAG-Sequence 在 Natural Questions 上报告 44.5 EM，高于同论文列出的 T5-11B closed-book 34.5 EM；这说明“检索外部文档 -> 再生成答案”的组织方式能缓解参数记忆不足。
任务拆解PromptChainer 提供可视化 prompt chain 调试；Decomposed Prompting 用多个子问题/子程序处理复杂任务。这些工作支撑静态 workflow 的工程化路线。
动态循环ReAct 把 reasoning、action、observation 放在同一个循环；论文报告在 ALFWorld 和 WebShop 上相对 imitation learning / reinforcement learning 方法分别提升 34 和 10 个绝对百分点。
框架化LangChain 文档把它定位为构建 LLM 应用和 agents 的框架，用来组合模型、检索、工具、memory 等部件；它不是模型，也不是 agent 本体。
产物
类型名称一句话说明具体应用来源
模式RAG先检索外部文档，再把片段交给模型生成答案。知识库问答、企业搜索、带引用回答。
框架LangChain组合模型、prompt、检索、工具和 memory 的 LLM 应用框架。RAG、chain、tool calling、agent 应用。
框架连接私有/领域数据和 LLM 应用的数据框架。文档索引、检索、知识助手。
早期动态 agent 演示AutoGPT / BabyAGI让 LLM 在循环里拆任务、排队、执行和观察结果。2023 社区演示把 dynamic agent loop 推到大众视野，但工程稳定性有限。
具体产品Glean / Perplexity / Microsoft 365 Copilot / Amazon Q Business把检索、企业数据和生成式问答产品化。企业搜索、带引用回答、办公数据问答、业务知识助手。
仍未解决

静态 workflow 可控但不灵活，遇到未预设状态就卡住；早期动态 agent 灵活但脆弱、昂贵、难评估，长链任务容易错误累积。

易错点

LangChain 和 RAG 都不是 agent：LangChain 是应用框架，RAG 是检索增强模式；agent loop 是另一种控制流。

过渡：第一代 orchestration 让 LLM 应用真正能接文档、接工具、跑流程，但工程上暴露出状态管理、恢复能力、可观测性和安全边界不足。下一步的关键决策是把 workflow/agent 表达成更明确的状态化系统。
Stage 06

状态化 Agent 框架与生产化表达

2024 · 状态化编排时代

workflow 和 agent 的边界被工程化说清楚。

起点瓶颈
论述

第一代 orchestration 能把步骤串起来，但生产任务还要求流程可以暂停、恢复、观察、回放和人工接管。瓶颈不再只是“下一步由代码还是模型决定”，而是整个任务执行过程有没有清晰的 ：哪些信息写入 ，哪些步骤是 ，什么条件沿着 跳转，失败后能否从 恢复，关键节点是否允许 。

例子
任务状态Acme 年报任务跑到一半时，系统必须知道：已检索哪些页、R&D 数字是否已抽取、引用是否回到原文验证、表格解析失败了几次、是否等客户确认风险措辞。
失败路径如果表格解析失败，系统应跳到“换解析器 / 重新检索 / 请求人工确认”节点，而不是带着空数字继续生成备忘录。
瓶颈缺的是能表达状态、节点、边、恢复点和人工介入的流程结构，而不是再多写一个 prompt。
证据
边界混乱Anthropic 的 Building Effective Agents 明确区分 workflow 和 agent：workflow 通过预定义代码路径编排 LLM 与工具，agent 则由 LLM 动态指导自身流程和工具使用。这说明业界需要把“代码控制”和“模型动态控制”的边界工程化说清楚。
长流程需求LangGraph 文档把目标放在 long-running、stateful workflow 和 agent，并强调 durable execution、persistence、streaming、human-in-the-loop 等能力；这些能力正对应“流程能否恢复、观察和人工接管”的瓶颈。
证据边界这一阶段更多是工程框架和架构经验材料，不是一个统一 benchmark。因此文档只引用框架能力和架构定义，不伪造“状态图成功率”数字。
突破与产出
论述

关键变化是 ：把任务表达成有状态的图。节点表示步骤，边表示跳转，state 保存文档片段、工具结果、错误、重试次数、人工审批结果和最终产物。它让 workflow/agent 从“脚本拼接”走向 、可审计、可暂停、可恢复的生产化表达。

是静态/半静态编排的官方术语锚； 是状态图框架； 和 更偏多 agent 编程/编排框架； 是工具与数据源连接协议； 则把模型动作推进到 GUI/桌面环境。它们经常一起出现，但不是同一层。

例子
图结构检索年报 -> 抽取 R&D 数字 -> 计算趋势 -> 验证引用 -> 生成备忘录；每一步都把结果写入 state，下一步根据 state 决定。
恢复引用缺失时回到“检索证据”；客户要求确认风险措辞时进入 human-in-the-loop；工具报错时从 checkpoint 恢复，而不是整条任务重跑。
边界状态图改善控制流和恢复能力，但不会自动提高模型推理质量，也不会自动让工具安全可靠。
证据
官方模式命名Anthropic Building Effective Agents 列出 prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer 等 workflow 模式，给静态/半静态编排提供了清晰术语。
状态图能力LangGraph 文档将其定位为构建 long-running、stateful workflow 和 agent 的基础设施，强调 durable execution、streaming、human-in-the-loop、persistence 等能力。
CheckpointLangGraph persistence 文档说明 checkpoint 支持 human-in-the-loop、memory、time travel debugging 和 fault-tolerant execution。
多 agent 框架AutoGen 文档将其描述为用于构建 scalable multi-agent AI systems 的事件驱动编程框架；CrewAI 官方材料将其定位为面向工程师的 multi-agent automation / orchestration 框架。
真实环境入口Anthropic 2024-10 发布 Computer Use beta，让 Claude 通过 API 感知并操作计算机界面；这把 agent 从文本/工具调用推进到 GUI 环境。
工具连接Anthropic 2024 年提出 MCP，目标是把 AI assistant 连接到内容仓库、业务工具和开发环境。
产物

工程定式Anthropic 5 类 workflow 模式官方命名 prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer。静态/半静态 workflow 的术语锚定。

仍未解决

状态图能改善控制和恢复，但不能自动解决模型能力、工具安全、权限边界、跨厂商互操作和评估问题。

易错点

状态图不是智能本身：图画得再好，也不能替代模型能力、数据质量和工具可靠性。

过渡：状态化框架把“流程如何运行”说清楚了，但真正复杂的开发任务还要求模型能长时间读代码、改文件、运行命令、看失败日志并修复。下一步的关键场景是 agentic coding harness。
Stage 07

Reasoning Models 与 Agentic Coding Harness

2024 下-2025 · Coding Harness 时代

模型能力与真实执行环境开始合体。

起点瓶颈
论述

状态化框架能表达流程，但真实软件任务还要求 agent 进入工程环境：读仓库、定位文件、编辑代码、运行命令、看测试失败、生成 、隔离风险、保留日志。瓶颈从“流程能不能恢复”推进到“模型能不能在真实 和 里闭环工作”。这需要模型能力，也需要模型外的 。

例子
任务转写年报任务变成：“写脚本从 Acme PDF 抽取研发投入表格，运行脚本，发现解析失败，查看日志，修解析逻辑，再生成备忘录。”
真实难点模型不仅要知道 CAGR 怎么算，还要找到 PDF 解析代码、理解依赖、编辑文件、运行测试、根据报错改 patch，并避免破坏其他功能。
瓶颈这已经不是问答，而是需要文件系统、shell、测试、沙箱、补丁、回滚和权限边界的执行任务。
证据
真实任务难度 用真实 GitHub issue 评估模型修复代码问题。OpenAI 介绍 SWE-bench Verified 时指出，截至 2024-08-05，原 SWE-bench leaderboard 上 top agents 在 SWE-bench 约 20%、SWE-bench Lite 约 43%，说明真实代码修复仍是硬问题。
评估噪声 的推出说明，早期真实 issue 评估存在可执行性、描述清晰度和测试可靠性问题；要讨论 coding agent，必须关心可运行环境和评估质量。
突破与产出
论述

这里必须分两层： 是模型能力，让模型更擅长复杂问题； 是推理时投入更多计算来换取更可靠推理； 是模型外工程系统，提供仓库读取、搜索、编辑、shell、测试、patch、权限、日志和恢复循环。真正的 是二者叠加：模型会判断，harness 让判断进入真实工程环境。

、、、 都是 coding agent 产品形态；Aider、Cline 则代表更轻量或开源的开发者 harness 路线。注意：2021 年 Codex 是代码模型；2025 年后的 Codex 是 OpenAI 的软件工程 agent 产品线/能力，既有本地 CLI、IDE、App 配对工作形态，也有云端委派任务形态，同名但层级不同。

例子
Harness 做什么读仓库、搜索 PDF 解析代码、编辑文件、运行测试、看失败日志、提交 patch，并把这些动作记录成可审查的执行轨迹。
Reasoning 做什么判断失败原因、设计修复步骤、决定先改解析器还是先补测试，并在多个可能路径之间取舍。
边界它更能执行真实任务，但仍需要权限控制、成本控制、可复现环境、人工审查和回滚机制。
证据
模型能力层OpenAI o1 公告报告，2024 AIME 上 GPT-4o 平均解出 12%，o1 单样本为 74%。这说明 reasoning model 和 test-time compute 是模型能力层的变化，但它本身还不是 coding harness。
Harness 结果Claude 3.7 Sonnet 公告同时发布 Claude Code，并报告在 SWE-bench Verified 489 个可运行子集上，基础 为 63.7%，高计算设置为 70.3%。
工具环境Claude Code 文档说明它能理解代码库、编辑文件、运行命令并协助开发任务；OpenAI Codex 文档/公告说明 Codex 可在隔离环境中读取、修改和运行代码。
产品形态Cursor 官方文档描述其 Agent 可跨多个文件读写代码；Devin 文档描述其具备 shell、代码编辑器并能写、运行和测试代码；Aider 与 Cline 文档分别代表终端 pair programming 与编辑器内开源 coding agent 路线。

仍未解决

Coding harness 提升了真实任务可执行性，但仍需要权限控制、成本控制、任务评估、环境可复现、长任务监督，以及与非代码工具/其他 agent 的互通。

易错点

Reasoning model 和 harness 不能混为一谈：一个是模型能力，一个是让模型接触真实工程环境的系统。

过渡：coding agent 证明“模型 + harness + 环境反馈”可以完成更真实的任务，但每个产品都有自己的工具接口、上下文协议和协作方式。下一步的关键决策是协议化和 SDK 化。
Stage 08

协议生态与官方 Agent SDK

2025-2026 · 协议与 SDK 时代

工具连接、agent 协作和开发者原语开始标准化。

起点瓶颈
论述

Coding agent 证明了“模型 + harness + 环境反馈”能处理真实任务，但生态开始碎片化：每个 agent、工具、数据源、平台都有自己的连接方式、状态格式、权限边界和任务交接方式。瓶颈从“单个 agent 能不能干活”推进到“多个 agent、工具和平台能不能互相发现、交换任务、传递产物、保留权限边界”。这里需要 、 和开发者层的 。

例子
多 agent财务文档 agent 找年报与公告，表格 agent 计算研发投入趋势，邮件 agent 写客户备忘录，CRM agent 把结果同步到客户记录。
互通问题如果每个 agent 都用自己的工具协议、状态字段、产物格式和权限模型，财务 agent 很难把“已验证的研发投入表”安全交给邮件 agent。
瓶颈缺的是跨系统通信对象、工具连接协议、任务交接语义，以及开发者构建 agent 时可复用的标准原语。
证据
互操作碎片化A2A 规范的引言把问题背景说清楚：agent 可能由不同框架、语言或供应商构建，因此需要共同语言和交互模型。这里证明的是“跨系统互操作成为瓶颈”，不是把 A2A 当作瓶颈本身。
工具连接碎片化MCP 公告把目标放在连接 AI assistants 与内容仓库、业务工具、开发环境；这反映出工具/数据源接入已经从单应用问题变成生态级连接问题。
开发者原语碎片化OpenAI、Anthropic、Google 分别推出 Agents SDK、Claude Agent SDK、ADK，说明开发者需要复用 agent、tool、handoff、guardrail、tracing、session 等构建原语，而不是每个项目重写一套。
突破与产出
论述

关键变化是协议、SDK、平台三层开始分开：协议定义跨系统对象和连接方式；SDK 定义开发者构建 agent 的通用原语，例如 、、、、；平台则负责部署、治理、评估和运行。Orchestration 从“自己拼框架”走向官方 API/SDK 和跨系统协议。

MCP 偏工具/数据源连接，A2A 偏 agent 间互操作；OpenAI Agents SDK、Claude Agent SDK、Google ADK 偏开发者构建原语；Vertex AI Agent Builder / Agent Engine 这类产品偏平台化运行与治理。

例子
MCP 侧财务 agent 通过 MCP 连接年报库、数据库、文件系统或企业工具，不需要每个工具都写一套私有接入方式。
A2A 侧财务 agent 把“已验证的研发投入表”作为 artifact 交给邮件 agent，邮件 agent 继续生成客户备忘录。
SDK / 平台侧开发者用 Agents SDK 定义 tool、handoff、guardrail 和 trace，再把 agent 部署到平台里观察、治理和迭代。

仍未解决

协议和 SDK 仍在快速演化。Multi-agent interoperability 不是已经彻底解决的问题，而是正在形成的工程共识：工具连接、任务交接、权限、状态语义、评估和安全都还在迭代。

易错点

MCP 和 A2A 不是同一层：MCP 主要解决模型/agent 如何连接工具和数据源；A2A 主要解决 agent 之间如何互操作。
