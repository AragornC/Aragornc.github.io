① 来源:谁、何时、为什么造它

谁做的:Qdrant(读作 "quadrant",象限)由 Andrey Vasnetsov(CTO) 和 André Zayarni(CEO) 联合创办。背后是一家同名公司 Qdrant Solutions,总部在德国柏林(并设有美国办公室)。它不是某个大厂的副产品,而是一家专门做向量检索的独立创业公司。

什么时候开源:项目大约在 2021 年开源,代码托管在 GitHub(qdrant/qdrant),如今是 GitHub 上 star 数最高的向量数据库之一。

为什么造它(解决什么痛点):作者一开始想做向量搜索,试过 FAISS 这类"算法库"。但库只是"一个会算最近邻的函数",它不帮你存数据、不帮你做增删改、不能边过滤边搜、也不能扩展成集群。把这些生产功能自己补全非常痛苦。于是作者决定从零写一个"生产可用"的向量数据库——不只是算向量相似度,还要原生支持 payload(每条向量附带的元数据)+ 强过滤,这正是 RAG / 电商推荐里最缺的能力。

用什么语言:整个引擎用 Rust 写。Rust 没有 GC(垃圾回收停顿),内存安全又接近 C 的性能,很适合做这种又快又要稳的底层系统。

开源协议:Apache License 2.0,非常宽松,可商用、可改、可闭源分发。

背后的公司/社区:公司持续融资,2024 年 A 轮约 2800 万美元,2026 年 B 轮再融 5000 万美元(总融资约 8800 万美元,投资方含 Spark Capital、Bosch Ventures 等)。商业化主要靠托管服务 Qdrant Cloud,核心引擎保持完全开源。

② 原理 + 架构

客户端Python / REST / gRPC
→
Collection一个"表",定 size+距离
→
Segments数据切成多段并行
→
向量存储 + HNSW 图近邻搜索
+
Payload 存储 + 字段索引元数据过滤
→
合并打分Top-K 结果

一句话理解架构:一个 Collection(集合,相当于一张表)里的数据会被切成很多 Segment(段)。每个段都是"自给自足"的:它自己存一份向量、自己存一份 payload(元数据)、自己建自己的索引。查询时所有段并行各自找 Top-K,最后汇总。这样设计便于并发、便于增量写入、也便于水平扩展。

底层用什么 ANN:核心是 HNSW(分层可导航小世界图)。它不是把你的查询向量和库里每条都比一遍(那叫暴力搜索,太慢),而是把向量组织成一张"多层的邻居关系图",像坐地铁一样先坐"快线"跳到大致区域,再换"慢线"逼近最相似的点——用一点点精度换巨大的速度。Qdrant 不内置 IVF;对超大规模"放不进内存"的场景,它支持把向量和 HNSW 图放到磁盘(mmap / on-disk),再配合量化(把每个数压成 int8 甚至 1 bit)把内存占用压下来。

它最大的特色——可过滤的 HNSW(filterable HNSW):普通做法是"先搜后过滤"(搜出 100 个再丢掉不符合标签的,可能剩没几个)或"先过滤后搜"(标签筛完图断了,搜不准)。Qdrant 把过滤条件直接塞进图的遍历过程,边走图边判断 payload 是否满足条件,并额外加边保证图在强过滤下仍然连通。结果是:即使过滤掉 90% 的数据,召回率依然很高。

查询怎么走:请求进来 → 路由到 Collection 的各个 Segment → 每段在 HNSW 图上做带过滤的近邻搜索,同时查 payload 索引 → 各段返回局部 Top-K → 汇总、(可选)用原始向量重打分 → 返回最终结果。混合检索(稠密向量 + 稀疏向量/BM25)通过 Query API 在服务端用 RRF 等方式融合排名。

③ 存入的数据长什么样(真实代码白盒)

# 用官方 Python 客户端: pip install qdrant-client from qdrant_client import QdrantClient from qdrant_client.models import ( VectorParams, Distance, PointStruct, Filter, FieldCondition, MatchValue, PayloadSchemaType, ) client = QdrantClient(url="http://localhost:6333") # 本机 Docker 起的实例 # ① 建集合(相当于建表):向量维度 768,用余弦距离 client.create_collection( collection_name="articles", vectors_config=VectorParams(size=768, distance=Distance.COSINE), ) # ② 给元数据字段建 payload 索引 —— 这样按 category 过滤才快 client.create_payload_index( collection_name="articles", field_name="category", field_schema=PayloadSchemaType.KEYWORD, ) # ③ 插入一个 point:id + 向量 + payload(元数据)。upsert = 有则更新无则插入 client.upsert( collection_name="articles", points=[ PointStruct( id=1, vector=[0.12, 0.94, 0.03], # 实际应是 768 维,这里省略 payload={ "category": "tech", "title": "什么是向量数据库", "ts": 1719446400, # 时间戳,可用于范围过滤 "lang": "zh", }, ), ], ) # ④ 查询:给一个查询向量,只在 category=tech 里找最相似的 5 条(强过滤 + 向量搜索一起算) hits = client.query_points( collection_name="articles", query=[0.10, 0.90, 0.05], # 查询向量(768 维) query_filter=Filter( must=[FieldCondition(key="category", match=MatchValue(value="tech"))] ), limit=5, with_payload=True, ).points for h in hits: print(h.id, h.score, h.payload["title"])

它在磁盘/内存里大概怎么落地:每个 Collection 落在 storage/ 下,数据切成多个 Segment;每段把向量、payload(元数据,可理解为每条向量挂的一个 JSON)、HNSW 图和payload 字段索引分开存(可全放内存,也可 mmap 落盘)。热数据(量化向量 + 图)留内存保证快,原始全精度向量按需从磁盘读出来重打分;写入靠 WAL(预写日志)保证宕机不丢数据。

④ 优势 / 劣势

✓ 优势

  • 过滤是它的杀手锏:可过滤 HNSW 把元数据条件融进图遍历,强过滤下仍保持高召回——这是很多向量库的痛点。
  • Rust 实现,性能稳:无 GC 停顿,延迟可预测;在多家公开 benchmark 里吞吐/延迟名列前茅。
  • payload 表达力强:支持 keyword / 整数 / 浮点 / 布尔 / 地理坐标 / 文本全文等多种字段索引,过滤条件可 must/should/must_not 任意组合。
  • 省内存的工程能力:标量/二值量化 + on-disk 存储,可在 64GB 机器上服务上亿向量。
  • 原生混合检索:稠密 + 稀疏(BM25)向量同库存放,Query API 服务端融合,不必再外接关键词引擎。
  • 部署门槛低:一条 Docker 命令就能起单机;自带轻量 Web UI,上手快。

✗ 劣势

  • 生态比老牌数据库年轻:问题/最佳实践沉淀不如 Elasticsearch、PostgreSQL 那样海量。
  • 不是通用数据库:没有 SQL、没有 JOIN、不做事务,只能当"向量+元数据"检索层,通常还要配一个主库。
  • 自建分布式集群有运维成本:分片、副本、扩缩容要自己规划;省心就得上 Qdrant Cloud(付费)。
  • 内存敏感:想要极致低延迟,HNSW 图最好驻内存,大规模时 RAM 成本不低(可用量化/落盘缓解但有取舍)。
  • HNSW 单一路线:不内置 IVF 等其它索引,极端规模下的索引策略选择面相对窄。
  • 批量重建索引偏慢:大规模灌数据 + 建图是计算密集型,初次导入需要时间和调参。

⑤ 什么时候选 / 什么时候别选

✓ 适合

  • 做 RAG / 语义搜索 / 推荐,且检索时要按用户、租户、分类、时间等元数据强过滤。
  • 数据量在百万到数十亿向量,在意查询延迟和召回质量。
  • 想要一套稠密+稀疏(关键词)混合检索而不想再单独维护一个全文引擎。
  • 团队喜欢自托管开源、又希望未来能平滑迁到托管云(Qdrant Cloud)。
  • 需要多租户隔离(用 payload 字段做租户过滤是常见且高效的玩法)。

✗ 别用

  • 数据只有几万条:直接用 pgvector / SQLite + 向量插件甚至内存里算就够,别引入新组件。
  • 你要的是通用数据库(事务、SQL、复杂关联查询)——那是 PostgreSQL/MySQL 的活。
  • 已经重度使用 Elasticsearch 且关键词检索为主,加个向量字段比整套迁移更划算。
  • 完全不想运维、也不想引入新服务:优先考虑 PostgreSQL 的 pgvector 扩展。
  • 团队只接受全托管 SaaS 且不在意厂商锁定:Pinecone 这类纯托管可能更省心。
一句话:Qdrant 是用 Rust 写的开源向量数据库,最大亮点是"可过滤的 HNSW"——能边搜向量边按元数据强过滤还保持高召回;如果你在做需要按标签/租户/时间精确过滤的 RAG 或语义搜索,它几乎是首选,但它不是通用数据库,通常要和主库搭配使用。
