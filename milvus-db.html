① 来源:谁、何时、为什么造它

谁做的:由 Zilliz(中文常称「星智云」/上海赜睿) 这家公司发起并主导开发,创始团队从 2017 年左右开始做这件事。后来 Milvus 捐给了 Linux 基金会下属的 LF AI & Data 基金会(大致 2020 年成为孵化项目,2021 年毕业),变成一个有中立基金会托管的开源项目,而不是某家公司私有。

什么时候开源:第一个开源版本大约在 2019 年放出。后来经历过一次大重写:早期是单机为主,从 2.0 版本起改成了现在这套「云原生、存算分离」的分布式架构。

为什么造它(解决什么痛点):传统数据库(MySQL/PostgreSQL)擅长「精确查找」——你给一个 ID,它返回这一行。但 AI 时代的需求变了:你有一张图片/一段文字,想找「跟它最像的」内容。这些内容被模型转成几百上千维的向量(embedding),要在上亿条向量里快速找到「最相似的 Top-K」。普通数据库做不了这种「相似度搜索」,自己写又难以扩展到几十亿规模。Milvus 就是专门解决「海量向量的近似最近邻(ANN)搜索 + 能像数据库一样水平扩展、做过滤、保证一致性」这个痛点的。

用什么语言写的:系统主体(协调、调度、节点)用 Go 写,最吃性能的向量计算和索引引擎(底层叫 Knowhere)用 C++。你写代码时用的是 Python SDK(pymilvus),还有 Java / Go / Node.js 等官方客户端。

开源协议:Apache License 2.0,非常宽松,商用免费、可改可分发。

背后的公司 / 社区:商业公司是 Zilliz,它提供官方全托管云服务 Zilliz Cloud(跑在 AWS/GCP/Azure 上,省去你自己运维集群)。开源项目本身归基金会,社区活跃、GitHub 星标很高,是目前最主流的开源向量数据库之一。

② 原理 + 架构

客户端pymilvus / SDK
→
接入层 Proxy校验/路由/汇总结果
→
协调层 Coordinator调度/建索引指挥/一致性
→
工作节点Query/Data/Index Node
→
存储层etcd · 对象存储 · 消息队列

读懂这张图(从左到右):

1. 接入层(Proxy 代理):无状态的「前台」。你的请求先到这里,它负责校验、做负载均衡、把请求分发下去,最后把各节点返回的结果汇总排序再给你。

2. 协调层(Coordinator,Milvus 的「大脑」):管整个集群——谁存哪块数据、什么时候该建索引、什么时候该把数据压实(compaction)、保证集群一致性。它只指挥,不亲自干活。

3. 工作节点(真正干活的,无状态、可随便加机器):
· Query Node(查询节点):从对象存储把数据和索引加载进内存,执行相似度搜索。
· Data Node / Streaming Node(数据节点):接收新写入的数据,把内存里「还在长大的」数据落成固定的数据块。
· Index Node(索引节点):在后台为数据块构建 ANN 索引,建好后存回对象存储。

4. 存储层(数据真正落在哪,存算分离的关键):
· etcd:存「元数据」——集合的 schema、各种位点/检查点,要求强一致、高可用,也用来做服务注册和健康检查。
· 对象存储(MinIO / S3 / Azure Blob / GCS):存真正的大头——向量数据快照、标量数据、各种索引文件。便宜、可无限扩。
· 消息队列 / WAL(Pulsar / Kafka,新版还有自研 Woodpecker):所有写入先进这条「日志流」,保证写入持久、可回放、可恢复,也实现了「写入后很快就能查到」的实时性。

底层用什么 ANN:Milvus 不绑死一种算法,而是支持一大堆索引让你按「速度 vs 精度 vs 内存」权衡。CPU 内存类:FLAT(暴力精确)、IVF_FLAT / IVF_SQ8 / IVF_PQ(倒排聚类,省内存)、HNSW 及其量化变体 HNSW_SQ / HNSW_PQ(图索引,查询快、最常用)、SCANN;磁盘类:DiskANN(数据放 SSD,内存放不下也能搜上亿向量);还有 GPU 索引。简单理解:数据量小用 HNSW 求快,内存紧用 IVF_PQ 压缩,数据超大放不进内存就上 DiskANN。

查询是怎么走的(一句话串起来):请求 → Proxy 分发 → 各 Query Node 在自己负责的数据块上,用建好的 ANN 索引各算各的 Top-K,同时按你的标量过滤条件(expr)筛掉不符合的 → 结果回 Proxy 做全局归并排序 → 返回最终 Top-K。

③ 存入的数据长什么样(真实代码白盒)

# 安装: pip install pymilvus (本地零依赖可用 Milvus Lite,生产用单机/集群) from pymilvus import ( MilvusClient, FieldSchema, CollectionSchema, DataType, ) # 1) 连接。 给一个本地文件名 => 用嵌入式 Milvus Lite; # 生产则填 uri="http://localhost:19530" 连单机/集群 client = MilvusClient(uri="./milvus_demo.db") # 2) 定义“表结构”(Schema):一个集合 = 一张表 fields = [ # 主键: 64 位整数, 自动生成 FieldSchema(name="id", dtype=DataType.INT64, is_primary=True, auto_id=True), # 向量字段: 768 维浮点向量(比如 BERT/bge 的 embedding 输出) FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=768), # 标量字段: 用来做元数据过滤 FieldSchema(name="category", dtype=DataType.VARCHAR, max_length=64), FieldSchema(name="price", dtype=DataType.INT64), ] schema = CollectionSchema(fields, description="商品向量库 demo") # 3) 建集合 client.create_collection(collection_name="products", schema=schema) # 4) 为向量字段建索引(决定搜索快不快/准不准) index_params = client.prepare_index_params() index_params.add_index( field_name="embedding", index_type="HNSW", # 也可换 IVF_FLAT / DiskANN metric_type="COSINE", # 相似度度量: COSINE / L2 / IP params={"M": 16, "efConstruction": 200}, # HNSW 图的关键参数 ) # 若用 IVF_FLAT 则是: index_type="IVF_FLAT", params={"nlist": 1024} client.create_index(collection_name="products", index_params=index_params) # 5) 插入实体数据(向量 + 元数据一起写) rows = [ {"embedding": [0.12] * 768, "category": "鞋", "price": 299}, {"embedding": [0.34] * 768, "category": "包", "price": 899}, {"embedding": [0.56] * 768, "category": "鞋", "price": 1299}, ] client.insert(collection_name="products", data=rows) # 6) load: 把集合加载进内存才能搜(集群里就是分发到 Query Node) client.load_collection(collection_name="products") # 7) 搜索: 带标量过滤(expr)——只在“鞋且价格<1000”里找最相似的 2 条 results = client.search( collection_name="products", data=[[0.2] * 768], # 查询向量 limit=2, # Top-K filter='category == "鞋" and price < 1000', # 元数据过滤表达式 output_fields=["category", "price"], # 返回哪些标量字段 search_params={"params": {"ef": 64}}, # HNSW 查询期参数: ef 越大越准越慢 ) print(results)

它在磁盘 / 内存里大概怎么落地:Milvus 把每个集合的数据切成一块块 segment(数据段);新写入先进消息队列、在内存里形成「growing segment」,攒够后封存(sealed)并落到对象存储(MinIO/S3),索引节点再为它单独建好 ANN 索引也存回对象存储——向量、标量、索引是分开存的文件;集合的 schema 等元数据放在 etcd。查询时,Query Node 把需要的 segment 和索引从对象存储加载进内存(所以要先 load),在内存里跑搜索。这套「计算节点无状态 + 数据在对象存储」的设计,就是它能水平扩到几十亿向量的根本原因。

④ 优势 / 劣势

✓ 优势

  • 真能扩到几十亿向量:存算分离 + 计算节点无状态,加机器就能扛更大数据量和并发,这是它相对轻量库最大的护城河。
  • 索引选择最丰富:HNSW / IVF 系列 / DiskANN / GPU 索引全有,能按「速度-精度-内存-成本」精细权衡,别的库往往只给一两种。
  • 功能完整且生产级:标量过滤、混合检索(稠密向量 + BM25 全文)、多路召回、分区、RBAC、多租户,该有的都有。
  • 部署弹性大:从嵌入式 Milvus Lite(一个 pip 包)到单机 Docker,再到 K8s 分布式集群,同一套 API 平滑长大。
  • 生态成熟:LangChain / LlamaIndex / Dify 等几乎都原生支持,文档全、社区大、有官方托管云 Zilliz Cloud 兜底。

✗ 劣势

  • 分布式版运维重:完整集群涉及 etcd、对象存储、消息队列等多个依赖组件,自建和调优门槛高,小团队容易被运维拖垮。
  • 架构概念多、学习曲线陡:segment、load、coordinator、各类节点……比「一个进程搞定」的轻量库(如 Chroma)难懂得多。
  • 必须先 load 再查:数据要加载进内存才可搜,内存是主要成本和容量瓶颈(放不下才上 DiskANN,但会更慢)。
  • 小数据量是「杀鸡用牛刀」:几万到几十万向量场景,它的分布式优势用不上,反而徒增复杂度。
  • 资源占用偏高:即便单机版,内存/CPU 开销也明显高于嵌入式方案,不适合极端轻量或边缘部署。

⑤ 什么时候选 / 什么时候别选

✓ 适合

  • 向量规模千万到几十亿,需要水平扩展和高并发的生产系统。
  • 要求高级检索能力:复杂标量过滤、稠密+全文混合检索、多路召回、分区。
  • 团队有运维能力(或愿意用 Zilliz Cloud 托管),想要长期可演进的基础设施。
  • 需要多种索引按场景调优(用 DiskANN 装下超大数据、用 GPU 加速等)。
  • 企业级需求:RBAC 权限、多租户、高可用。

✗ 别用

  • 只有几万到几十万向量的小项目或 Demo——Chroma / pgvector 更省事。
  • 已经在用 Postgres 且数据量不大,只想加点向量能力——直接上 pgvector 别引入新系统。
  • 团队没人能运维分布式系统,又不想花钱用托管云。
  • 要嵌入到客户端 / 边缘设备、追求极致轻量零依赖(虽有 Lite,但定位仍偏服务端)。
  • 需求只是「临时跑个原型」,几天就丢——为它搭一套架构不划算。
一句话:Milvus 是为「海量向量 + 水平扩展 + 生产级功能」而生的开源向量数据库——数据量大、要高并发、要丰富索引和混合检索时它最强;但分布式运维偏重、概念多,小项目用它属于杀鸡用牛刀(那种场景选 Chroma / pgvector,嫌运维麻烦就直接上官方托管 Zilliz Cloud)。
