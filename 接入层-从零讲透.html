地基0

一次请求，到底是啥？

先把"你刷手机"这件事讲清楚

你打开快手 App，看到一个视频。这背后发生了什么？

你的手机，向远方某台电脑说："把这个视频给我。" 那台电脑收到后，把视频送回来。就这么简单的一来一回。

客户端 Client

"提出要求的那一方"。你的手机、电脑、浏览器，都是客户端。客户 = 要东西的人。

服务器 Server

"提供服务、给东西的那台电脑"。它不是你桌上的电脑，是放在机房里、24 小时开着、专门回答请求的电脑。服务 = 伺候你的人。

请求 / 响应 Request / Response

请求 = 客户端发出的"我要 XX"。响应 = 服务器返回的"给你 XX"。一问一答，叫一次请求。

地基1

手机怎么知道去找"哪台"服务器？

IP 地址 + 端口

世界上有几千万台服务器。你的手机怎么知道"快手的视频" 在哪一台？

答案：每台服务器都有一个独一无二的门牌号。

IP 地址 IP Address

每台联网设备的"门牌号"，长这样：142.250.66.78（四段数字）。全世界唯一，靠它就能在茫茫网络里精确找到这一台机器。

但是！一台服务器上同时跑着很多个程序：一个管登录、一个管视频、一个管评论…… 光有门牌号（IP）只能找到"这栋楼"，还要知道找"哪个房间"。这就需要端口。

端口 Port

一台服务器里"房间号"，是个数字（0–65535）。比如网页程序常住 80 房间、加密网页住 443 房间。IP 找到楼，端口找到房间。

地基2

数据怎么从手机"流"到服务器？

TCP 连接 = 打电话

找到地址了，但不能直接把数据"扔"过去。要先建立一条通道，像打电话要先拨号接通，才能说话。

TCP 连接 TCP Connection

TCP 是一套"怎么可靠传数据"的规矩（协议）。连接 = 手机和服务器之间临时建立的一条"专线"。建立好后，数据就在这条线上来回跑。就像打电话先拨通，才能讲话。

三次握手 Three-way Handshake

"拨号接通"的具体过程，要来回打三次招呼才算接通：
① 手机："喂，能听到吗？"
② 服务器："能，你能听到我吗？"
③ 手机："能，开始吧！"
→ 三句话之后，连接才正式建立。所以"建连接" 本身是有成本的（要等三个来回）。

问题3

一台服务器，能扛多少？

QPS 与"天花板"

一台服务器再强，也有极限。它能同时接的"电话"（连接）有限，每秒能算的请求也有限。

QPS Queries Per Second

"每秒能处理多少个请求"。Query=查询/请求，Per=每，Second=秒。一台普通服务器大概能扛 几万 QPS（比如 3 万）。

关键的算账

1500 万 ÷ 3 万 = 500 台。

核心4

几百台机器，请求该发给哪一台？

轴① 横向摊薄负载均衡登场

有 500 台机器了。但新问题来了：你的手机发请求，该连哪一台？

不能让用户自己选——用户根本不知道有哪 500 台、哪台正闲着。
所以需要在用户和这 500 台之间，加一个"分发员"，由它来决定每个请求发给谁。

负载均衡器 Load Balancer，简称 LB

站在所有服务器最前面的"分发员"。负载=工作量，均衡=分摊均匀。它收到所有请求，再"均匀地"分给后面的服务器，让每台都不会太累。这就是"横向摊薄"的核心装置。

🖥️ 1号 🖥️ 2号 🖥️ 3号 … 🖥️ 500号
分发员（LB）站最前面，把洪水分成 500 条小溪，每台只接 1/500
类比：食堂打饭

500 个窗口（服务器），门口站一个引导员（负载均衡器），他喊："你去 3 号窗口，你去 17 号窗口……" 让排队的人均匀散开，不会全挤在一个窗口。

核心5

分发员怎么决定"发给谁"？

五种负载均衡算法

分发员脑子里有一套"规则"，决定下一个请求发给哪台。常见 5 种，每种一个类比：

① 轮询（Round Robin）

挨个轮着来：1号→2号→3号→…→500号→1号→…循环。最简单、最公平。

类比

发扑克牌：一人一张，转圈发，绝对公平。

缺点：不管每台机器忙不忙，一律平均分。如果有台机器特别慢，照样塞给它。

② 加权轮询（Weighted Round Robin）

好机器多分，差机器少分。给每台机器一个"权重"（能力值），按能力分配。

类比

新来的壮汉（强机器）一次扛 3 箱，瘦小的（弱机器）一次扛 1 箱。按力气分。

③ 最少连接（Least Connections）

谁手上的活最少，就发给谁。分发员盯着每台机器"当前在处理几个请求"，挑最空闲的。

类比

超市结账：你会自动走到排队最短的那个收银台，而不是傻傻轮流。

④ 一致性哈希（Consistent Hashing）

同一个用户，永远发给同一台机器。 怎么做到？把用户 ID 用一个固定公式（哈希）算出一个数，这个数对应固定的某台机器。

哈希 Hash

一个"把任意东西变成固定数字"的公式。比如 哈希("用户张三") = 永远是 88。同样输入永远同样输出 → 所以张三永远被算到同一台机器。

类比

你的"专属理发师"：每次去都找同一个，因为他记得你上次剪的样子（机器上缓存了你的数据，同一台命中缓存，快）。

"一致性"的意思：加机器/减机器时，只有少部分用户被重新分配，大部分还是原来那台（不会全乱套）。

⑤ P2C（Power of Two Choices，二选一）

随机挑 2 台，比一下谁更闲，发给更闲的那台。现代生产最爱用——又简单又接近"最少连接"的效果。

类比

排队时不数所有队列（太累），随便瞄 2 个队，站短的那个。省力又有效。

算法一句话适合
轮询挨个转圈机器都一样强
加权轮询强的多分机器强弱不一
最少连接谁闲给谁请求耗时不均
一致性哈希同用户同机器要缓存命中 / 会话保持
P2C ⭐随机二选闲现代生产首选
进阶6

分发员看不看"信件内容"？

L4 vs L7

分发员转发请求时，有两种工作方式：只看信封 / 拆开看信。要讲清这个，先讲一个概念：网络是分层的。

网络分层 OSI / TCP-IP 模型

数据从你手机到服务器，要经过好几层"打包"，像快递层层套盒。我们只需记住两层：
• 第 4 层（传输层）：管"地址"——IP 和 端口。
• 第 7 层（应用层）：管"内容"——你具体要哪个视频、带什么 cookie。
所以叫 L4（Layer 4）和 L7（Layer 7）。

L4 负载均衡L7 负载均衡
看什么只看信封（IP + 端口）拆开看信（URL、cookie、内容）
快慢极快（不拆包）慢一点（要拆包分析）
聪明程度笨（不懂内容）聪明（能按内容路由）
能干啥纯转发"视频请求发A组，评论请求发B组"
代表软件LVSNginx / Envoy
类比：快递站 vs 公司前台

L4 = 快递分拣员：只看包裹上的地址（IP+端口）就往车上扔，不拆开看里面是啥，所以飞快。
L7 = 公司前台：拆开看"哦这是给财务部的合同"，再决定送哪个部门，更聪明但更慢。

LVS Linux Virtual Server

Linux 系统自带的 L4 负载均衡器，工作在第 4 层，只看 IP+端口、极快，能扛百万级并发。大流量入口的第一道分发常用它。

Nginx 读作 "Engine-X"

最流行的 L7 负载均衡器 + 网页服务器。能拆开看内容、按 URL 路由，还能限流、缓存。比 LVS 聪明，但单台吞吐稍低。

实战常组合

最前面用 LVS（L4，快，扛量） 把流量粗分到多个 Nginx（L7，聪明，细分），再由 Nginx 转给具体服务器。快 + 聪明 两全。

容灾7

分发员自己挂了怎么办？

轴③ 兜底VIP + Keepalived

所有请求都先过分发员（LB）。万一分发员自己宕机了——那后面 500 台再好也没用，因为没人分发了。这叫单点故障。

单点故障 Single Point of Failure，SPOF

系统里"只有一个、挂了就全完"的那个点。高可用设计的头号大敌。

解法：准备两个分发员（主 + 备），再用一个"漂移的门牌号"指向当前活着的那个。

VIP Virtual IP，虚拟 IP

一个"不固定绑在某台机器上的门牌号"。平时挂在主分发员身上；主挂了，这个门牌号瞬间漂移到备用分发员身上。对外永远是同一个地址，用户无感。

Keepalived 保持存活

一个"监工"程序。它一直盯着主分发员的心跳，一旦发现主挂了，立刻把 VIP 切到备用的身上。它就是负责"漂移门牌号"的那个人。

📱 用户都连 VIP：1.1.1.1
↓（VIP 现在指向主）
🚦 主分发员✓ 活着
🚦 备分发员待命
👁️ Keepalived盯着主
主挂了 → Keepalived 把 VIP（1.1.1.1）瞬间切到备用 → 用户完全没感觉

"kuaishou.com" 怎么变成 IP 的？

轴① 摊薄DNS

你输入的是"kuaishou.com"这种名字，但网络只认数字 IP。中间需要一本"电话簿"把名字翻译成 IP。

DNS Domain Name System，域名系统

互联网的"电话簿"。你问它"kuaishou.com 的 IP 是多少？"，它告诉你"1.1.1.1"。域名（名字）→ IP（数字）的翻译机。

DNS 负载均衡

这本"电话簿"还能耍花招：同一个名字，给不同用户返回不同的 IP。北京用户给北京机房的 IP，上海用户给上海机房的 IP。这是最前面、最粗的一道分发（连分发员都还没碰到，DNS 就先分了一次）。

提速9

每次说话都要重新拨号吗？

轴② 减负长连接 vs 短连接

还记得第 2 层说的"建连接要三次握手（3 个来回）"吗？如果每个请求都重新建连接、用完就断，那光"拨号"就浪费大量时间。

短连接长连接
怎么做每个请求：拨号→说话→挂断
怎么做拨号一次，反复说话，不挂断
成本每次都付"三次握手"的时间只在开头付一次
适合偶尔来一次的请求高频、持续的请求（如风控）
类比：打电话

短连接 = 每说一句话就挂电话，下句话重新拨号——傻。
长连接 = 拨通后一直聊，聊完再挂——聪明。风控这种每秒上千万请求，必须用长连接，省掉海量握手成本。

连接池 Connection Pool

提前建好一批连接"养着"，谁要用就借一条，用完还回去，不用每次新建。把"建连接"的成本均摊到几乎为 0。

底层10

操作系统层面还能怎么榨？

轴② 减负TCP 调优

到了最底层，连接本身还有几个"旋钮"可以调，让机器扛更多连接。三个高频名词：

backlog 连接排队区

三次握手还没完成的连接，先在一个"等待区"排队。backlog 就是这个等待区能站多少人。 太小 → 高峰期排不下、新连接被拒。调大它能扛更多突发连接。

TIME_WAIT 挂断后的"冷却期"

连接挂断后，端口不会立刻释放，要"冷却"一会儿（确保残留数据收完）。高并发下挂断的连接极多 → 大量端口卡在冷却期 → 端口被耗尽，新连接建不了。 要调参数加速回收。

keepalive 心跳保活

长连接如果很久不说话，怎么知道对方还活着？定期发个"还在吗？"的小信号探一下。对方没回 → 判定断了，回收这条连接。避免"僵尸连接"白占资源。

这三个是 Linux 操作系统的网络参数，调好了能让单台机器多扛几倍连接 —— 属于"纵向减负"里最底层的一拧。

🔬 TIME_WAIT 深挖：它到底卡在四次挥手的哪一步？

先把最容易绕晕的点钉死：TIME_WAIT 不是"挥手之前"也不是"挥手之后"的独立事件——它是一个状态，是主动关闭方发完第 4 个 ACK 之后、端口彻底释放之前的那约 60 秒。连接关闭不是"啪一下关掉"，而是走一段有名字的台阶（四次挥手），TIME_WAIT 是倒数第二级台阶，先关的那一方要在上面多站 60 秒。点"下一步"看它卡在哪 ——

为什么发完最后一个 ACK 还要再等 60 秒？

① 怕最后那个 ACK 在路上丢了。客户端发完 ACK 就以为完事，但它可能丢包；丢了服务器收不到确认，会重发自己的 FIN。客户端得还"在场"（停在 TIME_WAIT），才能补一个 ACK。要是立刻关了、端口都让给别人了，服务器重发的 FIN 就没人正确回应。

② 怕旧连接的残包污染下一条新连接。一条连接靠 (源IP, 源端口, 目IP, 目端口) 四元组唯一标识。若立刻用同一端口建新连接，上一条还在网上飘的残包会被当成新连接的数据 → 串台。等约 60 秒（2×报文最大存活时间），保证旧包全部"过期死光"再复用。

真实代码：亲眼看 TIME_WAIT 堆成山。一个最简单的服务器，配两种客户端，跑时另开终端用 ss（socket statistics）盯状态：

① 服务器（谁先 close 谁吃 TIME_WAIT，这里让客户端先关）
import socket
s = socket.socket()
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(('127.0.0.1', 9999)); s.listen(128)
while True:
    conn, addr = s.accept()   # 接一条连接（完成三次握手）
    conn.recv(1024)           # 收一句
    conn.send(b"hello")       # 回一句
    conn.close()
② 短连接客户端：每个请求新建一条、用完就关
# client_short.py —— 短连接
import socket
for i in range(10000):
    c = socket.socket()
    c.connect(('127.0.0.1', 9999))  # 建连接（三次握手）
    c.send(b"hi"); c.recv(1024)
    c.close()                        # 用完立刻关 ← 埋下一个 TIME_WAIT
③ 另开终端盯着 TIME_WAIT 涨
$ ss -tan | grep 9999 | awk '{print $1}' | sort | uniq -c
   9847 TIME-WAIT      # 一万次请求，堆出近一万个 TIME_WAIT
      3 ESTAB

# 把循环改成 range(100000) 并发跑，端口很快不够用：
OSError: [Errno 99] Cannot assign requested address   # ← 端口耗尽

本机能用的端口就约 6 万个，全卡在 TIME_WAIT 冷却期 → 新连接建不出来。这就是 L10 那句"端口被耗尽"的真相。

④ 换长连接客户端：建一次，复用同一条发一万次
# client_long.py —— 长连接 / 连接复用
import socket
c = socket.socket()
c.connect(('127.0.0.1', 9999))   # ★ 只建一次！
for i in range(10000):
    c.send(b"hi"); c.recv(1024)      # 复用同一条连接
c.close()                        # 全部发完才关这一次

$ ss -tan | grep 9999
      1 ESTAB          # 全程 1 条连接，TIME_WAIT 顶多 1 个
结论：根治靠连接复用，不是靠调内核参数

一万次请求，短连接堆出近一万个 TIME_WAIT；长连接只产生 1 个。所以高并发下治 TIME_WAIT 的正解是「长连接 + 连接池」（见 L9），调 tcp_tw_reuse 只是辅助；tcp_tw_recycle 新内核已删除、在 NAT 后会误杀，别用。

容灾11

整个机房停电了怎么办？

轴① 摊薄单元化 / 多活

前面 500 台都放在一栋楼（一个机房）。万一这栋楼整个停电 / 着火 / 光纤被挖断——全完。所以要把鸡蛋放到不同篮子。

机房 IDC，数据中心

放服务器的"楼"。成百上千台机器集中放在里面，有空调、备用电、专线。

方案意思能扛什么灾
同城双活同一个城市建两个机房，都在干活，一个挂另一个顶单机房停电
异地多活不同城市（北京+上海+广州）都有机房同时干活整个城市级灾难（地震/大停电）
单元化把用户切成几片，每片放进一个"自包含的单元"，单元里啥都全单元独立，一个坏不影响别的 + 方便异地扩展
类比

同城双活 = 家里两个保险丝盒，一个跳闸另一个还供电。
异地多活 = 北京广州都有分店，北京地震了广州照常营业。
单元化 = 把客户按地区分给不同分店，各分店自给自足。

兜底12

洪峰真的太大，先在门口拦一道

轴③ 兜底接入层限流

就算 500 台，也有扛不住的极限（比如突发 3000 万 QPS）。这时与其让所有请求冲进来把系统压垮，不如在最外面的门口，先拦掉一部分，保住核心不挂。

限流 Rate Limiting

"限制流量"：超过设定的速度，多余的请求直接拒绝（返回"稍后再试"）。宁可拒绝一部分，也不能让全部冲垮系统。

类比：景区限流

景区每天只放 1 万人。第 10001 个人来了，门口直接说"今天满了，明天请早"。放进去 1 万人玩得好，全放进去 5 万人挤踩踏——所以必须门口拦。

Nginx limit_req

Nginx（L7 分发员）自带的限流功能。在接入层就能设"每秒最多放 N 个进来"，多的挡在门外。越早拦越省（别让洪水进了核心才发现扛不住）。

统一13

所有请求先过一道"统一大门"

API 网关

很多通用的事——检查你是不是登录了、记日志、限流、防攻击——每个服务都自己做太重复。不如设一个"统一大门"，所有请求先过它，把这些通用活集中干了。

API 网关 API Gateway

站在所有后端服务前的"统一入口大门"。API = 程序对外提供服务的接口。网关在这里统一做：鉴权（你是谁、有没有权限）、路由（这个请求该转给哪个服务）、限流、日志、防刷。把横切的通用逻辑集中到一处。

类比：公司大门保安

所有访客先过大门保安：查证件（鉴权）、登记（日志）、人多了排队（限流）、引路（路由）。各部门自己不用再各设一道岗。

收口14

盖好了，回头看三轴

接入层的所有东西，归到三轴

现在把前面盖的所有楼层，归回到三轴里——你会发现每个知识点都属于某一轴：

轴在接入层的落地对应楼层
轴① 横向摊薄负载均衡（分发到多机）、DNS 分发、多活/单元化L4、L5、L8、L11
轴② 纵向减负长连接复用、连接池、TCP 底层调优L9、L10
轴③ 横切兜底接入层限流、VIP+Keepalived 高可用、快速失败L7、L12
一句话总结接入层

接入层干三件事：① 把洪水分到几百台机器上（负载均衡 + 多活）② 让每条连接尽量省（长连接 + TCP 调优）③ 扛不住时门口先拦、分发员自己也不能挂（限流 + VIP 高可用）。这正好就是三轴在"流量入口"这一层的全部落地。

面试怎么说（把这层串成一句）

"接入层我会从三轴讲：横向摊薄靠 DNS 按地区分到多机房、机房内 LVS+Nginx 多级负载均衡（L4 快分、L7 细分）+ 多活容灾；纵向减负靠长连接复用 + 连接池 + TCP 内核调优（backlog/TIME_WAIT/keepalive）；横切兜底靠接入层就近限流 + VIP+Keepalived 消除分发器单点。"
