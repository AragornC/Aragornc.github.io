ReentrantLock:比 synchronized 灵活在哪

核心

synchronized 是关键字,加锁解锁全自动(出了代码块自动放锁),但很死板:拿不到锁只能一直傻等,不能反悔。ReentrantLock 是一个类,要手动 lock() / unlock(),换来的是灵活。先看它当普通锁也对:

▶ ReentrantLock 计数(手动 lock/unlock)无特殊参数
200000。注意 unlock 一定放在 finally 里,否则异常时锁泄漏

它真正的杀手锏是 tryLock(超时)——拿不到锁可以等一会儿就放弃,这是 synchronized 永远做不到的(避免线程被一把锁永久卡住):

▶ tryLock:锁被占着,等 1 秒拿不到就放弃无特殊参数
输出:"等了1秒还没拿到 → 放弃",不傻等
synchronizedReentrantLock
形态关键字,自动加/放锁类,手动 lock()/unlock()(要写 finally)
拿不到锁只能一直等可超时(tryLock)、可中断、可放弃
公平性非公平可选公平锁(先到先得)
等待/唤醒wait/notify(只一个条件)Condition(可多个条件队列)
📌 AQS 一句话(底层地基):ReentrantLock、Semaphore、CountDownLatch 这些底层都是同一个东西——AQS(AbstractQueuedSynchronizer)。AQS 内部就是「一个 int 状态 state + 一条等待线程的排队队列」:抢锁 = 用 CAS 把 state 从 0 改成 1,成功就拿到,失败就进队列排队挂起。看,又是第 4 课的 CAS。

🔬 AQS 到底长啥样?(点一遍就懂) 别被名字 AbstractQueuedSynchronizer 吓到。把它想成银行的「叫号排队系统」:中间一个数字 state 表示"资源还剩多少"(当锁用时:0=空闲、1=被占),旁边一个等候区队列排着没抢到、正在睡觉的线程。点「下一步 ▶」,看 3 个线程抢 1 把锁:

state0锁空闲
等待队列(没抢到的线程在这排队 + 睡觉,先进先出)
📌 AQS = 「state + 队列」的通用模板。它把最难、最容易写错的活儿——用 CAS 原子地改 state、排队、把线程挂起/唤醒——全包了。各个工具只需回答一个问题:"state 怎么算才叫拿到资源"。对照着看就懂为什么它们是"一家人":
・ReentrantLock:state = 上锁次数(0=没人锁,1=锁了1次,2=同一线程重入2次…)
・Semaphore(K):state = 剩余许可证数(每 acquire 减1,减到0就排队)
・CountDownLatch(N):state = 还差几个没完成(每 countDown 减1,await 等它到0)
理解了 AQS,等于一次看穿半个 JUC 的发动机。
②

协调工具:让线程"等齐再走 / 限流"

核心

CountDownLatch(倒数门闩):设一个计数 N,每个线程干完活 countDown() 减 1,主线程 await() 一直等到减到 0 才放行。就像裁判等所有选手都准备好,才喊"开跑"。(第 4 课那个数 HashMap 的 demo 就用了它)

▶ CountDownLatch:裁判等 3 个选手都就位无特殊参数
看:三个选手陆续就位后,裁判才喊"一起出发"

Semaphore(信号量 / 许可证):手里有 K 张通行证,线程要先 acquire() 抢一张才能进,出来 release() 还回去,没证的排队等。天然的限流器——比如停车场只有 2 个车位:

▶ Semaphore:停车场只有 2 个车位,5 辆车抢无特殊参数
任何时刻最多 2 辆在场,其余排队,有人走才有人进
📌 一句话区分:CountDownLatch = "人齐了再开始"(等多个线程都完成);Semaphore = "最多 K 个同时进"(限流)。还有个 CyclicBarrier = "大家互相等齐、然后一起过、还能反复用"。它们底层都是 AQS。

亲手造一个死锁(并让 JVM 揪出来)

核心

死锁 = 两个线程各拿着一把锁,又都想要对方手里那把,谁也不肯先放 → 永远卡住。点「下一步 ▶」,看这个"环"是怎么一步步锁死的(绿实线=已持有,红虚线=在等待):

▶ 制造死锁 + JVM 自动检测报告无特殊参数
会打印"检测到死锁",并指出谁等谁的锁
死锁的 4 个必要条件怎么破(破一个即可)
① 互斥:资源同时只能一人用(锁的本性,通常没法破)
② 持有并等待:拿着 A 还要等 B一次性把要用的锁全申请到,要么全拿要么不拿
③ 不可剥夺:不能硬抢别人的锁用 tryLock(超时):拿不到就主动放掉手里的再重试
④ 循环等待:你等我我等你成环最常用:规定所有人按同一顺序加锁(都先 A 后 B),环就成不了
📌 实战记这一条:死锁最常见的根因是"加锁顺序不一致"(线程1先A后B、线程2先B后A)。让所有线程都按同一个固定顺序拿锁,死锁基本就绝迹了。线上排查死锁:jstack <pid> 会直接打印 "Found one Java-level deadlock"。
