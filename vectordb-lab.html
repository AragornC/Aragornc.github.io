这页讲什么:四个「数据库级」向量方案

做 RAG / 语义检索时,存放与搜索向量的工具大致分两层。库级(library)如 FAISS,本质是「一个会算最近邻的函数」——它只负责相似度计算,不帮你存原文、不做增删改、不能边过滤边搜、也不自带服务和集群。本页不收录 FAISS,因为它要自己补全一大堆生产能力。

这里对比的 4 个都是数据库级(database)方案:它们在向量索引之上提供了元数据存储、过滤、增删改、持久化、网络服务乃至分布式扩展,拿来就能当生产检索层用。它们的定位差异很大——从「一行 pip 内嵌进脚本」的 Chroma,到「能扛几十亿向量」的 Milvus,再到「直接长在你现有 Postgres 里」的 pgvector,以及「自托管首选、过滤强」的 Qdrant。下面的对比表、决策树和卡片帮你快速对号入座。

② 决策树 · 30 秒选型指南

从上往下读,命中第一条就用对应方案。大多数人停在前两三条。

已经在用 PostgreSQL?且向量量级在数千万以内,想让向量和业务数据共享 SQL / 事务 / 备份 → 别再搭第二套系统。
pgvector
完全不想运维任何东西?只想调个 API 就用上向量检索,且接受托管 SaaS。
托管
Pinecone / Qdrant Cloud / Zilliz Cloud
海量向量(上亿~数十亿)+ 高并发,且有 infra / 运维团队?要丰富索引(HNSW/IVF/DiskANN/GPU)和水平扩展。
Milvus
要自托管的通用首选?百万~数十亿规模,看重「边搜边按标签/租户/时间强过滤还保持高召回」,性能稳。
Qdrant
学习 / 原型 / 个人项目 / 中小规模?想一行 pip 装好、内嵌进脚本、原文+向量一站式存,最快从 0 跑到 1。
Chroma
最重要的一条:规模没到就别上 Milvus。几万到几百万向量的场景,Milvus 的分布式优势用不上,反而要搭 etcd、对象存储、消息队列一整套,徒增运维复杂度——属于「杀鸡用牛刀」。这种规模优先 Chroma(原型)或 pgvector(已用 PG),要自托管通用就 Qdrant,真等数据涨到上亿、单机扛不住时再迁 Milvus 也不迟。
