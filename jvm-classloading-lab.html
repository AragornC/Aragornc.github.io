类加载机制 · 单步白盒

类的"图纸"怎么从 .class 文件装进元空间;双亲委派怎么走;类加载器为啥会泄漏。← 内存结构 · GC 垃圾回收 → · 知识地图

😌 接着上一页: 内存那页里我们说"类的图纸已经在元空间了"——它是怎么进去的?就是"类加载"干的活。 一句话:把磁盘上的 .class 文件读进来、检查、登记到元空间、生成入口对象,让这个类能被使用。

① 类加载在干嘛:.class → 能用的类

.class 文件=你写的 .java 被编译后生成的文件,里面是 JVM 能懂的字节码(一种中间指令)。类加载就是把它"装进"JVM 变成能用的类。
.class 字节流
从 jar/磁盘/网络/运行时动态生成读进来
→
元空间:类元信息
把"图纸"(类结构、方法字节码、静态变量、常量池)登记进去
→
堆:Class 对象
造一个该类的 Class 对象,当作反射访问的入口
所以"类加载"的产物落在两处:元空间(类的图纸/元信息)+ 堆(一个 Class 对象当门把手)。下面看它具体分几步走。

② 五个阶段,单步走(重点:静态变量啥时候才是真实值)

加载→验证→准备→解析→初始化。点"下一步",盯住右边那个静态变量 count 的值怎么变。
class Counter {
  static int count = 10; // 静态变量
  static { // 静态代码块
    count = count + 5;
  }
}
count 的值轨迹: 加载 ·未分配 验证 ·未分配 准备 ·0 解析 ·0 初始化 ·15
📐 元空间:Counter 类元信息（共享）
📦 堆:Counter 的 Class 对象

③ 双亲委派:一个类该谁来加载?(点类名看)

类加载器分层:有请求时,先往上委派给父亲,父亲能加载就父亲加载;父亲不行才自己来。点个类名试试。
类加载器(ClassLoader)=专门负责"把类装进来"的组件,它们有上下级关系(下面三层)。双亲委派=收到加载请求时,自己先不动手,一路上交给父亲,直到顶层;顶层能加载就加载,逐级往上谁先找到谁加载。

④ 类加载器层次 + 为什么会"泄漏"撑爆元空间

三层(+ 可选自定义),从顶到下:

启动类加载器 BootstrapC++ 写的、JVM 自带。加载最核心的库(java.lang.* 等)。它没有"父亲"。
平台/扩展类加载器 Platform加载 JDK 的一些扩展模块。父亲是 Bootstrap。
应用类加载器 Application加载你自己的 classpath(你写的业务类)。父亲是 Platform。日常你的类都它加载。
自定义类加载器（可选）框架/容器自己写的,用于热部署、隔离、动态加载等。父亲一般是 Application。
⚠️ 泄漏怎么发生的(接上一页元空间 OOM):
规则:一个类的元信息(在元空间)能被卸载,当且仅当"加载它的那个类加载器"被 GC 回收掉。 而类加载器引用着它加载的所有类,类又反过来引用着加载器——它们是"一损俱损"的一团,要卸一起卸。

于是热部署翻车就这么来的:每次重新部署都 new 一个新的类加载器装一遍类;如果旧的类加载器被某个静态变量、缓存、或没停的线程抓着不放、回收不掉 → 它装的那一整批类的元信息就永远卡在元空间 → 部署几次,元空间一路涨 → OutOfMemoryError: Metaspace。
所以你上一问的"类加载器为什么会泄漏",根子就在这条"加载器↔类 互相引用、一起生死"的规则上。
小结:类加载 = 加载→验证→准备→解析→初始化 五步,把 .class 变成元空间里的类 + 堆里的 Class 对象;双亲委派保证核心类不被篡改、同名类不重复加载;类加载器和它的类一起生死,加载器泄漏 = 元空间泄漏。下一个白盒就是 GC(垃圾回收)——把"谁是垃圾、怎么清"讲穿。
