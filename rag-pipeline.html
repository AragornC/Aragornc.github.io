一条 RAG 向量检索，从「写进去」到「查出来」

把整条链路拆成 9 步，每步只回答四件事：做什么 · 大白话比喻 · 用什么算法 · 为什么这么做。

建库（写入·离线，做一次） ①加载→ ②切块→ ③向量化→ ④建索引 ⟹ 检索（查询·在线，每次问都跑） ⑤查询向量化→ ⑥召回→ ⑦融合→ ⑧重排→ ⑨喂给大模型
写入侧：建库时做一次，存起来反复用 检索侧：每次提问都实时跑一遍 可选 进阶步骤，简单场景可跳过
第一阶段 · 写入侧（建库 / 离线一次性）—— 把资料变成「可被搜索的向量」存好
步骤做什么大白话比喻常用算法 / 工具为什么这么做
1加载 & 解析
Load / Parse		 把 PDF、网页、Word、数据库里的内容，统一抽成干净的纯文本。 把一摞各种格式的书、报纸、网页，先全部撕成「只有字」的白纸。 PDF/HTML 解析器 OCR（扫描件） 去页眉页脚/乱码清洗 机器只认纯文本。格式越乱，后面切块和向量化越容易出错（垃圾进、垃圾出）。
2切块
Chunking		 把长文档切成一段段小块（chunk），每块几百字，常带重叠。 一本书太厚没法整本比对，先撕成一页页便利贴，每张写一小段。 固定窗口 + overlap 递归切分(按段落/句子) 语义切分 按标题/表格结构切 ①向量模型有长度上限；②块太大→检索不精准、混入无关内容；块太小→丢上下文。这是精准 vs 完整的核心权衡。
3向量化
Embedding		 每个小块文本 → 一串数字（向量，如 512/768 维），语义近的块向量也近。 给每张便利贴贴一个「气味标签」，意思像的便利贴气味也像，方便以后凭气味找。 BGE / E5 / GTE OpenAI text-embedding SBERT（都是 BERT 类，对比学习训练） 把「语义相似」变成「向量距离近」，这样找资料就变成了数学上的「找最近的点」。中文要用中文/多语模型。
4建索引
Indexing		 把所有向量存进向量库，并建「近似最近邻(ANN)」索引加速。可选同时建 BM25 关键词倒排索引 + 结构字段。 几百万张便利贴不能一张张翻。先按气味分门别类挂成一张「捷径地图」，找的时候走捷径。 HNSW（图索引，最常用） IVF（聚类倒排） PQ/SQ（量化压内存） BM25 倒排 百万级向量逐个算距离太慢。ANN 用「牺牲一点点准确换百倍速度」。BM25 倒排为后面的混合检索备好关键词通道。
第二阶段 · 检索侧（查询 / 在线，每次提问都跑）—— 把问题也变成向量，去库里捞最相关的
步骤做什么大白话比喻常用算法 / 工具为什么这么做
5查询向量化
Query Embed		 用户的问题，用同一个向量模型也转成一个向量。 把你的问题也提炼出一个「气味标签」，等会儿拿它去配。 同步骤③的模型 (可选)查询改写/扩展 HyDE 必须和建库用同一个模型，否则两边「气味」标准不一致，根本配不上。
6召回
Retrieval / ANN		 拿问题向量，去索引里捞出最近的 top-k 个块（粗筛，k 通常几十～几百）。可选同时用 BM25 捞一批关键词命中的。 拿你问题的气味，顺着捷径地图，先抓一大把气味最像的便利贴出来。 HNSW 近邻搜索(ef 参数) cosine / 点积 BM25 打分 先「宁滥勿缺」捞一批候选，保证该有的别漏（recall 优先），精排留给后面。
7混合融合可选·强烈推荐
Hybrid Fusion		 把「向量召回」和「BM25 关键词召回」两份结果合并成一份排名。 一个朋友凭「意思像」推荐，一个朋友凭「字眼对」推荐，把两份名单合成一份更靠谱的。 RRF（按排名融合，最常用） 加权分数融合 SPLADE(稀疏向量) 向量擅长语义、却漏精确词（IP、错误码、型号）；BM25 反之。融合补彼此盲区，是基线之上性价比最高的一招。RRF 按名次合并，绕开两种分数量纲不同的坑。
8重排可选·推荐
Rerank		 对候选里的前 N 个（20～100），用更强的模型把「问题+这块」一起读，精算相关度重新排序，取最终前几名。 候选太多，请一位「最较真的评委」把每张便利贴和你的问题逐一对照，挑出真正最对的几张。 Cross-Encoder 重排器 bge-reranker Cohere Rerank 召回用的双塔模型（query、doc 分开编码）快但糙；交叉编码器把两者一起喂、精度高但慢，所以只精排少量候选——粗召回保 recall，重排保 precision。
9喂给大模型
Augment + Generate		 把最终选出的几块文本，连同问题一起塞进提示词，让 LLM 据此作答（并可附引用）。 把挑出的几张最相关便利贴，连同问题交给学霸，让他「照着这些资料」回答，而不是凭空编。 Prompt 拼接(问题+context) 引用/出处标注 LLM 生成 这是 RAG 的最终目的——让大模型基于检索到的真实资料回答，减少幻觉、可溯源。检索质量直接决定回答质量。

选型对照 · 每步到底选哪个？

绿色高亮行 = 大多数人应该先用的默认选项。先用默认跑通，有了评测数据再针对性升级。

② 切块策略 —— 怎么切？
选项优势劣势什么场景用
固定窗口
+overlap		 最简单，速度快，可预测 会从句子/语义中间硬切断，割裂上下文 原型验证、纯文本日志；图省事的起步方案
递归切分默认 顺着段落→句子切，保结构、平衡好 需按文档类型调分隔符 绝大多数 RAG 的首选。2026 基准里 512token 递归切分排第一(69%)
语义切分 按"意思"边界切，精度最高(可+70%) 慢、贵(要额外算 embedding 判断断点) 高价值知识库、技术文档，且预算允许
结构切分
(按标题/表格)		 尊重原文档天然结构，表格不被切碎 依赖文档有清晰结构(Markdown/HTML) 结构化强的文档:手册、财报、带表格的 PDF

📏 实用默认：chunk 256–512 token，overlap 10–20%。注意"上下文悬崖"——块太大(>2500token)反而召回质量掉。

③ Embedding 模型 —— 用哪个把文本变向量？
选项优势劣势什么场景用
小模型起步默认
bge-small/large、text-embedding-3-small		 快、便宜、维度小(省存储)，本地可跑 难句/长难文档语义 reach 有限 先用它跑通，拿域内评测集量化效果再决定要不要升级
大模型
text-3-large、voyage-3-large、Cohere v4		 语义最准(MTEB 榜首梯队) 贵、慢、向量大，多为 API 依赖 检索质量是瓶颈、且小模型实测明显不够时再上
中文/多语
bge-m3、bge-zh、multilingual-e5		 中文/跨语言不退化(英文模型对中文≈噪声) 同档英文模型可能略弱于专精英文的 中文场景必选——这正是我们项目踩过的坑(英文 MiniLM→换 bge-zh)

⚠️ 铁律：建库和查询必须同一个模型；中文千万别用纯英文模型。选型先看 MTEB 榜 但一定用自己的数据复测。

④ ANN 索引 —— 几百万向量怎么建"捷径地图"？
选项优势劣势什么场景用
Flat
(暴力精确)		 100% 准确，无需调参 O(N) 逐个算，量大就慢 数据量小(几千~几万)或对召回零容忍——我们项目就用它当 ground truth
HNSW默认
(图索引)		 同等召回下查询最快，支持动态增删 内存占用大(存图的边)，建图慢 大多数 RAG 的默认:内存够、要高召回低延迟、数据会变
IVF-Flat
(聚类倒排)		 内存比 HNSW 省，超大规模也快 召回略低，需调 nprobe;静态数据更合适 数据量很大(>5000万)、内存比 HNSW 紧张
IVF-PQ
(聚类+量化压缩)		 内存省 10~100×，能塞下亿级 有损压缩→召回下降,需精调 海量向量 + 内存/成本是硬瓶颈,愿用召回换容量

🧭 路线：先 HNSW → 规模/成本顶不住了再换 IVF → 再不行上 IVF-PQ 压缩。小数据直接 Flat。

⑥⑦ 召回方式 —— 用哪条通道找候选？
选项优势劣势什么场景用
纯向量
(Dense)		 懂语义/同义/改写 漏精确词:IP、错误码、型号、人名 问答、概念检索、口语化 query
纯关键词
(BM25/稀疏)		 精确字面匹配，零训练、可解释 不懂同义("引流"≠"导流"就漏) 代码/日志/法条/精确术语检索

⑧ 重排 —— 要不要再请个"较真评委"？
选项优势劣势什么场景用
不重排 零延迟、零成本 top 几名精度受限于粗召回 召回已够好、对延迟极敏感、demo
Cross-Encoder推荐
bge-reranker、Cohere Rerank		 query+doc 一起读，精度显著提升 慢→只能精排少量(top 20~50) 对答案质量要求高时加;只重排融合后的前 N 条,缓存重复 query

🍱 一份"拿来就用"的默认配方

  • 切块:递归切分,512 token / overlap 15%
  • Embedding:中文用 bge-m3 或 bge-large-zh(英文 text-embedding-3-small);建库查询同款
  • 索引:HNSW(数据小直接 Flat)
  • 召回:向量 + BM25 混合,用 RRF 融合
  • 重排:对融合后 top 30~50 用 bge-reranker 精排,取最终 top 3~5
  • 升级顺序:先把这套跑通并建好评测集 → 缺什么补什么(先加混合检索,再加重排,最后才动模型/切块)。没有评测集就调参 = 蒙。

三句话记住整条链路

  • 写入侧（4 步）：撕成纯文本 → 切小块 → 每块变向量 → 建索引存好。做一次，反复用。
  • 检索侧（5 步）：问题也变向量 → 捞一批候选 → 两路结果融合 → 较真重排 → 喂大模型作答。每次提问都跑。
  • 为什么分这么多步：单一手段都有盲区——召回求全（别漏）、重排求准（别错）、融合补短（语义+字面），分工接力才又快又准。

最小可用 vs 生产级

  • 最小能跑：② 切块 + ③ 向量化 + ④ 建索引 + ⑤ 查询向量化 + ⑥ 召回 + ⑨ 生成。（就是最朴素的「向量检索 RAG」）
  • 生产加料：再加 ⑦ 混合检索（性价比最高）和 ⑧ 重排（精度再上一档）；切块策略和 embedding 选型是隐形胜负手。
  • 对照你那个 向量检索解剖台：BM25 = 步骤⑥的关键词通道；Dense = 步骤③+⑥的向量通道；图式渐近 = 沿结构图的另一种召回思路。
