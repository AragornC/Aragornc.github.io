① 来源:谁、何时、为什么造它

谁做的:由独立开发者 Andrew Kane(GitHub 账号 ankane)发起并主力维护。他还写过一堆机器学习相关的开源库。如今项目在 GitHub 的 pgvector/pgvector 组织下,由社区共同维护,贡献者来自各大云厂商和数据库公司。

什么时候开源:大约 2021 年首次开源发布(0.1.0)。此后版本稳步迭代,2024 年 10 月发布 0.8.0(引入迭代扫描),到 2026 年初已发布到 0.8.2 版(2026-02 发布,修复了一个并行 HNSW 索引构建的缓冲区溢出安全漏洞 CVE-2026-3172,CVSS 8.1)。

为什么造它(解决什么痛点):大模型时代,文本/图片都会被「嵌入模型」转成一长串数字(向量)。要做语义搜索、RAG、推荐,就得存这些向量并快速找「最相似的」。在 pgvector 出现前,你往往得另起一个专门的向量数据库,于是数据被切成两半:业务数据在 Postgres,向量在别处,两边要同步、要保证一致、要维护两套系统。pgvector 的思路是:别再搞第二个数据库了——直接给你已经在用的 PostgreSQL 加一个「向量」列类型和相似度搜索能力,向量和业务数据躺在同一张表里,共享同一套事务、备份、权限和 SQL。

用什么语言写的:核心是 C 语言(因为 Postgres 扩展必须用 C 写,才能深入数据库内核加新类型、新算子、新索引)。

开源协议:PostgreSQL License,这是一种类似 BSD/MIT 的极宽松协议,商用、闭源、再分发基本没限制。

背后的公司/社区:没有一家公司「拥有」它,它是纯社区开源项目。但它被整个 Postgres 生态当作事实标准,几乎所有云上的托管 Postgres(Supabase、Neon、AWS RDS/Aurora、阿里云、Google Cloud SQL/AlloyDB、Azure 等)都默认带着它。

② 原理 + 架构

客户端任意 PG 驱动 / SQL
→
PostgreSQL 内核查询解析 / 事务 / WHERE 过滤
→
pgvector 扩展vector 类型 + <=> 算子
→
ANN 索引HNSW 图 / IVFFlat 倒排
→
堆表 + 磁盘8KB 页 / WAL / TOAST

一句话理解架构:pgvector 不是一个独立的数据库,而是「寄生」在 PostgreSQL 里的一个扩展(extension)。它没有自己的存储引擎、没有自己的网络层,全都借用 Postgres。它只往 Postgres 里加了三样东西:① 一种新的列类型 vector(以及节省空间的 halfvec、稀疏向量 sparsevec、二值 bit);② 几个距离算子(<=> 余弦距离、<-> 欧氏 L2 距离、<#> 负内积);③ 两种专门给向量用的索引访问方法。

存储层:向量就是表里一个普通的列,跟着行一起存进 Postgres 的 8KB 堆页(heap page)。维度高、体积大的向量会被 Postgres 的 TOAST 机制挪到行外单独存。所有写入都过 WAL(预写日志),所以你天然就有了崩溃恢复、流复制、时间点恢复(PITR)。

索引层(底层 ANN):精确搜索(全表算距离)在数据量大时太慢,所以 pgvector 提供两种近似最近邻(ANN)索引:

  • HNSW(分层可导航小世界图):构建一个多层「跳表式」邻居图,查询时从顶层粗略跳、逐层细化。查询又快又准,但建索引慢、占内存多。不需要预先有数据就能建。默认首选。
  • IVFFlat(倒排文件):先把所有向量聚成若干个「桶(list)」,查询时只看离你最近的几个桶。建得快、省内存,但召回/速度的平衡不如 HNSW,而且需要表里先有数据来训练聚类中心。

注:pgvector 自带 HNSW / IVFFlat,不内置 DiskANN;若想要面向 SSD 的磁盘型索引,要看具体云厂商的增强版(如某些托管平台的扩展)。

查询怎么走:你写一句普通 SQL,Postgres 解析后发现 ORDER BY embedding <=> $查询向量 LIMIT 5,就会用上面的向量索引快速取回近邻;同一句里的 WHERE category=... 这类元数据过滤由 Postgres 自己处理。新版还加了「迭代扫描(iterative scan)」,避免过滤条件太严时召回不够的「过滤丢结果」问题。

③ 存入的数据长什么样(真实代码白盒)

-- 0) 在这个数据库里启用向量扩展(每库一次) CREATE EXTENSION IF NOT EXISTS vector; -- 1) 建表:向量只是其中一列,和业务字段躺在一起 -- vector(768) 表示这一列存 768 维的向量(维度要和你的嵌入模型一致) CREATE TABLE items ( id bigserial PRIMARY KEY, content text, -- 原始文本 category text, -- 业务元数据,后面拿来 WHERE 过滤 embedding vector(768) -- 768 维向量列 ); -- 2) 插入一行:向量写成 '[x,y,z,...]' 字符串即可(真实里通常是嵌入模型输出) INSERT INTO items (content, category, embedding) VALUES ('退货政策:30天内可无理由退款', 'faq', '[0.012, -0.043, 0.991, ...]'), ('如何重置登录密码', 'faq', '[0.220, 0.110, -0.330, ...]'); -- 3) 建 ANN 索引:用 HNSW + 余弦距离算子类(让相似度查询走索引、变快) CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops); -- 4) 查询:先按 category 过滤(SQL WHERE),再按余弦距离排序取最相似 5 条 -- <=> 是「余弦距离」算子,值越小 = 越相似;$1=类别,$2=查询向量 SELECT id, content FROM items WHERE category = $1 ORDER BY embedding <=> $2 LIMIT 5;

它在磁盘上大概怎么落地:这张 items 表和普通 Postgres 表完全一样——每行连同那 768 维向量(约 4×768+8 ≈ 3KB)写进 8KB 的堆页,超大的向量由 TOAST 拆到行外;写入走 WAL 保证不丢、可复制可恢复;而那条 HNSW 索引则是另一组磁盘页,里面存的是「向量之间的邻居图」结构,查询时数据库沿着这张图跳着找近邻,而不是逐行算距离。整张表/索引都能用 pg_dump 一起备份,享受 Postgres 的事务(ACID)、权限、JOIN 全套能力。

④ 优势 / 劣势

✓ 优势

  • 零新增系统:已经在用 Postgres 就直接 CREATE EXTENSION,不用部署/运维第二套数据库,也不用做跨库数据同步。
  • 向量与业务数据同表:能和订单、用户、权限等表直接 JOIN,过滤就是原生 SQL WHERE,表达力极强。
  • 白送 Postgres 全套能力:事务(ACID)、外键、备份、流复制、时间点恢复、行级权限——向量数据一并享受。
  • 生态无敌:几乎所有语言的 PG 驱动、ORM、BI 工具都能直接用;所有主流云的托管 Postgres 都内置它。
  • 协议宽松、完全开源:PostgreSQL License,商用无忧,不存在厂商锁定。
  • 混合检索可行:配合 Postgres 全文检索 + RRF 融合,关键词与语义检索能在同一库内组合。

✗ 劣势

  • 规模上限不如专用库:本质是单机扩展,到上亿级向量 + 高 QPS 时,纯靠 Postgres 横向扩展和性能会吃力。
  • 索引内存/构建成本高:HNSW 建索引慢、吃内存;大表重建索引是一笔不小的开销。
  • 调参靠你自己:m、ef_construction、lists、probes 等参数要手动权衡召回与速度,没有「智能默认」。
  • 功能比专用库窄:不内置 DiskANN、量化压缩、内置重排、多租户隔离等高级特性(部分要靠云厂商增强版)。
  • 过滤与 ANN 的配合有坑:强过滤 + ANN 可能召回不足,需要靠迭代扫描或精心建索引来缓解。
  • 共享数据库资源:向量查询吃 CPU/内存,可能和同库的在线业务互相抢资源,需要规划。

⑤ 什么时候选 / 什么时候别选

✓ 适合

  • 已经在用 Postgres,想就地加语义检索/RAG,不想再引入一个新系统。
  • 向量量级在万级到数千万,单机够用。
  • 需要把向量和业务数据强关联(复杂 WHERE、JOIN、事务一致性)。
  • 团队小、想省运维,直接用 Supabase / Neon / RDS 等托管 PG 一把梭。
  • 看重开源、无锁定、协议宽松。

✗ 别用

  • 向量规模奔着上亿甚至更高,且要求极致低延迟 + 高并发——选 Milvus/Qdrant/Vespa 这类专用分布式库。
  • 需要开箱即用的高级向量特性(DiskANN、标量量化、内置重排、分片副本管理)。
  • 团队完全没有 Postgres,只为做向量检索而单独搭一套 PG 不划算。
  • 向量写入/重建索引极其频繁、规模巨大,单机 Postgres 难扛索引构建压力。
  • 要求向量检索与在线交易业务严格资源隔离、互不影响。
一句话:pgvector 把「向量搜索」做成 PostgreSQL 的一个列类型和算子,让你不必另建向量数据库——已经在用 Postgres、规模在千万级以内、又想让向量和业务数据共享 SQL/事务/备份的团队,它几乎是默认最优解;但真要扛上亿向量、追极致性能与高级特性,就该上专用向量库。
