synchronized 到底锁的是"谁"?

核心

最容易踩的坑:以为"加了 synchronized 就安全"。错。 synchronized 锁的不是"代码",是一个对象(每个 Java 对象身上都自带一把锁,叫 monitor)。两个线程必须抢同一个对象的锁才会互斥;如果各锁各的对象,就是两把钥匙、互不干扰,照样撞车。切下面的开关看区别:

▶ 真跑:看锁不同对象会不会出错无特殊参数

synchronized 三种写法,锁的分别是不同对象 —— 一定要搞清你锁的是哪个:

写法锁的是哪个对象
synchronized void f(){}(实例方法)当前对象 this
static synchronized void f(){}(静态方法)这个类的 Class 对象(全类唯一)
synchronized(obj){ }(同步块)你括号里写的那个 obj
📌 记住:锁是"挂在对象上的一把钥匙"。只有抢同一把钥匙的线程之间才互斥。 第 1 课的 static synchronized inc() 之所以对,是因为静态方法锁的是同一个 Class 对象,两个线程抢的是同一把钥匙。

另一种 bug:改了,别人却"看不见"(volatile)

进阶

前面的 bug 是"算错"(丢更新)。这里是另一种 bug:看不见。每个线程为了快,会把变量缓存一份在自己手边(可以想成"本地副本")。结果:主线程把 running 改成 false,工作线程却一直读自己手边的旧副本 = true,于是永远停不下来。点「下一步 ▶」,两种模式对比着看:

看哪种:
工作线程 worker(在 while(running) 里转圈)
— 还没开始 —
主内存 runningtrue
主线程 main
准备睡 1 秒后
把 running 改成 false
▶ 普通变量:这个会"卡住",约 20 秒后被后端强制结束 —— 那个超时就是 bug无特殊参数
⚠️ 看到"⏱ 运行超时"别慌——这正说明 worker 永远没看到 false
▶ 加一个 volatile 关键字:worker 立刻看见、秒停无特殊参数
几乎瞬间结束,还会告诉你它转了几十亿次才看到
🔍 说人话 vs 真相:"本地副本"是个方便的比喻。真实原因是 CPU 各核有自己的高速缓存,加上 JIT 编译器为了快,会把 while(running) 里的 running 提到 CPU 寄存器里只读一次,后面循环根本不再回内存看。volatile 的作用就是命令 JVM:这个变量每次都老老实实读写主内存,不许偷懒缓存。
📌 两类并发 bug 收齐了:(1)原子性问题 = 丢更新(第1课,用锁/原子类修);(2)可见性问题 = 改了看不见(本课,用 volatile 修)。⚠️ 注意:volatile 只保证"看得见",不保证"算得对"—— 它修不了 count++ 的丢更新(那是原子性问题)。两件事别搞混。
