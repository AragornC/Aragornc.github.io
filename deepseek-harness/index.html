把 Harness 拆成一间
会自己接线的机器人工作室

这不是一份“把文件夹念一遍”的说明书。我们从一个最小问题开始： 给机器人装上模型、记事本和工具箱；拔掉任何零件时，依赖它的东西要安全停下，现场也要收拾干净。 Cordis 就是负责这套插拔、接线、断线和收尾规则的底座。

!
先纠正一个容易混淆的点

Cordis 不是模型、不是 Agent loop，也不是 Web 框架。它是一个“元框架”：规定动态组件怎样组合，但不规定业务是什么。

01 · The problem

先不谈代码：为什么需要 Cordis？

假设机器人已经在工作。你现在要热插拔一个搜索工具、切换文件系统后端，或换掉模型适配器。 难点不是“怎么调用函数”，而是变化发生后，整台机器还能不能处于一致状态。

A

装上去很容易

注册事件、开定时器、放进服务表、创建子插件——普通代码都能做到。

B

拔下来很难

监听器是否移除？计时器是否关闭？子组件是否先停？遗漏一个就会“幽灵运行”。

C

换依赖更难

文件系统提供方被替换时，谁依赖它？应该先停谁、再启动谁？半拆状态能否被看见？

动态系统要同时解决： 撤销我做过的事 ＋ 响应我依赖的东西
论文主张 时间可组合性（temporal composability）：组件移除时，它对共享环境的修改应被完整、安全地撤销。
论文主张 空间可组合性（spatial composability）：组件能声明依赖；依赖出现、消失或换身份时，生命周期会被协调。
源码事实 DeepSeek Harness 的模型适配器、工具注册表、会话日志、Agent loop 都作为插件装进同一棵树；它没有一块不可替换的业务“神圣内核”。
≠
“可卸载”不等于“时光倒流”

已经发到网络上的字节、已经被别人读走的文件、已经扣掉的钱，不会被一个 disposer 魔法抹除。论文只在 inverse 正确、步骤满足 pairwise independence 等假设时，证明经 Context 介导的状态达到 ≈：环境和 coeffect/service tables 精确一致，只忽略 registry control fields；这不是泛化的“看起来一样”。当前运行时只追踪并尝试调用作者提供的 disposer，不验证这些数学前提。外部发射需要延迟提交或补偿动作。

02 · Vocabulary

八个词，先用儿童版记住

下面每个比喻都只负责帮你建立第一印象。真正精确定义在后续源码段落里。

CContext：工作台

组件从这里拿服务、发事件、装子组件，也通过它登记需要回收的动作。

PPlugin / Component：零件说明书

一个函数、类或带 apply 的对象；告诉 Cordis “装我时做什么”。

SService：插座上的能力

例如 ctx.llm、ctx.tools、ctx.fs。名字是接口位置，提供方把实现插进去。

IInject / Coeffect：用电清单

组件提前声明“我需要 fs 和 tools”；没有插上时先别运行。

FFiber：一个零件的活体档案

记录它的状态、依赖版本、子 Context、清理栈和正在进行的切换。

EEffect：做事＋收据

每次改变环境，都同时交回一张“怎么撤销”的收据；Fiber 替你保管。

VEvent：广播与接力赛

插件之间的扩展点；有并行广播、顺序处理、遇到结果停止和洋葱中间件等模式。

LLoader：照清单装机器

把 YAML/JSON 配置行变成插件树；更新失败时尝试恢复旧组合。

1
一句话版

Context 是统一入口；Plugin 在自己的 Fiber 中运行；Service 是被提供的能力；Inject 声明所需能力；Effect 记录撤销；Event 提供协作；Loader 把声明式清单变成整棵树。

03 · Core mechanism

内核不是“总指挥”，而是几条守规矩的通道

根 Context 创建时就被 Proxy 包住，并挂上反射、注册表、事件与日志服务。 子 Context 通过原型链继承父环境，但可覆盖隔离与拦截信息。

01 · Registry 接收插件

识别函数、类或对象 apply，找到/创建 Runtime，再创建一个 Fiber。

02 · Fiber 拥有一个子 Context

插件不是直接拿根上下文；它获得带自己 Fiber、inject 与 intercept 状态的派生 Context。

03 · 父 Fiber 通过 effect 拥有子 Fiber

因此父组件卸载时，子组件也是其副作用的一部分，会被一并清理。

04 · 解析 Inject

缺少必须依赖时保持 PENDING；依赖齐全才进入加载。提供方身份变化会产生新 epoch。

05 · 执行插件

校验/解析配置后调用插件；产生的所有 effect、事件监听、服务和子插件都归这个 Fiber。

06 · ACTIVE / reload / unload

依赖变化触发重新计算；提供方退出 ACTIVE 会通知依赖者，provide 的清理还会等待它们稳定。其他兄弟 effects 可能并发，不能简化成全局串行。

解释性判断 Cordis 的“内核小”不是因为功能少，而是因为它只垄断组合语义：谁拥有谁、谁依赖谁、怎样清理、什么时候可见；模型调用和工具执行则交给 Harness 插件。
04 · Temporal composability

Effect：每做一组事，就把“后悔药”一起收好

ctx.effect(callback) 先为本次操作登记清理包装器，再执行 callback。 同一个 effect 内，callback 返回或 yield 的 disposer 会按 LIFO（后进先出）执行；但一个 Fiber 的多个顶层 effects 在卸载时会经 Promise.all 并发清理。 先登记包装器是为了应对 setup 期间的重入与失败。

!
保证有一个作者义务

运行时会跟踪 disposer，并在正常清理路径中按结构尝试执行；但某个串行 disposer 同步抛错、异步拒绝或永久不结算，都可能让该 effect 后面的清理无法完成。它更不能证明 disposer 真的是原动作的数学逆操作。论文明确把逆操作正确性留给组件作者。

∥
有清理先后要求时，不要拆成多个顶层 effect

当前 Fiber._unload() 会并发启动顶层 disposer。比如“必须先停止轮询，再关闭数据库”时，应把两步放入同一个 effect 的 disposer 链，或写一个明确串行的总 disposer。仓库 primer 也给出相同约束。

05 · Spatial composability

Inject + Fiber：插座变化，依赖者自动停和重开

组件不应偷偷摸摸读取任意全局服务；它声明 inject。 Context Proxy 读取服务属性时会检查声明，并依据当前隔离 realm 找到实现；未声明的访问会报错。

这是实际的六个状态，不是从左到右的单向流程：依赖缺失会稳定在 PENDING；依赖恢复进入 LOADING；启动异常清理后是 FAILED；显式 dispose 后是不可重启的 DISPOSED；“reload”是 UNLOADING → LOADING 的转换，不是一个状态。

为什么比较“提供方身份”，不只比较服务名？

同一个键 fs 仍然存在，但实现可能从本地文件系统换成远程沙箱。 Fiber 计算的 epoch 包含所解析提供方 Fiber 的 uid；新提供方意味着 uid 变化，依赖者因此重载。

为什么需要 committed view？

提供方正在卸载时，它内部可能已经拆掉一部分资源。Cordis 的 Proxy 沿 Fiber 链读取已提交快照； ctx.provide 的 disposer 会先移除全局绑定、通知并等待依赖者，再删除提供方自己的快照。 但这不等于一个 Fiber 内所有兄弟 effects 都有全局先后屏障——它们仍可能并发清理。

↻
环依赖不会被“聪明猜开”

A 必须等 B，B 又必须等 A，则双方都可能永久不活跃（当前代码状态名为 PENDING）。论文把依赖粒度与互相依赖列为开放设计张力；通常要抽出更小的共同服务或改成 broker。

06 · Events

事件不是只有“广播”：它还是可插拔控制流

Cordis 事件监听器归所属 Fiber；作用域过滤发生在每次 dispatch。不同 dispatch 模式表达不同协作契约。

事件模式播放器选择模式并运行
emit：同步点名

每位监听器立即被调用；返回值被忽略。

模式像什么适合Harness 示例
emit广播通知同步观察，忽略返回agent/status、内部生命周期通知
parallel同时派工彼此独立，等全部结束并行收集或关停工作
serial排队过检查点顺序重要，可停止agent/turn-stopping
bail抢答第一个不是 null / false / undefined 的结果胜出；0 和空字符串也会停止查找第一个能处理者
waterfall洋葱中间件包装/改写下游；不调用 next 即截断agent/request、llm/stream、tools/pre-execute、tools/execute、tools/post-execute
→
把 waterfall 想成一排安检门

每扇门可以先检查，再调用 next() 让请求进入下一扇门，回来后还可加工结果；不调用 next 就是明确拦截。它让重试、压缩、权限、日志等策略无需塞进 Agent loop 主体。

isolate：换插座编号

Loader 为 entry 创建本地或具名 realm，把服务名映射到 Symbol。共享同一标签的 provider 与 consumer 会进入同一隔离域。

intercept：给插座加使用说明

例如依赖 loader 的组件可声明是否必须等待所有加载任务结束；Service 的配置会从依赖者上下文解析。

解释性判断 isolate 是“一个进程里同名 service 有多套实现”的基础；上图使用 shipped Standard/Code preset 中真实被隔离的 planMode 举例。两个 entry 的 group id 都是 planning，所以 Symbol 描述可相同；真正隔离它们的是 Symbol 身份，而不是后缀文本。 工具则注册到共享 Host ctx.tools registry，每 Agent 的可见工具/提示主要由 dsh-scope 过滤，不应画成隔离的 tools service。

三个看似相近、其实不同的东西

Context.extend()

派生一个沿原型链继承的 Context；每个 Fiber 都自动获得它。不是安全隔离。

Cordis isolate

只把指定 service key 重定向到另一个 realm Symbol；不会复制整个容器。

Harness dsh-scope

控制共享 registry 中工具、提示与事件的可见范围；它是 Cordis 之上的 Harness 领域层。

08 · Declarative assembly

Entry 更新若新插件应用失败，会尝试重新启动旧插件；Group 更新也会删除新增项并重建旧项。但外部不可逆发射仍不在这个事务里。

Profile 与 Agent preset 也不是一回事

Profile：装这一整个进程

决定 Host 有哪些基础 provider、是否带 Web/Headless 表面、持久化和沙箱怎样配置。它通过 Loader entry tree 落地。

Preset：给某类 Agent 配书包

决定该 Agent scope 可见的 persona、提示段和 model-facing tools。Web 中 preset 是 standing mount，再由每个 Agent scope 继承；真正提供独立 service 的行还必须进入 Cordis isolate group。

2×
Web 实际上横跨两棵 Cordis 组合树

Node/Host 树承载模型、会话、工具、API 与服务器；浏览器端还有独立 Cordis 应用，加载 connection、client runtime、conversation、tool 与 settings 等 UI 插件。两边用 typed RPC + 事件流连接。

三类“事件”不要混在一起

Session events

追加到日志的持久事实：user/message、assistant/message、tool/result。重放后仍存在。

Agent events

活跃过程的控制面：inbox、状态、pre-step、request、steering、错误恢复。通常不等于历史事实。

Capability events

能力局部的扩展点：tools/*、fs/*、telemetry/*，不用改主循环。

源码事实 Harness 的关键不变量是“模型可见即已记录”：模型请求历史从 Session 的事件 surface 派生，而不是从 UI 或临时数组拼出来。

13 · Boundaries & trade-offs

为什么这样设计，以及要付什么代价

架构不是“优点集合”。每项能力都换来新的约束；下面把因果关系写完整。

得到：局部热插拔

effect 让资源所有权与创建位置相邻；Fiber 让父子卸载可传播。

付出：必须经过 Context

绕开 ctx 直接改全局变量、注册第三方监听却不交 disposer，框架就无法追踪。

得到：依赖响应式重载

inject + provider uid 让实现身份变化自动传播，不必每个组件手写 watch。

付出：更多生命周期复杂度

异步 setup、重入、并发卸载、失败回滚、稳定视图都需要严格状态机。

得到：能力可替换

Definition/Provider/Consumer 分离，让同一工具链换本地、沙箱或远程后端。

付出：接口与版本纪律

键名相同不代表语义兼容；依赖类型、版本漂移和多提供方策略仍要显式治理。

得到：配置可重组

Profile/Bundle/Patch 让产品表面由数据组装，用户能覆盖具体 entry。

付出：有效配置不再在一个文件里

必须用 dsh --profile web --dump-config 看最终树；整个 config 替换也要求覆盖者重述保留字段。

四个常见误解

误解 1：Service 就是全局单例

不准确。服务名可经 isolate 映射到不同 Symbol；同一进程可有多个 realm。

误解 2：所有插件按 YAML 顺序启动

不准确。Base patch 明确说行顺序不承载加载语义；激活由 service 可用性驱动。

误解 3：Cordis 就是依赖注入容器

只说对一半。它还规定 effect 回收、Fiber 生命周期、事件所有权、隔离与 Loader 对账。

误解 4：论文证明 Harness 会自我进化

错误。论文把自进化 harness 当动机与未来验证方向；当前仓库采用 Cordis 不等于完成了开放式自进化实证。

盾
依赖声明不是恶意代码沙箱

Context Proxy 能限制经 Proxy 的服务访问，类似能力请求；但恶意插件仍可直接调用 Node API。论文明确说这需要外部 sandbox。Harness 因此另有 sandbox/approval/file-system policy 层。
