地基0

消息队列(MQ)是干嘛的？

先一句话定位

前四层（接入/计算/缓存/存储）都是"请求来了，同步处理完就返回"。但现实里：很多事不必当场做完（下单后发短信、同步数仓）；很多流量扛不住当场处理（秒杀瞬时洪峰）；很多系统不该直接耦合（下单系统不该亲自去调用十个下游）。

消息队列(MQ) = 在系统之间架一个"中转站 / 缓冲池"：生产者把消息扔进去就走，消费者按自己的节奏取出来处理。三大价值：解耦、削峰、异步。常见实现：Kafka、RocketMQ、RabbitMQ、Pulsar。这一层怎么做好？还是那三根轴：

轴② 纵向减负
MQ 怎么给主链路减负：异步

MQ 给主链路减负的方式是"异步"——把非核心、耗时的操作从主流程剥离丢进队列，主流程只做核心、立刻返回。

F01

同步 vs 异步：剥离非核心耗时

下单主流程：扣库存(核心,必须同步) + 发短信/发券/记日志(非核心,可异步丢队列)。

import java.util.concurrent.*;
// 异步层 | 轴② 减负 | 同步 vs 异步：把非核心耗时操作从主链路剥离
public class F01_SyncVsAsync {
    static void step(String name, int ms) { try { Thread.sleep(ms); } catch (InterruptedException e) {} }
    public static void main(String[] a) throws Exception {
        // ① 同步：下单主流程把 4 件事一件件做完，用户一直等
        long t0 = System.currentTimeMillis();
        step("扣库存", 50); step("发短信", 100); step("发优惠券", 100); step("记日志", 100);
        System.out.println("【同步】用户等待 " + (System.currentTimeMillis() - t0) + " ms（4 件事全做完才返回）");

        // ② 异步：主流程只做核心(扣库存)，其余丢队列后台慢慢做，立刻返回
        BlockingQueue<String> mq = new LinkedBlockingQueue<>();
        Thread consumer = new Thread(() -> {
            try { String m; while (!(m = mq.take()).equals("STOP")) step(m, 100); } catch (InterruptedException e) {}
        });
        consumer.start();
        long t1 = System.currentTimeMillis();
        step("扣库存", 50);                                  // 核心，必须同步
        mq.put("发短信"); mq.put("发优惠券"); mq.put("记日志");  // 非核心，丢队列异步处理
        long userWait = System.currentTimeMillis() - t1;
        System.out.println("【异步】用户等待 " + userWait + " ms（扣完库存立刻返回，其余后台慢慢做）");
        mq.put("STOP"); consumer.join();
        System.out.println(">> 异步把非核心耗时操作从主链路剥离丢队列，主链路只做核心、立刻返回 → 用户体验从 ~350ms 降到 ~50ms。");
    }
}

异步化怎么判断

判断标准：这一步是不是用户必须当场等的"核心"？不是，就丢队列后台做。注意：异步是"稍后一定会做"，不是"不做"；而且必须保证消息不丢（见 F05）。用户等待从 ~350ms 降到 ~50ms。

轴① 横向摊薄
解耦 → 两端各自扩展

生产者和消费者通过队列"解耦"后，两端可以各自独立扩展、独立部署；再靠分区 + 消费者组让消费并行化，吞吐随分区数水平扩展。

F02

解耦：消费者挂了不影响生产

生产者和消费者不直接调用，通过队列中转。看消费者宕机时生产者照常投递。

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;
// 异步层 | 轴① 摊薄 | 解耦：消费者挂了/慢了，不影响生产者
public class F02_Decouple {
    static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) {} }
    public static void main(String[] a) throws Exception {
        LinkedBlockingQueue<Integer> mq = new LinkedBlockingQueue<>();
        AtomicInteger consumed = new AtomicInteger();

        Thread producer = new Thread(() -> {              // 生产者：不管消费者死活，照常投递 10 条
            for (int i = 1; i <= 10; i++) {
                try { mq.put(i); } catch (InterruptedException e) {}
                System.out.println("  [生产者] 投递消息" + i + "  (此刻队列积压=" + mq.size() + ")");
                sleep(80);
            }
        });
        Thread consumer = new Thread(() -> {              // 消费者：中途宕机一会儿，恢复后继续
            try {
                for (int n = 0; n < 10; n++) {
                    if (n == 3) {
                        System.out.println("  [消费者] *** 宕机 600ms（生产者不受影响，继续投递）***");
                        sleep(600);
                        System.out.println("  [消费者] *** 恢复，继续消费积压的消息 ***");
                    }
                    int msg = mq.take(); consumed.incrementAndGet();
                    System.out.println("  [消费者] 处理消息" + msg);
                }
            } catch (InterruptedException e) {}
        });
        producer.start(); consumer.start(); producer.join(); consumer.join();
        System.out.println(">> 生产者和消费者通过队列解耦：消费者宕机期间生产者照常投递，消息在队列里等着，恢复后接着消费——一条不丢，共消费 " + consumed.get() + " 条。");
    }
}

解耦 Decoupling

生产者只管把消息投进队列，不关心谁消费、消费得多快、消费者活没活。好处：① 消费者宕机/变慢，生产者不受影响（本 demo，积压留队列、恢复后接着消费）② 两端可独立扩展、独立部署 ③ 加新消费者订阅同一消息不用改生产者——比如"下单"事件，风控、营销、数仓可以各自订阅，互不知道对方存在。

F03

分区 + 消费者组：并行消费

一个 Topic 分多个分区，消费者组里每个消费者包一个分区，并行消费。

import java.util.concurrent.*;
import java.util.*;
// 异步层 | 轴① 摊薄 | 分区 + 消费者组：多分区并行消费，吞吐随分区数扩展
public class F03_PartitionParallel {
    static final int P = 4;
    public static void main(String[] a) throws Exception {
        List<BlockingQueue<String>> parts = new ArrayList<>();
        for (int i = 0; i < P; i++) parts.add(new LinkedBlockingQueue<>());

        int N = 12;                                            // 生产 12 条，按 key 哈希分到 4 个分区
        for (int i = 0; i < N; i++) {
            String key = "user" + i;
            int p = (key.hashCode() & 0x7fffffff) % P;
            parts.get(p).add("msg-" + key);
        }
        for (int i = 0; i < P; i++) System.out.println("  分区" + i + " 分到 " + parts.get(i).size() + " 条");

        // 消费者组：4 个消费者，各包一个分区，并行消费，每条处理 100ms
        long t = System.currentTimeMillis();
        CountDownLatch latch = new CountDownLatch(P);
        for (int i = 0; i < P; i++) {
            int id = i;
            new Thread(() -> {
                BlockingQueue<String> q = parts.get(id);
                while (q.poll() != null) { try { Thread.sleep(100); } catch (InterruptedException e) {} }
                System.out.println("  消费者" + id + " 处理完分区" + id);
                latch.countDown();
            }).start();
        }
        latch.await();
        System.out.println("4 个消费者并行处理 " + N + " 条，耗时 " + (System.currentTimeMillis() - t) + " ms");
        System.out.println("  对比：1 个消费者串行处理 " + N + " 条 ≈ " + (N * 100) + " ms");
        System.out.println(">> Topic 分多个分区，消费者组里每个消费者包一个分区并行消费 → 吞吐随分区/消费者数扩展（消费者数 ≤ 分区数）。");
    }
}

分区 / 消费者组 Partition / Consumer Group

分区=把一个 Topic 的消息拆成多条并行"车道"。消费者组=一组消费者分摊这些分区，且每个分区同一时刻只被组内一个消费者消费（所以消费者数 ≤ 分区数，多了闲置）。要提吞吐就加分区 + 加消费者。本 demo 4 分区并行 420ms vs 单消费者串行 1200ms。

轴③ 横切兜底
队列 = 缓冲垫 + 安全网

队列是高并发系统的"缓冲垫"和"安全网"：削峰挡洪峰、ack保证不丢、幂等容忍重复、分区保证局部有序、死信隔离毒消息。这一轴是 MQ 的可靠性重灾区，也是面试最爱问的地方。

F04

削峰填谷

瞬时洪峰(1000 条)先进队列缓冲，消费者按下游能力匀速消费(每批 100 条)。

import java.util.concurrent.*;
// 异步层 | 轴③ 兜底 | 削峰填谷：洪峰进队列缓冲，消费者匀速消费保护下游
public class F04_PeakShaving {
    public static void main(String[] a) throws Exception {
        LinkedBlockingQueue<Integer> mq = new LinkedBlockingQueue<>();
        int BURST = 1000;
        for (int i = 0; i < BURST; i++) mq.add(i);             // 瞬时洪峰：1000 条一下子涌入
        System.out.println("瞬时洪峰：" + BURST + " 条消息一下子涌入队列（队列瞬间积压 " + mq.size() + "）");
        System.out.println("下游能力有限，消费者匀速消费（每 50ms 处理一批 = 100 条）：");

        long t = System.currentTimeMillis();
        int batch = 0;
        while (!mq.isEmpty()) {
            for (int i = 0; i < 100 && !mq.isEmpty(); i++) mq.poll();   // 处理一批
            batch++;
            System.out.println("  第 " + batch + " 批处理后，队列还积压 " + mq.size() + " 条");
            Thread.sleep(50);
        }
        System.out.println("洪峰被队列削平，下游始终匀速处理，没被打挂。总耗时 " + (System.currentTimeMillis() - t) + " ms");
        System.out.println(">> 削峰填谷：洪峰先进队列缓冲（瞬间涨到 1000），消费者按下游扛得住的速率匀速消费（队列慢慢落）→ 下游看到的是平稳流量，不是瞬时 1000 并发。");
    }
}

削峰 + 消息积压

这是 MQ 最经典的高并发用途：秒杀/大促瞬时百万请求，直接打 DB 必挂；先进队列，下游匀速消费。代价：① 异步化 → 结果不实时（下单后显示"处理中"）② 要处理消息积压——若生产持续 > 消费，队列无限涨、延迟暴增。解法：加消费者 / 加分区 / 批量消费 / 临时降级丢弃非核心消息。

F05

消息不丢：ack 机制

先 ack 后处理(at-most-once,崩了丢) vs 先处理后 ack(at-least-once,崩了重发不丢)。

// 异步层 | 轴③ 兜底 | 消息不丢：ack 机制（先确认还是先处理，结果天差地别）
public class F05_Ack {
    // 模拟一个 broker：消息要等消费者 ack 才删除；没 ack 则保留、稍后重投
    public static void main(String[] a) {
        boolean crash = true;   // 假设消费者处理到一半崩溃

        System.out.println("【at-most-once：先 ack 后处理】");
        boolean inBroker1 = true;
        inBroker1 = false;                                   // 一拿到就 ack，broker 立刻删除
        System.out.println("  收到消息 → 先 ack（broker 已删除）→ 再处理...");
        if (crash) System.out.println("  处理到一半崩溃！→ broker 里已经没这条消息了 → 消息永久丢失 ✗");
        System.out.println("  结果：broker 中消息 = " + (inBroker1 ? "还在" : "已丢失") + "（最多消费一次，可能丢）\n");

        System.out.println("【at-least-once：先处理后 ack】");
        boolean inBroker2 = true;
        System.out.println("  收到消息 → 先处理...");
        if (crash) System.out.println("  处理到一半崩溃！→ 还没 ack → broker 保留消息，稍后重投");
        System.out.println("  重启后：broker 重投这条消息 → 这次处理成功 → ack");
        inBroker2 = false;
        System.out.println("  结果：消息没丢，但可能被处理 2 次（崩前处理一半 + 重投又处理）→ 需要幂等（见 F06）\n");

        System.out.println(">> ack 机制：先 ack 后处理 = at-most-once（崩了会丢）；先处理后 ack = at-least-once（崩了会重，但不丢）。");
        System.out.println(">> 生产几乎都用 at-least-once + 消费端幂等。真正的 exactly-once 要靠 broker 去重 + 事务（如 Kafka 事务），代价高。");
    }
}
运行中… javac F05_Ack.java && java F05_Ack
▌ 真实输出（本机 10 核 · OpenJDK 21 实跑）
【at-most-once：先 ack 后处理】
  收到消息 → 先 ack（broker 已删除）→ 再处理...
  处理到一半崩溃！→ broker 里已经没这条消息了 → 消息永久丢失 ✗
  结果：broker 中消息 = 已丢失（最多消费一次，可能丢）

【at-least-once：先处理后 ack】
  收到消息 → 先处理...
  处理到一半崩溃！→ 还没 ack → broker 保留消息，稍后重投
  重启后：broker 重投这条消息 → 这次处理成功 → ack
  结果：消息没丢，但可能被处理 2 次（崩前处理一半 + 重投又处理）→ 需要幂等（见 F06）

>> ack 机制：先 ack 后处理 = at-most-once（崩了会丢）；先处理后 ack = at-least-once（崩了会重，但不丢）。
>> 生产几乎都用 at-least-once + 消费端幂等。真正的 exactly-once 要靠 broker 去重 + 事务（如 Kafka 事务），代价高。
投递语义 Delivery Semantics

三种：at-most-once(最多一次，可能丢)、at-least-once(至少一次，可能重，主流选择)、exactly-once(恰好一次，要 broker 去重 + 事务，贵)。消息在三个环节都可能丢：生产端(发送失败要重试/确认)、broker 端(没落盘就宕机 → 要刷盘 + 多副本)、消费端(处理前就 ack → 本 demo)。

F06

重复消费 + 幂等

at-least-once 会重投同一条消息(扣款 3 次)，消费端用去重表避免重复执行。

import java.util.*;
// 异步层 | 轴③ 兜底 | 重复消费 + 幂等：at-least-once 会重投，消费端必须去重
public class F06_Idempotent {
    static int balance1 = 100, balance2 = 100;
    static final Set<String> processed = new HashSet<>();     // 去重表：记录已处理的消息 ID

    static void consumeNaive(String msgId, int amount) {       // 无幂等：来一条扣一次
        balance1 -= amount;
    }
    static void consumeIdem(String msgId, int amount) {        // 幂等：先查去重表，处理过就跳过
        if (processed.contains(msgId)) { System.out.println("    消息 " + msgId + " 已处理过，跳过(幂等)"); return; }
        balance2 -= amount;
        processed.add(msgId);
    }
    public static void main(String[] a) {
        System.out.println("一条扣款消息(扣 50)因重试被重复投递 3 次：");
        for (int i = 0; i < 3; i++) consumeNaive("msg-1", 50);
        System.out.println("  【无幂等】余额: 100 → " + balance1 + "   (扣了 3 次! 多扣了 100)");
        for (int i = 0; i < 3; i++) consumeIdem("msg-1", 50);
        System.out.println("  【幂等】  余额: 100 → " + balance2 + "    (只扣 1 次，重复消息被去重表挡住)");
        System.out.println(">> at-least-once 会重复投递，消费端必须幂等：用唯一消息 ID 去重(去重表 / Redis SETNX / 数据库唯一键)，重复消息不重复执行。");
    }
}

幂等 Idempotent

幂等 = 同一操作执行多次和执行一次效果相同。实现：唯一消息 ID + 去重(Redis SETNX / 数据库唯一键 / 状态机)。它是 at-least-once 的必备搭档：既然"不丢"就意味着"会重"，那就让"重了也没事"。本 demo：无幂等扣成 -50，幂等只扣一次到 50。

F07

顺序消息

同一用户的 充值→下单→退款 必须按序。多分区并行会乱序；按 key 进同一分区则有序。

import java.util.concurrent.*;
// 异步层 | 轴③ 兜底 | 顺序消息：同一实体的消息按 key 进同一分区，保证局部有序
public class F07_Order {
    static void handle(String msg, int ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) {}
        System.out.println("    处理完成: " + msg);
    }
    public static void main(String[] a) throws Exception {
        String[] ops = {"①充值100", "②下单扣100", "③退款100"};
        int[] cost = {150, 80, 30};                            // 故意让后面的更快完成, 暴露并行乱序

        System.out.println("同一用户的 3 个操作，业务上必须按 ①→②→③ 顺序处理。");
        System.out.println("【多分区并行】3 条消息分到不同分区，3 个线程并行处理：");
        ExecutorService p = Executors.newFixedThreadPool(3);
        CountDownLatch l = new CountDownLatch(3);
        for (int i = 0; i < 3; i++) { int id = i; p.submit(() -> { handle(ops[id], cost[id]); l.countDown(); }); }
        l.await(); p.shutdown();
        System.out.println("  → 乱序了! ③退款 比 ①充值 先完成 → 业务错乱(退了还没充进来的钱)\n");

        System.out.println("【同 key 同分区】3 条消息按 userId 哈希进同一分区，单线程顺序消费：");
        for (int i = 0; i < 3; i++) handle(ops[i], cost[i]);
        System.out.println("  → 严格 ①→②→③，顺序正确");
        System.out.println(">> 顺序消息：把同一实体(同一 userId)的消息按 key 哈希到同一分区，分区内单线程顺序消费 → 保证局部有序。全局有序代价大、很少用。");
    }
}

局部有序就够了

全局有序(整个 Topic 严格有序)要求单分区单消费者，吞吐极低，几乎不用。实际用局部有序：把同一 userId/订单ID 的消息按 key 哈希进同一分区、分区内单线程顺序消费，保证"这个实体"的消息有序，不同实体之间无所谓。又快又够用。本 demo 并行版 ③ 比 ① 先完成 → 业务错乱。

F08

死信队列

msg-bad 是脏数据永远失败，重试 3 次后投入死信队列，不阻塞 msg-2/msg-3。

import java.util.*;
// 异步层 | 轴③ 兜底 | 死信队列：反复处理失败的"毒消息"隔离掉，不阻塞后续
public class F08_DeadLetter {
    static LinkedList<String> dlq = new LinkedList<>();        // 死信队列
    static final int MAX_RETRY = 3;
    static boolean handle(String msg) {
        return !msg.contains("bad");                          // 假设 'bad' 消息是脏数据, 永远处理失败
    }
    public static void main(String[] a) {
        String[] msgs = {"msg-1", "msg-bad", "msg-2", "msg-3"};
        for (String msg : msgs) {
            boolean ok = false;
            for (int r = 1; r <= MAX_RETRY; r++) {
                if (handle(msg)) { System.out.println("  " + msg + " 处理成功"); ok = true; break; }
                System.out.println("  " + msg + " 处理失败，第 " + r + " 次重试...");
            }
            if (!ok) {
                dlq.add(msg);
                System.out.println("  " + msg + " 重试 " + MAX_RETRY + " 次仍失败 → 投入死信队列，不再阻塞后续");
            }
        }
        System.out.println("死信队列内容: " + dlq + "   (留给人工排查 / 定时再处理)");
        System.out.println(">> 死信队列(DLQ)：反复处理失败的'毒消息'丢进专门的队列，避免它卡住正常消息；之后人工排查或修复后重投。");
    }
}

死信队列 Dead Letter Queue, DLQ

专门存"处理不掉的消息"。触发：重试 N 次仍失败 / 消息过期 / 队列满。作用：把"毒消息"(脏数据、触发 bug 的消息)隔离出来，别让它无限重试、卡住整条消费链；之后人工排查或修复后重投。

补一个高频考点：业务和发消息的一致性（事务消息）

"扣了款"和"发了消息"必须同时成功或同时失败，否则：扣款成功但消息没发出去（漏发）、或消息发了但扣款回滚了（乱发）。解法：① 本地消息表——把"要发的消息"作为一条记录，和业务数据写在同一个本地事务里，再由后台扫描表把消息投出去；② 事务消息（RocketMQ）——先发"半消息"→执行本地事务→根据结果提交或回滚。本质都是用最终一致解决分布式事务（呼应缓存层那个"强一致做不到、接受最终一致"）。

一句话总结异步层

消息队列干三件事：① 用异步把非核心耗时操作从主链路剥离（减负）② 用解耦 + 分区 + 消费者组让生产消费各自水平扩展（摊薄）③ 用削峰挡洪峰、ack 保证不丢、幂等容忍重复、分区保证局部有序、死信隔离毒消息（兜底）。
